# B 터미널 입력 예제

## 단일 계약 통합 시연: PO-261104-018

한 계약으로 계약 해석 → 납품 전망 → 운송 조건 변경 → 대응 초안 흐름을
확인하기 위한 자료다. 메일과 운영 현황은 업무 문서 형식으로 작성했으며,
합성 출처·파일 해시·원문 대조 항목과 기대 계산값은 관리 파일에 분리했다.
회사명과 발주·운영 기록은 실제 거래 증빙이 아니다.

- [발주 메일](delivery_800_mail.md): 서린제어시스템 → 온결테크,
  최종 ESP32-POE / L / WROOM 800개, 2026-11-05 16:00 고객 도착.
  이전 견적 1,000개·미채택 L1·본사 주소와 최종 조건을 구분한다.
- [계약 및 운영 현황](delivery_800.md): 도착 100개·운송 중 100개·창고 200개·
  생산 배정 400개(관측 양품 100개 포함). 단일 납품 회차의 분할 출하다.
- [관리 정보](delivery_800_manifest.json): 합성 출처, 원문과 운영 자료의 연결,
  SHA-256, 필드별 대조 위치, 기대 계산값. 모델에 전달할 원문이 아니다.

| 확인 항목 | 운송 2시간 | 운송 3시간 30분 |
| --- | --- | --- |
| 기한 내 도착 예상 | 800개 | 700개 |
| 부족 예상 | 0개 | 100개 |
| 전량 도착 예상 | 11월 5일 15:30 | 11월 5일 17:00 |
| 생산 완료 예상 | 11월 5일 13:00 | 11월 5일 13:00 |
| 새 출고 검토 수량 | 600개 | 600개 |
| 기한 내 / 기한 후 새 출고 검토량 | 600개 / 0개 | 500개 / 100개 |

이 자료는 추가 파일로 보관한다. 기존 정상·지연 두 예제와
`mail_demo_cases.json`은 변경하지 않았다. **현재 웹 계약 카드와 LLM 메일 실행의
허용 목록에는 아직 연결하지 않았다.** 새 메일을 바로 기존 LLM 명령에 넣는 것은
지원하지 않으며, 아래는 운영 자료의 기존 B 계산만 확인하는 무료 명령이다.

```bash
.venv/bin/python -B - <<'PY'
from pathlib import Path
from examples.order_fulfillment.b_terminal_input import load_input, case_task

source = load_input(Path('data/order_fulfillment/examples/delivery_800.md').resolve())
_, task = case_task('cq06_transport2h', source)
comparison = task.data()['assessment']
for key, label in [('before', '운송 2시간'), ('after', '운송 3시간 30분')]:
    forecast = comparison[key]['forecast']
    print(label, forecast['on_time_quantity'], forecast['shortfall_quantity'],
          forecast['estimated_full_arrival_at'])
PY
```

운영 자료의 표는 정해진 입력을 구성하기 위한 별도 자료다. LLM 원문 추출에
표·관리 정보·기대 결과를 함께 넣어 정답을 제공하지 않는다. 실제 LLM 해석과
한국어 초안 품질은 이 새 자료로 아직 확인하지 않았다. 기존 제품 정의·계산 코드·
공통 API·A/C 데이터와 화면·업무 DB는 변경하지 않는다.

## 납품 관리 담당자의 세 상황

현재 `main`의 단일 납품 회차 범위로 정상·일부 지연·운송 조건 변경을 비교하는
[시연 상황과 입력 방법](DEMO_SCENARIOS.md)을 추가했다.
[정상 입력](demo_normal_800.md)과 [지연 입력](demo_risk_800.md)을 사용하며,
정상 입력은 창고 200개·최근 양품 100개/시간·운송 2시간이며,
지연 입력은 창고 100개·최근 양품 50개/시간·운송 2시간 30분이다.
세 번째 상황은 지연 입력의 기존 CQ06 운송 2시간 30분→3시간 30분 비교다.
아래 기본·혼합 기존 사례와 당시 실행 기록은 보존한다.

## 기본 사례: B-BASIC-800

같은 계약을 서로 다른 시각에 관측한 가상 자료다. 고객은 가상고객사 B,
제품은 ESP32-POE / L / WROOM, 약속은 800개를 2026-10-30 15:00 한국 시간까지
가상고객사 B 제2수령창고에 도착시키는 것이다. 실제 거래·생산·검사 자료가 아니다.

전량을 하나의 생산 작업에 배정한다. 06시 생산을 시작하고 09시 양품 누계300개,
10시 양품 누계400개를 관측한다. 양품을 별도 재고로 중복 합산하지 않는다.
창고·운송·기납품은 명시적으로0개다. 준비30분·운송2시간·분할 출고와
최근 추세 지속은 이 예제에 적은 계산 가정이다.

| 순서 | CLI case | 입력 파일 | 확인할 결과 |
| --- | --- | --- | --- |
| 1 | `cq01_intake` | `basic_800_0600.md` | 고객·제품·800개·납기·장소에 맞는 계약 후보, 저장·승인은 미수행 |
| 2 | `cq01_promise` | `basic_800_0600.md` | 위 납품 약속 설명, 이행 가능성은 아직 판단하지 않음 |
| 3 | `cq02_normal` | `basic_800_0600.md` | 06시 진행800개, 다른 상태0개, 미납품 잔량800개 |
| 4 | `cq03_normal` | `basic_800_1000.md` | 10시 완료400개, 남은400개, 최근 양품100개/시간, 생산 완료 예상14시 |
| 5 | `cq04_mixed` | `basic_800_1000.md` | 기한 내650개, 부족150개, 전량 도착 예상16:30 |
| 6 | `cq05_mixed` | `basic_800_1000.md` | 새 출고 검토800개=확보400+미래400, 출고 요청·고객 회신 초안, 기한 후150개 |
| 7 | `cq06_transport2h` | `basic_800_1000.md` | 운송2→3시간: 기한 내650→550개, 부족150→250개, 전량16:30→17:30 |

`cq04_mixed`와`cq06_transport2h`는 기존 CLI 선택 이름이다. 실제 조건은 선택한
파일의 값으로 결정되므로 CQ06은 여기서2→3시간이다. 각 명령은 독립 실행이며
앞 CQ의 LLM 출력을 다음 CQ로 자동 전달하지 않는다. 10시 원문으로 CQ02를
실행하면 생산 완료400개와 미완료 진행400개를 구분한다. 생산 완료는 창고 입고나
납품 완료를 뜻하지 않으며, 미납품 잔량은 여전히800개다.

## 터미널에서 한 대표씩 실행

저장소 루트와 가상환경에서 첫 접수를 실행하는 명령이다. 실제 API를 사용하며
이번 대표의 비용 상한은1달러다. 이후에는 위 표의 입력 파일과 case를 함께 바꾸고
출력 디렉터리도 새로 지정한다. 같은 디렉터리 재사용이나 실패 자동 재시도는 하지 않는다.

```bash
cd /Users/junhwa/Desktop/Ontol/ontologics
source .venv/bin/activate

B_BASIC_OUT="/private/tmp/b-basic-cq01-$(date +%Y%m%d-%H%M%S)-$RANDOM"

python -B -m examples.order_fulfillment.b_run run \
  --output "$B_BASIC_OUT" \
  --input "$PWD/data/order_fulfillment/examples/basic_800_0600.md" \
  --cost-policy "$PWD/artifacts/local/order_fulfillment/b_min_validation_20261030_7_233r2n/public-cost-policy.json" \
  --case cq01_intake \
  --transport openai \
  --representative-max-cost-usd 1.00

cat "$B_BASIC_OUT/shutdown.json"
```

위 명령은 유료 API를 사용한다. 이번 B 보완 작업에서는 실행하지 않는다.
무료 계산 확인과 HTTP 모의 응답 연결 검사는 실제 LLM의 한국어 답변 품질 성공을 뜻하지 않는다.
CQ01 약속의 제품 노드 조회 지침과 CQ01 접수 요약 지침을 보완했지만,
새 지침의 실제 LLM 답변 품질은 별도 실행으로 확인해야 한다.

## 기존 혼합 사례

`terminal_800.md`는 납품100·운송100·창고200·생산400이라는 별도 계약
B-TERMINAL-800의 예제다. 입력 원문은 보존했다. 현재 B 계산은 다음과 같다.

- CQ02: 납품100·운송100·창고200·생산 완료100·미완료 진행300개, 합계800개.
  미납품은700개다. 생산 완료분을 창고 재고에 중복 합산하지 않는다.
- CQ03: 전량 배정된 생산 작업400개 중 양품100개·남은300개,
  최근 양품 속도 시간당100개를 가정한 작업 완료 예상13시다.
  계약 전체의 생산·납품 완료 예상이 아니다.
- CQ04/05: 기한 내750개·부족50개·전량 도착 예상15:30,
  새 출고600개=현재 확보300개+미래 생산300개다.
- CQ06 운송2→3시간: 기한 내750→650개·부족50→150개·전량15:30→16:30.

일부 수량만 배정되거나 같은 생산 작업을 여러 회차에 나눈 경우에는 완료분의
회차별 귀속을 추정하지 않는다. 관측 시각은 `as_of`, 조회 시각은 `queried_at`이다.
기존 실제 성공·실패 결과는 당시 코드의 기록으로 유지하며 이번 무료 계산 결과와 구분한다.
