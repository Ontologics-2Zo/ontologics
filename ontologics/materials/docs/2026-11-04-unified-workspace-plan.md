# A 통합 화면 연결 계획

## 후속: 단계별 화면 흐름 개선

사용자 요청: 생산·자재 계획 안에서 무엇을 눌러야 하는지, 처리 후 무엇이 바뀌었는지 분명하게 보이도록 페이지를 나눈다. 이번 후속 변경은 `ontologics/static/planning.js`의 A 전용 화면과 이 문서에 한정한다.

설계: 기존 긴 화면에 안내만 추가하는 대신, 계약은 목록 → 원문 대조 → 제품 연결 → 계산 조건 → 결과, 요청은 목록 → 내용 확인 → 결과, 제품은 수량 → 제품 비교 → 결과로 나눈다. 현재 단계와 대상, 주 행동을 표시하고 완료 시 다음 화면으로 이동·포커스한다. RFQ는 결과에서 별도 보기로 열고 돌아갈 수 있게 한다. 기존 API·계산식·권한·미확인 규칙은 유지한다.

- [x] 단계 이동, 영역 내 진행·오류·완료 안내, 입력 유지 및 이전 결과 무효화 구현.
- [x] 계약/요청/제품 흐름과 RFQ 보기·다운로드를 기존 API에 연결.
- [x] 실제 화면의 주요 흐름·실패·뒤로가기·수량 변경을 확인하고 관련 회귀 검증.

공통 스타일 파일 대신 A 컨테이너 내부에 한정된 스타일을 사용한다. 다른 메뉴·백엔드·스키마는 변경하지 않는다. 이전 작업의 미커밋 변경은 보존한다.

화면 검증 근거: 실제 로컬 HTTP의 제품 200대 비교 → 결과 → RFQ TXT 다운로드, 200→30 조건 변경 시 이전 결과 제거, 120대 요청 계산, 계약 품목이 없는 30대 요청 차단, 기존 가상 계약 70대 계산 및 입력 복원을 확인했다. 같은 계약의 원문 대조를 재저장할 때 기존 연결이 유효하게 유지되는 경로도 확인했다. 통신 실패는 브라우저에서 한 차례 요청을 차단해 재현했고 입력 보존·오류 표시·실서버 재시도 성공을 확인했다. 760px 폭의 A 영역 넘침 없음, 다른 메뉴 이동 후 A 스타일 미적용 및 재진입 시 스타일 중복 없음, JS/CSP 오류 0을 확인했다.

검증 중 수정: inline style을 거부하는 기존 CSP를 유지하기 위해 신뢰된 A 화면 스크립트의 구성형 스타일시트를 사용했다. 모든 선택자는 `.materials-workspace` 하위에 한정된다. 공통 로딩이 끝나기 전에 새 A 버튼을 클릭해 동작이 무시되는 문제는 기존 공통 busy 표시를 관찰하여 A 영역을 잠그는 방식으로 해결했다. 새 권한·계산·공통 실행 로직을 만들지 않았다.

최종 검증: 실제 계산·다운로드 브라우저 흐름 재실행 통과, 요청 읽음 응답 지연 후 다음 단계 포커스 이동 통과, JS 구문·diff 검사 통과. 전체 unittest 1,713개 중 1,702개 통과, 환경 조건 11개 건너뜀, 실패 0개(722.245초, 종료 코드 0). 관련 로그·스크린샷은 로컬 임시 경로에만 보관한다. 이번 UI 후속 변경에서는 유료 모델 호출·그래프 승인·재고 차감·발주·외부 발송을 수행하지 않았다.

사용자가 승인한 범위: main의 생산·자재 계획 본문과 materials 연결 코드, 관련 테스트만 수정한다. 공통 코드·스키마·B/C·상단·메뉴는 수정하지 않는다. 기존 계약과 추가 요청의 자동 합산은 제외한다.

목표: 계약 검토 / 추가 생산 요청 / 제품별 자재 세 구역에서 기존 BOM·공정 자재 계산과 미발송 RFQ 초안을 이용한다. 수량을 한 번 전달하며 사용량·재고 미확인은 그대로 유지한다.

- [x] A workspace에 기존 요청 조회/검토와 제품 재고/공정 계산 연결. 결합 검토는 기존 계산기를 호출하고 근거와 초안을 A 로컬 기록에 보관한다. 실제 DB 테스트로 권한·멱등·수량·미확인·기존 연결 검증.
- [x] planning.js 본문에 세 구역, 제품별 토글, 동일 수량 계산, 근거 표시, 초안 다운로드를 연결한다. 변경된 입력에 이전 결과를 사용하지 못하게 한다.
- [x] A 전용 설정으로 요청 원본 저장소를 연결한다. 기본값은 동일 Host이며 별도 저장소는 서버 설정만 사용한다. 자격증명은 브라우저로 전달하지 않는다.
- [x] main 실제 HTTP 및 브라우저로 추가 요청과 제품별 계산·다운로드를 검증한다. 공통 사실·재고 차감·예약·외부 발송은 수행하지 않는다.
- [x] 관련 검사와 전체 회귀, 독립 검토 후 결과를 기록한다. 기존 미커밋 작업을 보존하고 자동 커밋/푸시하지 않는다.

검토 초점: 다른 회사 재고 혼용, 오래된 수량의 다운로드, 미확인의 0 변환, 조회자 권한 상승, 분리된 요청 저장소의 데이터 버전 혼동.

## 실행 설정

main의 기존 `ontologics.web serve`를 사용한다. 기본 요청 조회는 A와 동일 저장소다. 개발 환경에서만 별도 저장소가 필요한 경우 서버 시작 전에 다음 A 전용 환경변수를 지정한다.

- `MAT_REQUEST_SCHEMA`: 요청이 등록된 PostgreSQL schema
- `MAT_REQUEST_DATABASE_ENV`: 해당 저장소의 로컬 비밀 설정 파일 경로. 명시 파일은 A의 DATABASE_URL과 섞지 않는다.
- `MAT_REQUEST_GRAPH_BACKEND`: `neo4j` 등 기존 공통 조회 backend
- `MAT_REQUEST_GRAPH_ENV`: 그래프 접속 설정 파일
- `MAT_REQUEST_GRAPH_NAMESPACE`: 선택한 Neo4j 조회 공간

코드에 실제 저장소 이름·비밀번호·요청 ID를 넣지 않는다. 웹 요청으로 연결 대상을 변경할 수 없다. 이번 로컬 시연은 기존 승인 요청 v1~v4를 별도 Neo4j 조회 공간에 동기화했고 snapshots 해시가 전후 동일함을 확인했다. 기존 Neo4j 조회 공간은 유지했다.

### 2026-11-04 추가 요청 그래프 연결 복구·재검증

요청 목록이 0건이었던 원인은 실행 중인 통합 웹에 위 `MAT_REQUEST_*` 설정이 전달되지 않아 A의 기본 저장소를 조회한 것이었다. 기존 B 저장소에는 승인된 요청 2건과 `graph-0.4`에 맞는 Neo4j 조회 공간이 이미 있었다. 기능·공통 코드·스키마를 추가하지 않고 기존 `configured_request_host` 설정을 복구했다.

개발 환경에서 A와 B 저장소가 다르면 위 다섯 설정을 Git 제외 로컬 파일(예: `.env.materials-requests.local`)에 보관하고 **웹 서버 시작 전에 프로세스 환경으로 로드**한다. 파일을 생성하는 것만으로 자동 적용되지는 않는다. 현재 로컬 실행 래퍼는 공통 환경값 파서로 이 파일을 읽는다. 팀원이 실행할 때는 자신의 DB/schema·비밀 설정 경로·현행 스키마로 동기화된 Neo4j namespace를 사용해야 하며, 이 컴퓨터의 임시 경로를 복사하지 않는다. A/B가 같은 승인 저장소를 쓰면 별도 설정은 필요 없다.

복구 후 기존 120대 요청은 원래 계약·품목에 연결되어 조회됐다. 과거 30대 요청은 계약 품목 참조가 없어 기존대로 보완 필요로 표시했다. 과거 원문이나 계약을 임의로 정정하지 않았다.

사용자가 요청한 새 가상 시나리오는 기존 B `prepare_request`로 등록했다.

| 항목 | 등록 내용 |
| --- | --- |
| 요청 | `MREQ-RC-20261104-060` · 개정 1 |
| 기존 계약·품목 | `contract:planning:001` / `contract-item:planning:001` · 기존 100대 |
| 제품 | `config:esp32-poe:L:WROOM` |
| 추가 수량·사유 | 출하 검수동 서부·중앙·동부 3개 구역 × 20대 = 60대. 기존 계약과 포장·검수 구역용 120대 요청에 중복되지 않는 별도 수요 |
| 필요일 | 2026-11-27 · 생산 완료 기준 |
| 기준 근거 | `evidence:demo:plan:RC-20261103-01` · 기존 BOM, 임의 대체 없음 |
| 자료 구분 | `synthetic` · 기존 개발 검토 신원으로 검증한 가상 요청 |

등록은 기존 B 요청 원문 보관 → 공통 초안 검증 → 별도 개발 검토자 승인 → 공통 반영·Neo4j 동기화를 사용했다. 요청은 기존 `SourceDocument`·`Evidence` 두 노드로 저장하고 문서 안의 계약 품목·제품·기준 근거 ID를 검증한다. 새로운 요청 타입이나 전용 관계를 추가한 것이 아니다.

검증 결과:

- 승인 전 새 요청이 조회되지 않음, 동일 키 초안 재시도는 같은 초안으로 복원.
- B 승인 데이터 v4 → v5, 실제 Neo4j 노드 552 → 554, 요청 2 → 3건. 기존 v4 해시와 모든 기존 노드 내용 유지.
- PostgreSQL 정본과 Neo4j의 정확한 버전 전체 노드·요청 원문 재조회 결과 일치.
- 실제 Chrome의 추가 생산 요청 탭에서 새 요청·기존 계약 100대·추가 60대·제품·해시 검증된 계약 원문 확인. 문제 목록 없음, 계산 버튼 활성화, 새로고침 후 유지.
- 상세 열람으로 새 요청은 `new` → `seen`이 됐다. 계산·RFQ 생성·메일 발송은 수행하지 않았다. A 승인 그래프 버전은 기존 v1을 유지했다.
- 요청 저장소 설정·기존 등록/조회/계산/Neo4j 경로 관련 테스트 **17개 통과**, 브라우저 JavaScript 오류 0건. 이번 변경은 실행 설정·가상 데이터·이 문서에 한정하며 기존 미커밋 기능 변경은 보존했다.

화면 확인: 생산·자재 계획 → 추가 생산 요청 → 목록 새로고침 → `MREQ-RC-20261104-060`의 요청 내용 확인. 기존 계약 수량과 합산하지 않고 추가 60대만 다음 자재 계산으로 전달한다. 원문·데이터·실행 설정은 Git만 받아서 이전되지 않으므로 발표 환경의 저장소 준비가 별도로 필요하다.

## 검토 중 보완

- 명시적인 새 검토는 새 요청 키를 사용하여 같은 수량이어도 최신 재고를 다시 계산한다. 기존 공통 멱등 처리는 그대로다.
- 계약 재열기 시 결합 검토를 조회한다. 제품 연결·재고가 바뀐 저장 결과는 현재 결과로 표시하거나 다운로드하지 않는다.
- 계약에 이미 예약한 수량은 기존 BOM owner 규칙을 재사용해 중복 차감하지 않는다. 추가 요청과 다른 제품의 검토에는 해당 점유량이 가용량에서 차감된다.


## 브라우저 검증 근거

- 실제 main HTTP 화면에서 기존 요청 2건 조회. 완전한 120대 요청은 BOM/공정 검토와 부족 64종 초안 표시. 계약 품목이 없는 30대 요청은 보완 필요 유지.
- 제품 비교 200대 입력으로 Rev L/L1 두 제품 토글 확인. Rev L 공정 5종 계산, 액상 플럭스 부족 45.828 g 표시.
- 같은 200대 재검토 시 검토 시각이 갱신됨. 실제 RFQ TXT 다운로드와 내용(200대, BOM 부족 품목)을 확인.
- 200→30 수량 입력 변경 시 이전 결과/다운로드 제거 확인.
- 이미 연결된 가상 계약의 기존 검토량 70대 유지, 통합 계산 후 계약 재열람 시 수량/여유율/저장 결과 복원 확인.
- 외부 모델 호출·발송·발주·재고 차감 없이 기존 자료로 수행했다. A 로컬 검토 결과만 추가됐다.

## 최종 검증

- 최종 코드 기준 전체 unittest: 1,713개 중 1,702개 통과, 11개 환경 조건으로 건너뜀, 실패 0개. 실행 시간 756.626초, 종료 코드 0.
- 건너뛴 항목은 Shapely 2 관련 4개, Docker/명시적 통합 실행 조건 관련 6개, order_fulfillment 요청 입력 통합 환경 관련 1개다.
- `node --check ontologics/static/planning.js`, `git diff --check` 통과.

- 기존 미커밋 요청 처리 작업은 보존했다. 이번 연결 작업의 변경 범위는 A 화면인 `planning.js`, materials 연결 코드·문서, materials 테스트다. 공통 호스트·스키마·다른 메뉴·order_fulfillment 코드는 수정하지 않았다.
