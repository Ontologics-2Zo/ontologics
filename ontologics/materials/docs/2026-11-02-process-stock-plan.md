# 공정 자재 재고 조회 구현 계획

목표: 기존 BOM 재고 화면과 계약 보관함에서 공정 자재의 가상 회사 재고·조건부 수치·제품 및 근거 연결을 확인한다.

설계: materials 내부의 파일 근거 어댑터와 별도 PostgreSQL 시나리오 원장을 사용한다. 공통 온톨로지 스키마는 변경하지 않는다. 구성-공정검토-자재-로트-근거 관계를 A 전용 조회 그래프로 표현하며 적용 후보를 실제 승인 공정으로 표시하지 않는다. 두 구성이 동일 공용 재고를 참조한다. 재고는 명시적인 초기 등록으로만 생성하고 조회에서 가정값을 생성하지 않는다.

범위: materials 디렉터리 내부 코드 및 tests/materials 검사. 공통 모델·서비스·DB 코드는 수정하지 않는다. 기존 소스 데이터는 읽기 전용으로 사용한다. 수량은 Decimal과 단위를 사용하고 미확정 수요는 null로 유지한다. 재고 등록은 기존 host review 권한과 감사 경로를 사용한다.

- [x] 데이터/재고 규칙 실패 테스트: 해시 오류, 만료·보류·예약 차감, 구성 공유, 조건부 부족 범위, 미확인 유지.
- [x] library_process_materials.py: 근거 검증, 가상 로트 등록, 읽기 및 관계 조회.
- [x] contract_library_web.py: 읽기 API 및 명시적 시나리오 초기화 CLI 연결.
- [x] library_static: 회사 공정 자재 화면, BOM 검토 내 요약, 재고·근거·공유 구성 탐색.
- [x] 격리 PostgreSQL 통합/HTTP 및 브라우저 검증. 기존 코드 범위 회귀 실행.

사용자 승인 범위: 가상 회사 재고 생성과 웹 기능 구현은 이번 요청으로 승인됨. 배포/외부 발송/실제 공정 승인 없음. 실제 소비량이 없는 자재에는 재고만 표시하고 충분 판정을 하지 않는다.

검증: 신규 규칙/격리 DB/HTTP 테스트 12개 통과. 브라우저에서 L/L1 공용 재고, 100대/10대 플럭스 비교, 공식 근거 연결, 가상 재고 표시 확인. JS 문법·diff 검사 통과. 전체 회귀 결과는 PROJECT_STATUS.md에 기록한다.

## 제품별 통합 조회 후속 변경

사용자 확정 구성: 제품별 접기/펼치기 아래 기존 BOM과 공정 자재를 함께 표시한다. 상단 진입점은 ‘제품별 자재 재고’이며 기존 공정 재고 링크도 통합 화면으로 연결한다. 모두 펼치기/접기, 제품별 독립 비교 수량, 자재별 근거/로트 펼치기, 공용 재고를 참조하는 다른 제품으로 이동을 제공한다.

구현 범위는 materials 내부 5개 코드 파일뿐이다. product-inventory 읽기 API는 기존 카탈로그 조회와 BOM/재고 계산을 재사용하고 계획을 저장하거나 예약을 만들지 않는다. 전체 기존 계획 예약을 차감하므로 특정 계약의 자기 예약을 제외하는 계약 검토와 결과가 다를 수 있다. 재고 미연결을 0으로 바꾸지 않는다. 같은 재고의 제품별 표시를 합산하거나 동시 생산 가능 판정으로 해석하지 않는다.

검증: 임시 격리 DB 검사에서 두 구성×74개 BOM, 재고 미연결, 수량0/잘못된 입력, 생산계획 미저장을 확인. 브라우저에서 모두 펼치기/접기와 개별 토글, L 수량10·L1 수량100의 독립 유지, BOM/공정 동시 표시 확인. JS 문법/diff 검사 통과. 기존 전체 회귀의 환경 오류는 이전 기록 참조.

관련 회귀: 공정 자재/계약 보관함 25개 통과(77.033초). 통합 조회 임시 DB 검사도 통과. 전체 회귀는 이번 후속 UI 변경에서 재실행하지 않았다. 화면 증빙: /private/tmp/ontologics-product-inventory.png.
