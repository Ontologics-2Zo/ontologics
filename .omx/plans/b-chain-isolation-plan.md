## 1. 목표와 이름

추천 이름은 `order_fulfillment`, 한국어로 **계약·납품 이행 관리**다. 계약상 수량/회차 확인 → 현재 물량 → 생산 완료 예상 → 고객 도착 예상 → 대응 초안 → 변경 전후 비교라는 CQ01~06을 포괄한다. A의 `production_planning`이 생산 계획을 맡는다면 B는 그 생산 정보가 고객 약속 이행에 미치는 영향을 설명한다. A/B 간 실제 데이터 계약은 아직 구현된 것으로 보지 않는다.

`delivery_forecast`는 CQ04만 나타내고, `production_planning`은 A와 소유권이 겹치므로 B 전체 이름으로 사용하지 않는다. 이름은 추천안이며 아직 기존 파일·Agent 이름·데이터 ID를 바꾸지 않는다.

요구사항:

- B의 업무 코드·데이터·문서·예제·테스트는 B 전용 경로에 둔다.
- 클론한 공통 파일과 기존 클래스·메서드는 B 작업에서 수정하지 않는다. 공통 로직도 복사해 독자 구현하지 않는다.
- 온톨로지는 기존 타입·관계·필수 필드·의미를 유지하고 신규 정의만 확장한다.
- 승인·검증·사용자 권한·실행 기록·근거·시간 규칙은 기존 기반을 재사용한다. Agent에게 승인·반영 권한을 주지 않는다.
- 기존 CQ01~06 동작과 과거 증거를 보존한다. 분리 후에는 새 코드에서 재검증한다.

## 3. 먼저 해결해야 할 기술적 조건

**현재 main에서 공통 코드가 완전히 그대로인 채, 신규 B 타입을 기존 승인 경로에 저장하고 신규 B 도구를 기존 CommonHost로 실행하는 것은 공개 확장점만으로는 불가능하다.**

- `origin/main:ontologics/model.py:89`는 SCHEMA 밖 타입을 거부한다. 현재 파일의 대응 위치는 `ontologics/model.py:119`다. 별도 TTL 파일만 추가해도 Python 검증·승인·직렬화가 확장되지는 않는다.
- `ontologics/host.py:50`은 새 역할에 기존 허용 도구만 등록하도록 제한한다. 새 역할 등록과 새 도구 등록은 서로 다르다.
- `ontologics/host.py:92`는 Service를, `:177`은 ModelRuntime을 직접 생성한다. `runtime.py:81`도 Gateway를 직접 만든다. B subclass 파일을 만들어도 자동으로 사용되지 않는다.
- main의 Provider는 중앙 `function_tools`를 호출하고 그 함수도 중앙 허용 목록을 확인한다. 현재의 B 전용 응답 설정도 원래 main의 공개 계약에는 없다.

따라서 다음 책임을 구분한다.

| 담당 | 책임 |
| --- | --- |
| B 담당 | 전용 폴더의 업무 기능·스키마 추가 정의·도구·Agent·테스트 제공. 기존 공개 클래스/메서드는 호출해 사용. 공통 파일을 직접 고치지 않음. |
| 공통 담당 | 신규 스키마/검증/직렬화와 도구를 안전하게 등록할 공개 확장 계약 검토. 기존 승인·권한·기록 경로에서도 같은 확장이 적용되게 보장. Provider와 실행기의 설정 접점 검토. |
| 통합 담당 | 호환되는 공통 기반과 A/B 확장을 명시적으로 조립. 같은 이름 충돌·권한·버전·회귀 검사 확인. |

공통 담당자의 기반 변경은 이 계획으로 실행 승인된 것이 아니다. **누구도 공통 파일을 수정할 수 없다는 절대 조건이면, 현재 main에서 완전한 기존 동작 보존은 차단 상태**다. 이때 읽기 계산·fixture 기반 분리 작업까지만 진행할 수 있으며, 이를 기존 승인/Agent 연결 완료로 표시하지 않는다. 확장 접점 제공 또는 제약 조정 전에는 해당 통합 작업을 시작하지 않는다.

필요한 계약은 B 전용 코드가 공통으로 침투하는 대신, 공통이 명시적 확장 정의를 받는 방식이다. 최소 범위는 다음과 같다. 구체 API 이름·파일 구조는 공통 담당자가 정한다.

1. **스키마 확장:** 신규 타입·필드·관계·검증기를 등록하고 승인/반영·JSON-LD/T-box에서도 동일하게 사용. 기존 타입 재정의·필드 덮어쓰기는 거부.
2. **도구 확장:** B 도구 설명·입력 형식·처리기와 역할별 허용 목록을 함께 등록. 같은 사용자 권한·실행 기록·오류 경계를 재사용. 기존 도구 이름 덮어쓰기 금지.
3. **실행 조립:** 호스트·런타임·Provider가 같은 등록 정의를 사용하고, B별 JSON 응답 형식·호출/출력 제한을 공개 설정으로 전달. B 미등록 시 기존 동작 유지.

설치 설정도 함께 확인한다. 현재 최상위 `pyproject.toml`은 하위 패키지를 자동 탐색하지 않으므로 공통 담당자가 제공하는 패키지 포함 설정이나 별도의 설치 명세가 필요하다. 어떤 방식을 쓸지는 팀 방식에 맞춰 확정한다. B의 공통 파일 무수정 원칙과 설치 방법을 동시에 만족하지 못하면 미해결 의존성으로 남긴다.

전역 `SCHEMA.update`, 허용 목록 강제 교체, `_gateway` 사후 교체, 공통 클래스 메서드 덮어쓰기, 공통 승인 코드 복제, DB 직접 쓰기, `lookup`에 새 B 도구를 숨기는 우회는 사용하지 않는다.

## 4. 목표 폴더 구조

**이미 있는 폴더를 그대로 사용한다.** 기존 `data/`, `examples/`, `tests/`, `ontologics/`, `ontology/` 안에 각각 B 전용 폴더 하나를 두고, B 파일은 해당 폴더 안에 둔다. `docs/`에는 B 전용 문서 파일을 둔다. B 폴더들을 한데 담는 별도의 상위 폴더는 만들지 않으며, B 전용 폴더 안에도 기능별 하위 폴더를 추가하지 않는다. 아래 경로는 작업 예정이며 이번에는 폴더 생성이나 코드 이동을 하지 않았다.

```text
data/order_fulfillment/        # 기존 data 안의 B 데이터
examples/order_fulfillment/    # 기존 examples 안의 B 예제
tests/order_fulfillment/       # 기존 tests 안의 B 테스트
ontologics/order_fulfillment/  # 기존 ontologics 안의 B Python 파일
ontology/order_fulfillment/    # 기존 ontology 안의 B 온톨로지 파일
docs/order_fulfillment.md     # 기존 docs 안의 B 문서 파일
```

`docs/order_fulfillment/` 폴더는 만들지 않는다. 공유 설명은 우선 `docs/order_fulfillment.md`에 모으고, 길어져 분리가 필요하면 `order_fulfillment_` 접두사의 전용 파일을 추가한다. 이번에 저장하는 개인 계획서는 공유 문서가 아니라 `JunhwaDocs/06_B체인_분리/B_체인_분리계획.md`다.

현재 공통 파일은 기존 위치에 두며, B 하위 패키지는 승인된 공통 버전에 의존한다. root `README.md`, `PROJECT_STATUS.md`, `docs/TOOLS.md` 등에 B 내용을 다시 끼워 넣지 않고 새 B 전용 문서를 사용한다. 공통 인덱스 연결이 필요하면 공통 담당자 변경으로 분리한다. 개인 `JunhwaDocs/`, 환경 파일과 과거 로컬 실행 원본은 공유 대상에서 제외한다.

각 종류의 목적지는 다음과 같다.

| 현재 B 자료 종류 | 분리 후 목적지 |
| --- | --- |
| `ontologics/`에 추가한 B 계산·검증과 공통 파일에서 분리할 B 처리기 | `ontologics/order_fulfillment/` |
| `examples/b_*.py`의 업무 지침·평가기·연결 코드 | 재사용할 부분은 `ontologics/order_fulfillment/` 안의 파일, 실행 예제는 `examples/order_fulfillment/` 안의 파일 |
| `data/b_*.json`, B 가상 원본 | 목표는 `data/order_fulfillment/`. 기존 출처 경로·원본 불변 규칙을 먼저 확인하고 이동/매핑 방법을 확정 |
| B 관련 테스트 | `tests/order_fulfillment/` |
| B 신규 온톨로지 정의 | `ontology/order_fulfillment/` 안의 파일, Python 실행 검증 정의는 `ontologics/order_fulfillment/` 안의 파일 |
| 기존 공통 문서에 추가한 B 설명 | `docs/order_fulfillment.md` 또는 같은 접두사의 별도 파일 |

이는 종류별 목적지다. 파일별 최종 대응표는 분리 Task 02에서 작성한다. 기존 파일을 여기서 이동하거나 지우지 않는다. 기존 원본의 경로·ID·SHA·locator와 과거 기록은 보존하고, 실제 원본 이동에 제약이 있으면 경로 매핑 또는 별도 새 근거 버전을 먼저 설계한다.

온톨로지 파일을 분리하는 것과 RDF 식별자를 바꾸는 것은 별개다. 기존 `Configuration`·`Evidence`·`SourceDocument` 정의와 ID는 재사용한다. 새 B 정의에는 팀이 합의한 namespace를 쓰되, 이미 기록된 B 타입/ID를 폴더 이름에 맞춰 일괄 변경하지 않는다. namespace 이전이 필요하면 명시적인 매핑·새 버전·호환성 검토를 거친다.

## 6. 원본 복원과 합치기 전략

현재 작업 브랜치에서 공통 변경을 바로 되돌리지 않는다. 과거 CQ01·02 공통 변경은 커밋에도 들어 있고 CQ03~06은 미커밋 파일도 있으므로, 지금 공통 파일을 복원하면 검증 가능한 현재 상태를 잃을 수 있다.

실제 분리 구현 시에는 보존한 현재 브랜치를 비교 기준으로 남기고, 합의된 공통 기준에서 분리용 브랜치/작업 공간을 만든다. 그곳에 B 추가 파일만 가져와 연결·검증한다. 공통 확장 접점이 새 팀 커밋으로 제공되면 그 커밋을 기준으로 삼는다. 현재 브랜치를 통째로 병합해서 과거 공통 수정까지 다시 끌어들이지 않는다. 이전 구현은 새 구조의 동작을 대조하는 기준으로 유지한다.

공통 파일 무수정 여부는 오래된 클론 버전이 아니라 **팀이 합의한 공통 기준 커밋 대비**로 판정한다. 공통 담당자의 승인된 기반 변경과 B의 변경을 별도 diff/커밋 단위로 구분한다. 테스트·manifest·문서·설치가 끝난 뒤에만 최종 B 변경 집합을 공유한다. 이번에는 브랜치 생성·복원·파일 이동을 수행하지 않는다.

## 7. 위험과 검증 방법

- **폴더만 옮겨 실행 불가:** 확장 계약 검사와 CQ01 수직 연결을 먼저 통과시킨다. subclass/adapter만으로 지원되지 않는 경계를 해결됐다고 처리하지 않는다.
- **원본 경로·출처 훼손:** 기존 source ID·SHA·locator·원본 파일을 보존한다. 메타데이터 변경이 필요하면 새 fixture/근거 버전과 대응표로 다루고 과거 DB/보고서를 덮어쓰지 않는다.
- **공통 권한·승인 로직 복제:** 허용된 공개 경로만 사용하고 새 B 기능이 승인·반영·신원 주입을 우회하지 못하는 음성 검사를 추가한다.
- **새 폴더가 설치되지 않음:** 공통 담당자와 B 하위 패키지·자료의 설치 계약을 확정하고 저장소 밖 import/자료 로딩 검사를 수행한다. 최상위 설치 파일을 B에서 임의 수정하거나 배포 도구·외부 패키지를 새로 도입하지 않는다.
- **테스트가 줄어도 성공처럼 보임:** 이전 요구사항/테스트 목록을 새 경로와 매핑하고 발견 수·skip·누락을 점검한다. A 패키지가 실제 제공된 뒤에만 A/B 동시 등록·이름 충돌·경계 검사를 통합 성공으로 보고한다.
- **과거 실모델 성공을 새 구조에 오인:** 무료 모의 HTTP/권한/사실/인용 검증을 먼저 수행하고, 실제 대표 재검증은 이후 별도 호출 예산으로 수행한다. 실제 호출 이전에는 통과했다고 쓰지 않는다.

## 8. 계획 단계 검증과 남은 결정

이 계획은 소스와 로컬 origin/main의 정적 비교에 근거한다. 현재 작업의 실행 테스트·DB·API는 재실행하지 않았다. 이전 586개 무료 테스트·34개 예제 및 실제 LLM 결과는 기존 코드의 기록이다.

폴더 배치는 사용자 요청대로 **각 최상위 폴더의 `order_fulfillment/` 하위 폴더 + docs의 전용 파일**로 정했다. 실행 전 추가로 정할 것은 공통 담당자가 제공할 확장·설치 접점과 그 접점을 포함하는 기준 커밋이다. **확장 접점이 없는 현재 main을 그대로 유지하면서 전체 기능을 완전 분리할 수 있다고 약속하지 않는다.** 공통 수정이 전혀 허용되지 않는 조건이 유지되면 지원 가능한 읽기 계산 범위와 차단된 승인/Agent 통합 범위를 명시한다.
