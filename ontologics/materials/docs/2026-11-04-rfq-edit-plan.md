# RFQ 수정·저장 Implementation Plan

**Goal:** 계산된 RFQ 문서를 화면에서 수정·저장하고, 선택한 저장본을 다운로드와 구매팀 메일 첨부에 사용한다.

**Architecture:** 계산 결과 원문은 변경하지 않는다. A 전용 불변 문서 개정에 원본 해시·이전 문서·작성자·시각을 남긴다. 메일은 명시적으로 선택한 저장본의 바이트를 고정한다. 이후 문서 수정으로 기존 초안·발송 이력이 바뀌지 않는다.

**Tech stack:** 기존 Python/PostgreSQL 호스트, A 전용 보존 파일, vanilla `planning.js`. 새 공통 코드·스키마·의존성 없음.

**Spec:** 사용자의 “RFQ 초안 … 수정하고 저장하는 흐름 추가” 요청과 기존 생산·자재 계획 영역 한정 조건.

## 결정

- 계산 원본을 덮어쓰면 계산 근거와 실제 전달 파일이 섞이므로 별도 수정본을 보존한다.
- 브라우저에서만 수정하면 재조회·실제 첨부가 달라질 수 있으므로 서버에 저장한 뒤 사용한다.
- RFQ 전체 문장을 수정할 수 있다. 문서 수정이 BOM/재고 계산 결과를 다시 계산한 것으로 표시하지 않는다. 수정본을 쓰는 메일 본문에서도 원래 품목 수를 수정 문서의 확정 품목 수로 주장하지 않는다.
- 현재 사용자가 받은 문서 ID를 저장 기준으로 삼고, 다른 사용자의 새 수정본이 있으면 덮어쓰지 않고 충돌을 알린다. 입력 내용은 화면에 유지한다.

## 구현

- [x] `materials/rfq_document.py`: 원본(v0)·수정본 읽기, UTF-8 256 KiB 이하 검증, 권한·원본 해시·업무 참조, 불변 개정·동시 저장·동일 요청 재시도.
- [x] `materials/workspace.py`: `rfq-document-get(source_kind, review_id)`, `rfq-document-save(source_kind, review_id, base_document_id, text, request_key)` 연결. 메일 액션에 선택적 `rfq_document_id`를 추가한다. 기존 호출에서 생략하면 원래 계산 RFQ를 선택해 호환성을 유지한다.
- [x] `materials/rfq_mail.py`: 저장본을 검증해 MIME 첨부·다운로드·그래프 증빙 참조에 고정. 타 RFQ 문서 지정은 거부한다.
- [x] `static/planning.js`: RFQ 내용 편집·저장·저장본 표시, 저장하지 않은 변경 표시, 다운로드/다음 단계에서 저장 요구, 계산 원문 조회. 메일 작성으로 이동할 때 선택한 저장본 ID를 전달한다.
- [x] `tests/materials/test_rfq_document.py` 및 메일/HTTP 테스트: 권한·크기·원본 무결성·동일 키·동시 충돌·다른 RFQ 참조 차단·수정 첨부·기존 발송 보존.
- [x] 실제 격리 PostgreSQL/Chrome: 편집→저장→새로고침→다운로드→메일 첨부 일치, 다음 개정 후 기존 기록 보존, 저장 응답 유실·동시 편집 충돌 확인.
- [x] 관련 및 전체 회귀·JS 구문·변경 범위를 확인하고 사용 중인 로컬 화면에 반영한다. 실제 외부 메일 발송은 하지 않는다.


## 검증 기록

- RFQ 문서 8개, 기존 메일 12개, A HTTP 4개를 합친 관련 **24개 테스트 통과**. 원본 불변, 동시 저장 충돌, 같은 키 재시도, 잘못된 문서 참조, 권한·크기·변조 및 선택한 수정본의 정확한 첨부를 확인했다.
- Chrome·격리 PostgreSQL에서 v1/v2 편집·저장·다운로드·새로고침, 저장 응답 유실 시 동일 버전 복구, 두 창의 충돌과 입력 보존을 확인했다. UTF-8 한글·이모지 포함 파일과 MIME 첨부가 바이트 단위로 같았다.
- RFQ v2 저장 이후에도 먼저 만든 v1 메일·그래프 증빙은 v1 해시를 유지했다. v2 첨부 정보 조회 실패 시 작성 진행이 차단되고 입력은 보존되며, 재시도 후 v2 파일로 고정되는 것도 확인했다.
- 별도 사용자 승인·그래프 반영 재조회, 모바일 390px 가로 넘침 없음, JavaScript 오류·외부 요청 0건. 시험 서버·스키마·보존 파일은 정리했다. 증거는 `/private/tmp/rfq-edit-e2e/`에 보관하며 사용자 계약·RFQ 문서는 수정하지 않았다.
- 기존 로컬 8062 서버를 같은 DB/schema/graph 설정으로 재시작했다. 사용 중인 RFQ 읽기와 선택한 RFQ의 메일 첨부 해시 일치를 읽기 전용으로 확인했고 업무 데이터 버전은 유지됐다.
- 독립 검토에서 지적한 첨부 조회 실패 시 구버전 선택 잔존 문제는 수정 후 브라우저로 재검증했다. 공통 코드·스키마·다른 업무 화면 변경은 없다.

- 최종 전체 unittest discovery: **1,763개 실행, 실패·오류 0, 기존 환경 조건 skip 11**, 787.920초. RFQ 편집·메일·증빙·HTTP 관련 **51개는 모두 실행·통과**했다. 전체 로그 `/private/tmp/rfq-edit-full-tests.log`. JS 구문·diff 공백·A 전용 변경 범위도 최종 확인했다.
