# 생산계획 웹 전체 흐름 시험 시나리오

> 공통 통합 이후 기준: `graph-0.2`에서 A/B 신규 타입을 공통 저장·조회·RDF·Neo4j에 연결했다. 아래 Task별 미등록·분리 기록은 당시 이력이다. 현재 계약과 실행 방법은 [TOOLS](TOOLS.md#ab-신규-업무-타입의-공통-저장조회), 완료 근거는 [PROJECT_STATUS](../PROJECT_STATUS.md)를 따른다. A 전용 업무 테이블의 승인 fact 자동 편입을 뜻하지 않는다.

현재 전체 업무 흐름은 [A 생산계획 흐름](MATERIALS_FLOW.md)을 기준으로 한다. 업무 단계·분기·저장 시점 변경 시 해당 문서도 함께 갱신한다.

준비일: 2026-10-30, Asia/Seoul. 사용자 요청에 따라 재고·협력사 관리 화면 개발은 미룬다.
기존 시험 화면과 가상 입력으로 업무 흐름을 확인한다. 이 문서는 기대 결과이며 웹 통과 기록이 아니다.
실제 OLIMEX 제품·BOM과 가상 고객·계약·재고·생산 조건을 구분한다.

## 공통 조건과 진행 순서

- 고객이 ESP32-POE L/WROOM 100대를 주문했다. 기존 이행·배정은 각각 0대다.
- 고객 도착 납기는 2026-11-10이며 날짜만 확인됐다. 임의의 마감 시각을 추가하지 않는다.
- 재고 기준은 2026-10-26 09:00 +09:00이다. 고정된 과거 시험 시각이며 현재 재고를 뜻하지 않는다.
- 확인된 BOM 소요량은 LAN8710 IC 1개/대, 2.2k 저항 8개/대, 10k 저항 11개/대다.
- 기본 생산 조건은 2026-10-26 10:00부터 자원 가용, 준비 60분, 시간당 20대, 손실·불량·재작업·중단 없음이다. 교대·휴일을 반영한 일정이 아니다.
- 입력 파일은 [web_scenarios.json](../data/materials/web_scenarios.json)이다. 기존 계약 원문은 보존했다. 사용자용 등록 화면 없이 시험 자료로 제공한다.

각 사례는 독립된 새 접수로 시작한다. 기존 웹의 `standard` 사례를 선택하고 JSON의 해당 사례에 있는 계약 원문, 재고, 생산 조건, 초기 수량을 사용한다. 새 사례 ID는 아직 화면 선택지에 연결되지 않았다.

1. Alice로 예제 불러오기 후 해당 시험값을 설정하고 원문을 접수한다.
2. 원문·추출 수량·L/WROOM 구성 후보·미확인을 확인한다.
3. Bob으로 전환해 현재 버전의 **주문 수량만** 확인한다. 전체 계약·생산·구매 승인이 아니다.
4. Alice로 돌아와 직접 호스트 계산을 실행한다.
5. 동일 입력으로 대역 Agent 경로를 실행해 수량·부족·시간이 직접 계산과 같은지 비교한다.
6. 생산 계획, 대체 검토안, 견적·납기 확인 요청 문서 3개를 열고 다운로드한다. 본문과 다운로드가 같은지 확인한다.
7. 같은 실행을 반복해 중복 문서·중복 재고 차감이 없는지 확인한다. 화면 입력 변경 후에는 이전 결과가 숨겨지고 재접수가 필요한지 확인한다.

대역 Agent는 실제 모델이 아니다. 실제 모델의 원문 이해·설명 품질은 별도 검증한다. 초기 수량의 일정은 화면이 명시한 **전체 자재가 준비됐다는 시험 가정**에 따른 값이며 실제 자재 확보 증거가 아니다.

## S01 — 예약 재고를 빼니 70대까지만 검토 가능

영업이 100대 주문의 생산 가능 여부를 묻는다. 창고의 IC 100개 중 30개는 다른 주문용으로 예약돼 있다.

| 부품 | 보유 | 예약 | 사용 가능 | 100대 소요 | 부족 |
|---|---:|---:|---:|---:|---:|
| LAN8710 IC | 100 | 30 | 70 | 100 | 30 |
| 2.2k 저항 | 600 | 40 | 560 | 800 | 240 |
| 10k 저항 | 1,200 | 100 | 1,100 | 1,100 | 0 |

초기 수량 70, 잔여 30을 사용한다. 확인된 항목 기준 상한은 70대다. 가상 소비 후 10k 저항은 330개 남아 잔여 30대의 소요 330개를 충족한다. IC 30개와 2.2k 저항 240개는 추가 확보가 필요하다.

초기 70대의 조건부 완료는 2026-10-26 14:30 +09:00이다. 잔여 완료·고객 도착 준수·총 구매 금액은 미정이어야 한다. 협력사 견적·납기 자료가 없으므로 협력사를 임의 추천하거나 단가·입고일을 만들면 실패다.

## S02 — 세 부품 재고가 충분해도 전량 가능을 확정하면 안 됨

창고에서 같은 부품의 추가 재고를 확인했다. IC 보유를 130개, 2.2k 저항 보유를 840개로 바꾸고 예약은 유지한다. 사용 가능은 각각 100개·800개이며 10k는 1,100개다. 초기 수량은 100이다.

세 부품의 부족은 모두 0, 확인 항목 기준 상한은 100이다. 전체 자재 준비 가정 아래 일정 계산값은 2026-10-26 16:00 +09:00이다.

하지만 나머지 71개 BOM 행의 재고와 일부 실장 조건은 미확인이다. `whole_bom_material_limit`는 null을 유지하고 전량 생산 확정·자재 확보 완료로 표시하면 실패다. 이 사례는 완전한 정상 생산 증명이 아니라 과도한 확정을 막는 시험이다.

## S03 — 핵심 부품이 모두 예약돼 착수 불가

IC 보유는 30개인데 30개 모두 다른 주문에 예약돼 있다. 다른 두 재고는 기본값을 유지한다. 초기 수량은 0이다.

IC 사용 가능 0, 확인 항목 기준 상한 0이다. 100대 전체를 잔여 물량으로 남기고 IC 100개·2.2k 저항 240개의 확보 필요를 표시한다. 예약된 IC를 사용하거나 선행 생산 시작·완료를 만들어서는 안 된다. 견적·납기 확인 요청으로 이어져야 한다.

## S04 — 자재 외에 생산 라인도 병목

S01과 같은 재고지만 생산 라인이 2026-11-11 10:00 +09:00에야 비어 있다. 초기 수량 70을 유지한다.

확인 항목 기준 상한 70과 부족 수량은 S01과 같다. 전체 자재 준비 가정이 있더라도 초기 70대 완료 계산은 2026-11-11 14:30 +09:00으로 이동해야 한다. 이는 고객 납기일 11월 10일보다 늦다. 이 생산안으로 납기를 지킬 수 있다고 표시하면 실패다. 잔여 일정·배송 기간·고객 합의는 별도로 미확인으로 남긴다.

## S05 — 재고 실사가 끝나지 않아 수량 미확인

LAN8710 재고의 `quantity_state`를 `unknown`, 보유 수량을 null로 두고 초기 수량은 0으로 둔다.

IC 가용 수량과 부족 수량은 null이며 0으로 바꾸면 실패다. 다른 확인 항목에서 계산되는 70대 상한은 참고값일 뿐 IC 확보나 착수 가능량이 아니다. 2.2k 부족 240개는 별도로 유지하고, IC 실사와 나머지 자재 확인을 요청한다. 전체 BOM 한도와 확정 생산 가능량은 미확인이다.

## S06 — 부족 부품의 다른 개정이 보여도 대체 확정 금지

추가 준비 대상이다. U2의 TPS2376D 재고가 0인 가상 상황에서 L1의 TPS2375D가 대안인지 검토한다. 실제 BOM·보존된 개정 변경 이력만 사용한다.

L1은 기존 구성 전환의 후보로 제시하되 U2 단독 교환을 승인된 대체로 취급하지 않는다. R50·R51·R6 등 관련 변경, 기술 검토와 고객의 개정 변경 허용을 확인해야 한다. 후보 재고를 L 구성의 가용 수량에 더하지 않는다. 근거가 부족하면 대체 검토안·확인 요청으로 끝나는 것이 정상이다.

현재 표준 웹의 세 부품 재고와 후보 처리에 U2 시험값을 연결하는 준비가 필요하다. S06용 웹 입력은 아직 제공하지 않으며 기존 `examples.materials_substitution`의 분리 사례를 참고한다.

## 현재 실행 상태와 다음 작업

2026-10-30의 읽기 점검에서 시스템 Python의 `psycopg`가 없음을 확인했다. 공통 `SCHEMA`에 Contract·ContractItem·DeliveryRound·ComponentStockSnapshot이 등록되지 않았으며, 기존 생산계획 시드 그래프를 `validate_graph`에 전달하면 `UNKNOWN_TYPE` 오류 5개로 거절된다. DB 연결·웹 시험은 수행하지 않았다.

먼저 분리된 A 스키마의 공통 검증·승인·저장 연결이 필요하다. 실행 환경은 PROJECT_STATUS의 별도 회귀 기록에 나온 캐시 Python·일회용 PostgreSQL 구성을 재사용할 수 있다. 단순 T-box 출력이나 검증 우회로 통과시키지 않는다. 웹 실행 후 사례별 상태·실제 수량·문서·오류·직접/Agent 비교를 별도 기록한다. 자료 준비와 산술 확인은 웹 통과로 집계하지 않는다.

준비 검증: 5개 입력 모두 `validate_planning_context`의 로컬 catalog 참조 검사를 통과했다. 기존 `available_stock`·`calculate_material_requirements`·`build_production_plan` 함수로 가용·부족·상한·선행/잔여 수량을 기대값과 대조했다. 기재한 완료 시각은 준비시간·처리율의 산술값을 대조했다. DB에 반영된 입력, 웹 일정 경로, 다운로드 결과, 실제 모델 답변은 아직 검증하지 않았다.

## 2026-10-30 계약 보관함: 접수와 해석 분리

A 전용 `python -m ontologics.materials.contract_library_web --port 51171`
는 환경의 PostgreSQL에 `a_contract_library` schema를 사용한다. `--schema`로 명시 가능하다.
기존 시험 화면과 달리 임시 schema/종료 시 삭제/fixture 적재를 하지 않는다.
`DATABASE_URL`은 공통 환경 로더로 읽으며 값·키를 로그에 출력하지 않는다.
로컬 실행은 기존 compose.yaml을 수정하지 않고 별도 project `ontologics-a-contracts`,
localhost 55433, named volume `ontologics-a-contracts_postgres_data`로 시작했다.
서버 프로세스 재시작과 관계없이 볼륨이 유지된다. 백업·운영 인증 구현을 뜻하지 않는다.

화면: 새 계약 등록 → PDF/TXT 선택 → 계약명/선택 거래처 입력 → 저장 → 목록 검색 →
원본 상세/다운로드. 계약명·거래처는 사람이 입력한 검색 메타데이터이지 모델 추출 사실이 아니다.
원본은 `pp_contract_originals.content` BYTEA로 저장하고 해시·바이트 길이를 매 조회 시 검사한다.
원본 저장만 수행하므로 파싱 불가능한 PDF도 보관할 수 있다(PDF 헤더 확인). PDF는 다운로드로
확인하며 TXT는 안전한 textContent 미리보기를 제공한다. 최대600KB, UTF-8 TXT/PDF만 받는다.
같은 바이트 재접수는 기존 계약 반환, 다른 원본은 별도 계약 ID를 만든다. 계약 간 개정 연결,
내용 수정, 삭제, 해석 요청은 이번 단계에서 제공하지 않는다. 상태는 보관됨/해석 전이다.

실제 HTTP POST와 PostgreSQL SELECT/INSERT를 사용한다. 공통 Host 신원·Service의
권한/트랜잭션/요청 재생/감사 기록·HTTP CSRF를 재사용한다. A 전용 저장 테이블은 원본
접수 기록이며 온톨로지 그래프 승인/등록으로 취급하지 않는다. Agent에게 SQL을 노출하지 않는다.
서비스 사용 흐름만 표시하되 로그인은 미연결인 localhost 전용임을 하단에 표시한다.

실제 PG 테스트3개: 재접속·검색·원본 일치, 중복·요청 키 충돌·읽기전용 권한·변조 검사,
HTTP CSRF·저장·검색·원본 반환. 브라우저로 가정 계약을 파일 업로드한 뒤 웹 서버를
실제 종료/재시작했고 검색·재조회·다운로드 바이트 일치를 확인했다. 모델 API 호출0회.
테스트 로그 `/tmp/ontologics-contract-library-results/web-preflight.log`,
화면 `/tmp/ontologics-contract-library.png`. 운영/전체 CQ 완료를 뜻하지 않는다.

### 후속: 등록 시 실제 해석과 원문 대조 확인

현재 보관함 실행에는 공통 OpenAI 설정과 명시적 비용 정책이 필요하다. 새 등록은 원본 저장 후
실제 API 해석을 수행한다. 기존 계약은 상세의 ‘저장된 계약 해석하기’로 최초 처리한다.
해석 결과는 별도 테이블에 영속 저장되며 조회에서는 모델을 재호출하지 않는다.
계약 상세에서 원문·값·인용 근거를 대조한 항목만 체크하고 ‘선택 항목의 해석 확인’을 누른다.
이는 추출 내용을 읽고 확인했다는 기록이며 계약 체결·생산/구매·대체 적용 승인이 아니다.
잘못된 항목은 체크하지 않고 재해석/원본 보완 대상으로 남긴다. 직접 값 수정 기능은 없다.
재해석은 유료 API를 새로 호출하고 새로운 결과를 만들므로 이전 항목 확인을 물려받지 않는다.
해석 실패/스캔 PDF는 원본을 보존하며 확인할 수 있는 결과로 위장하지 않는다.
source_only 출력은 원문 표현용이며 기존 생산계획 함수에 바로 전달하는 정규화된 입력이 아니다.
최신 실행 근거와 한계는 PROJECT_STATUS의 같은 날짜 후속 기록을 참조한다.

## 2026-10-31 전체 해석 검토

개별 체크박스 대신 제품·수량·납기·제약을 검토한다. 근거가 검증된 값은 `해석 유지`,

1. 부족 부품 검토·구매 요청에서 **특정 부품 대체 검토·수량 계산**을 연다. 원래 제품 구성은 고정된다.
2. 부족 부품 카드의 **대체품과 영향 검토 기록**을 열고 등록된 부품 중 검토 대상을 선택한다. 이 목록은 호환 추천 목록이 아니다.
3. 기존 회로·나머지 BOM 변경 없이 1:1 대체 및 부분 혼용 가능한지 기술·계약 검토 근거와 상태를 기록한다. 가용재고·회사/창고 범위·시각·보고 근거도 입력한다. DB에 사람의 검토 기록으로 저장되며 진위나 기술 적합성을 자동 인증하지 않는다. 미확인/불가 상태는 적용할 수 없다.
4. 검토한 대체 수량을 입력하고 **대체 수량 적용 후 부족량 계산**을 누른다. 원부품 40개 부족에 30개 대체 계획이면 원부품 잔여10개, 40개 대체 계획·대체재고30개이면 대체품 구매10개다. 동일 대체품의 재고는 한 번만 계산하고 기존 BOM에서의 수요도 합산한다. 순환/연쇄 대체와 한 원부품에 복수 후보 동시 적용은 현재 지원하지 않는다.
5. 전후 표를 확인하고 적용 사유와 전체 확인 후 저장하면, 해당 부품 계획의 남은 원부품/대체품 부족분으로 구매 요청을 작성한다. 모두0 수량이면 대체 없이 원안의 부족분으로 진행한다. 미확인 다른 부품은 그대로 남고 전체 생산 가능 여부는 확정하지 않는다.
6. 원본 BOM/제품 구성/재고는 수정하거나 차감하지 않는다. 검토 상태·재고 보고·계약·소요량이 바뀌면 기존 적용 결과와 구매 초안을 최신으로 사용할 수 없다. 부품 검토는 `pp_component_replacement_reviews`, 적용 결과는 기존 A 선택 이력 테이블의 `mode=component_replacement`로 저장한다.

### 보관 파일에서 확인한 영향 근거

- `data/sources/OLIMEX-Revision-changes-task05.txt` 34행: U2 TPS2376D→TPS2375D 변경 및 R50/R51 비실장 기록. 단순 직접 교환 승인 근거가 아니므로 이 조합의 직접 대체 확정을 차단한다.
- 같은 파일33행: R6 2.2k→10k, 충전 전류455mA→100mA. 별도 항목이며 U2 변경 때문에 발생했다고 단정하지 않는다.
- 같은 파일46–47행: TPS2376PW→TPS2376D 변경에 따른 TSSOP-8→SOIC-8 패키지와 배치 변경.
- 같은 파일59–60행: TPS2376PW 사용 시 UVLO 설정용 R50/R51 전압 분배기 추가.
- `ESP32-POE-user-manual.odt`에는 TPS2375PW 관련 입력 전압 제한과 상세 데이터시트 확인 안내가 있다. 다른 패키지인 TPS2375D에 그대로 일반화하지 않는다.
- 보관된 L/L1 BOM(PDF/ODS)과 개정 이력은 부품 사용 및 변경 근거다. 검토한 파일들에서 특정 대체품을 현 구성에 직접 사용해도 된다는 완전한 핀/전기/열/검증 결과표는 확인하지 못했다. 원본 파일을 변경하지 않았다.

### 호환 대체품 표시 제한

현재 화면은 최신 소요량에 연결된 직접 호환 확인 검토가 있는 부품만 영향 검토 기록을 열 수 있다. 선택 목록은 그 기록의 대체품으로 제한한다. 초기 호환 검토 등록은 이 화면에서 제공하지 않으며, 확인된 기록이 없으면 빈 상태 안내를 표시한다. 부품 이름이나 개정 변경 사례로 자동 호환 판정하지 않는다.


## 2026-10-31 가상 저항 대체 승인·재고 시나리오

사용자 요청에 따라 실제 로컬 PostgreSQL의 A 전용 저장소에 가상 운영 자료를 추가했다. 공통 그래프·BOM·T-box는 변경하지 않았다. `library_replacement_scenario.install(application, contract_id)`는 기존 120대 검토와 가상 회사 재고를 확인한 뒤 새 재고 스냅샷, 소요량 검토, A 전용 가상 부품 정의와 호환 검토 기록을 저장한다. 같은 입력의 재실행은 기존 기록을 반환한다.

- 대상: 2026-11 ESP32-POE 120대 신규등록 계약, Rev L WROOM.
- 원부품: 4.7R/R0402, 제품당 1개, 소요 120개, 가용 80개, 부족 40개.
- 대체품: DEMO-R4R7-0402, 가용 30개. 기술·계약 허용 조건은 명시적인 가상 승인이다. 실제 OLIMEX 승인으로 사용하지 않는다.
- 30개 대체 적용: 원부품 구매 필요 10개, 대체품 구매 필요 0개. 다른 세 부품의 부족 20/40/120개와 미확인 항목은 유지한다.
- 대체 미적용: ‘대체 없이 기존 부족량으로 구매 요청’으로 원부품 부족 40개를 유지한다. 별도 적용 사유를 요구하지 않는다.
- 대체 적용: 수량 입력 → 부족량 계산 → 전체 확인 → 결과 저장 후 구매 요청. 메모는 선택이다. 승인 근거·재고 범위 검증은 그대로 유지한다.
- 두 흐름 모두 서버 계산·저장된 선택안을 기준으로 구매 요청 초안을 DB에 저장한다. 실제 재고 예약/차감이나 외부 송부는 하지 않는다.

실제 DB 시드 반복 실행에서 동일 승인 ID 반환을 확인했고, 브라우저에서 40 → 10 및 대체품 구매 필요 0을 확인했다. 사용자가 직접 저장할 수 있도록 결과 미리보기에서 열어 두었다. 기존 구매 초안은 이력으로 보존되며 재고 기준 변경 후에는 최신 초안으로 취급하지 않는다.
