# 제조 제품정보 서비스 공통 기준

문서 정리일: 2026-10-25, Asia/Seoul. 이 문서는 v2 전달안과 진행표를 구현에 연결한 PRD·CQ·결정 기록이다. 원본은 `docs/reference/`에 보존한다. O01~O08의 확정일과 의미는 아래 결정 기록을 유지한다. 구현·검증 완료 여부와 다음 작업의 단일 기준은 `PROJECT_STATUS.md`다. 이 문서에 범위로 적었다는 이유만으로 구현 완료를 뜻하지 않는다.

## 서비스 목적과 전체 범위

공개 설계 기준을 활용하는 가상 전자보드 제조·조립 회사를 대상으로, 실제 사양서·기존 BOM을 읽어 등록할 제품·구성 정보를 만들고 개별 보드·부품 로트 이력과 연결한다. OLIMEX 내부 운영을 재현하는 서비스가 아니다.

| 업무 | 시작과 결과 | 사람과 공통 도구의 책임 |
| --- | --- | --- |
| S2 제품 등록 | 자료 접수 → 대상·개정·변형 식별 → 추출·정규화 → 기존 기준 연결과 차이 확인 → 검토·수정·승인 → 등록 | Product가 근거를 붙인 초안을 만들고 사람이 특정 버전을 검토한다. 공통 도구가 유효성·권한·승인 버전·중복을 검사하여 반영한다. |
| S1 문제 상황 분석 및 생산·사용 이력 보완 | 대상·목적·시간 조건 접수 → 구성·로트·시간 이력 조회 → 포함·조건상 제외·추가 확인 설명 → 보완 자료 접수 → 보완안 검토·승인 → 같은 조건 재조회 | Quality가 조건과 확인 한계를 설명하고 Product가 제출된 근거로 보완안을 만든다. 공통 도구가 승인된 이력을 반영하고 이전·이후 데이터 버전을 조회한다. |
| 원본과 이력 관리 | 원본 위치·버전·해시·근거 위치, 개별 보드·로트, 재고·입출고, 장착·제거, 승인 이력을 연결 | 파싱과 시드 적재, 운영 등록, 서비스 실행 기록을 구별한다. 출고만으로 장착을 추론하지 않는다. |
| 결과 공유 | 조회 조건·대상 집합·규칙 버전·데이터 버전·근거·남은 미확인을 함께 전달 | 포함을 고장 원인으로, 제외를 안전 판정으로 바꾸지 않는다. |

**BOM 생성은 원본에 있는 구성의 구조화**다. 새로운 부품 조합·호환성·옵션 조합을 설계해서 채우지 않는다. 사양 자료만으로 전체 구성을 확인할 수 없으면 확인된 속성만 초안에 담고 검증된 BOM 연결이나 추가 자료를 요청한다. BOM만 있는 경우 부품 상세 사양은 미확인으로 남길 수 있다. 자료 형식에 따라 일반 파서를 우선 사용하며 OCR·LLM 호출을 강제하지 않는다.

S2의 완료는 승인된 제품·구성 버전과 원본을 다시 확인하고 S1에서 활용할 수 있는 상태다. S1의 완료는 근거 있는 조사, 누락·충돌 설명, 이력 보완과 동일 조건 재조회다. 초기 기준 데이터의 직접 시드 적재는 개발 편의 기능이며 S2 승인 등록 경로의 완료 증거가 아니다.

### 1차 목표 — PostgreSQL 기반 S1·S2 사용자 서비스 완성

현재 PostgreSQL JSONB 그래프·pgvector 검색·Python 검증과 공통 승인·조회 도구를 유지해 전체 사용자 업무를 연결한다. 동료는 이 문서의 S1/S2·CQ·O01~O08과 [공통 도구 계약](TOOLS.md)을 같은 기준으로 사용한다. 제품·구성 정의의 등록과, 해당 구성에 연결하는 개별 보드·로트·장착/제거 기록의 등록은 구분하되 같은 검증·사람 승인 경로를 사용한다.

| 업무 단위 | 완료를 판단할 결과 | 구별할 검증 범위 |
| --- | --- | --- |
| 공통 기반과 Agent 개발 시작 | 대표 자료와 CQ, 조회·검증·초안·승인 도구의 실제 호출, 역할별 실행 예제와 근거·오류 확인 방법 | 개발 시드·사람 역할 대역·최소 실모델 예제의 성공을 전체 사용자 서비스 완료로 계산하지 않는다. |
| S2 사용자 흐름 통합 | 실제 OLIMEX L/L1 WROOM 원본을 접수해 제품·개정·기존 구성에 연결하고 사용자가 추출값·원본 근거·차이·미확인을 확인한다. 작성자와 다른 인증된 검토자가 보완 요청/반려/승인하고, 승인된 정확한 버전만 반영해 이후 조회와 S1에서 재사용한다. | 이미 파싱한 두 행의 모델 초안 작성과 실제 원본 접수부터 등록까지의 통합을 구별한다. 근거 없는 신규 BOM·부품 조합을 생성하지 않는다. |
| S1 사용자 흐름 통합 | 사용자가 개별 보드·로트·A/B 조건으로 포함·조건상 제외·추가 확인 필요와 근거·충돌을 조회한다. 제출된 보완 근거를 검증·사람 승인 후 반영하고, 동일한 조사 조건에서 데이터 버전만 달리해 전후 결과와 남은 미확인을 확인한다. | 아래 시간 계약의 B 장착 구간 겹침·[start,end)를 유지한다. 사전 준비된 버전의 설명과 실제 보완 흐름을 구별하며, 미확인 장착·고장 원인·안전성을 임의로 확정하지 않는다. |

Supervisor·Product·Knowledge·Quality의 책임을 실제 LLM·공통 도구에 연결하고, 사용자 화면 또는 동등한 업무 인터페이스에서 등록·조사·검토·승인·보완·결과 확인이 가능해야 한다. 검색 챗봇은 조회 조건·근거·미확인 사항·데이터 버전을 제공한다. 역할별 별도 모델·서버의 개수는 완료 기준이 아니다.

실제 인증 신원으로 권한·자기 승인 금지·실패·재시도·중복 방지를 검증한다. 검토 대기·보완 요청·실패 상태에서는 현재 대상과 버전, 필요한 자료 또는 다음 행동을 전달하며, 재시도·중복 방지·승인 확인은 공통 실행 계층이 담당한다. 개발용 시드·임시 사용자 대역·최소 실모델 호출 성공만으로 전체 사용자 서비스 완료를 선언하지 않는다.

### 별도 통합 목표 A — RDF/OWL·SHACL·SPARQL + Neo4j

제조 제품·개정·부품·로트·이력의 의미와 관계를 RDF/OWL로 표현하고 SHACL 구조·관계 검증과 SPARQL 조회를 연결한다. 승인된 지식을 Neo4j의 서비스 조회용 그래프로 동기화하며 공통 식별자·원본 근거·실제/가상 구분·승인 버전을 보존한다.

같은 데이터·규칙 버전과 질의 조건에서 기존 PostgreSQL 기반 CQ와 RDF/Neo4j 조회의 의미·포함/제외/미확인 판정이 일치해야 한다. 동기화 실패·재시도에서도 중복이나 누락을 검증하고, 불완전한 적재나 서로 다른 버전의 결과를 정상 조회로 공개하지 않는다. 기존 T-box·JSON-LD 생성만으로 이 목표를 완료 처리하지 않는다. 상세 매핑·동기화·공개 조건은 [TOOLS의 후속 설계](TOOLS.md#후속-통합배포-설계-미구현)를 따른다.

### 별도 배포 목표 B — AWS

CPU EC2, RDS PostgreSQL·pgvector, S3, 외부 LLM·임베딩 API를 목표 구성으로 한다. 외부 모델 API 사용을 전제로 자체 GPU 서버는 기본 필수 구성에서 제외한다. RDF/Neo4j를 병용하면 각 그래프 저장소의 배포·접근·백업·동기화 책임을 별도로 정의한다.

실제 AWS 환경에서 S1·S2 전체 사용자 업무, 인증·권한, 저장 영속성, 모델 API 호출, 로그와 장애·백업 복구를 검증해야 배포 완료다. 로컬 Compose나 CI 성공은 AWS 배포 완료 근거가 아니다.

통합 목표 A와 배포 목표 B는 현재 1차 서비스의 선행 조건이 아니며, 서로 독립적으로 진행·검증할 수 있다. AWS는 PostgreSQL 기반 서비스만으로 배포 검증할 수 있고 RDF/Neo4j 통합은 AWS 없이 검증할 수 있다. 어느 한쪽의 완료를 다른 쪽의 선행 조건으로 만들지 않는다. 여기서 목표 A/B는 시간 조회 A/B와 구분한다.

### 현재 필수 범위와 후속 회사 업무 확장

회사 업무 전체의 온톨로지를 한 번에 구성할 필요는 없다. 아래 항목과 Change·Supplier·Report의 독립 Agent 추가는 현재 목표 범위에서 제외한 **후속 확장 후보**다. 이번 통합·배포 목표의 선행 조건이 아니며 구현 일정·자료 정책까지 확정한 것은 아니다.

| 영역 | 현재 유지할 필수 범위 | 후속 검토 후보 |
| --- | --- | --- |
| 회사 규칙 | 자기 승인 금지, 변경 묶음 승인, 정확한 승인 버전 반영, A/B 시간 기준 | 사규 문서의 등록·시행일·개정·적용 대상 관리 |
| 대응 매뉴얼 | 현재 S1/S2의 처리·보완·승인 흐름과 필요한 근거 안내 | 매뉴얼 수집·검색, 상황별 절차 추천, 사용한 절차 버전 추적 |
| 조치 관리 | 개별 보드의 장착·제거 기록, 이력 확인 범위, 제출된 보완 근거 | 담당자 업무함·작업 지시·점검표·조치 완료 및 후속 관리 |

‘조치 관리 확장을 미룬다’는 이유로 S1의 장착·제거·보완을 제외하지 않는다. 확장 시에는 추가 CQ·원본·허용 데이터·권한과 승인/실제 수행 완료의 차이를 검토한다. 가상 회사 규정·검사 결과·작업 완료 기록을 현재 허용 데이터에 자동으로 추가하거나 OLIMEX의 실제 운영 사실처럼 취급하지 않는다.

## 공통 의미와 데이터 경계

| 개념 | 공통 의미와 식별 규칙 |
| --- | --- |
| 제품 모델 | 제조사와 모델로 식별하는 제품 정의. 개별 실물이 아니다. |
| 제품 개정 | 같은 모델의 설계 개정. 변형·옵션과 구별한다. |
| 구성 | 특정 개정과 원본에서 확인한 변형의 BOM 기준. 이름만 비슷하다고 합치지 않는다. |
| BOM 항목 | 구성 → 항목 → 부품 모델의 관계, 수량·단위·위치·실장 조건·원본 행을 보존한다. `NA`나 실장 미확인 항목을 일반 소요량으로 확정하지 않는다. |
| 부품 모델 | 확인된 원문 표기·패키지와 출처 범위를 보존한다. 검증하지 않은 제조사 품번·대체 가능성을 추론하지 않는다. |
| 개별 제품 | 보드 한 대. 가상 식별자와 적용 구성을 연결하며 모델 정의와 별도로 등록한다. |
| 부품 로트 | 회사·공급처·부품 모델·로트 식별자를 함께 사용한다. `L07` 문자열만으로 서로 다른 부품이나 공급처의 로트를 합치지 않는다. |
| 장착·제거 | 개별 보드, 로트, 장착 위치와 사건 시점을 근거에 연결한다. 제거 사실만 있으면 그 사실만 보완하며 존재하지 않는 새 장착을 만들지 않는다. |
| 이력 확인 범위 | 특정 보드·기간에서 이력이 완전하다는 별도 근거. 검색 결과 없음과 같지 않다. |
| 근거 | 원본 문서의 버전·해시·위치 및 주장이 나온 행·표·페이지. 실제·가상 구분을 유지한다. |

실제 자료는 OLIMEX 공개 사양·설계·BOM이다. 가상 기록은 회사의 재고·입출고, 개별 제품·부품 로트 식별, 장착·제거와 그 이력의 확인 범위에 한정한다. 가상 검사 결과·고장 원인·불량률·가동 시간은 허용 범위에 추가하지 않는다. 사용자 조사 요청과 확인된 사실도 구분한다.

C 클레임 대응 범위에 한해 생산라인과 보드별 생산 기록, 고객 클레임, 품질 사건·영향 범위, 생산 중단·출고 보류 요청서를 가상 기록으로 허용한다. 클레임 증상은 고객 신고 원문이며 확인된 불량이나 원인이 아니다. 시험 결과·조치 판정·재생산 요건은 별도 논의 후 정한다. 세부 조건은 [claim_response 데이터 정책](claim_response/DATA_POLICY.md)을 따른다.

그래프의 개체·관계는 T-box와 공통 검증 코드에서 관리한다. A-box는 실제 출처를 가진 제품·구성과 가상임을 표시한 운영 사례다. 필수값·참조·자료 구분은 검증 계층, 식별·정정은 업무 규칙, 시간 판정은 공통 조회, 승인·반영·재시도는 실행 계층의 책임이다. 별도 그래프 서버나 MCP는 1차 서비스의 필수 조건이 아니다.

## 시간 조회 계약

사용자가 2026-10-22에 채택한 기준: A는 지정 시점의 장착 상태, B는 **장착 구간과 조사 기간의 겹침**이며 시작 포함·끝 제외다. B는 실제 가동 시간을 뜻하지 않는다.

- 확인된 장착 구간 `[장착, 제거)`에서 A는 `장착 ≤ at < 제거`, B는 `장착 < end` 그리고 `제거 > start`다. 시작 전에 장착했어도 기간에 겹치면 B에 포함된다.
- 입력은 시간대가 명시된 시각이다. 날짜만 있는 자료에 임의의 시각을 넣어 확정하지 않는다. 사건 시점·문서 작성 시점·수집 시점·승인 시점·Git 커밋 시점은 별개다.
- 조회할 개별 제품 집합을 명시한다. 기준 제품을 제외할 경우 제외 ID도 조건에 남긴다. 하나의 제품 확인과 여러 제품 탐색은 같은 규칙을 사용한다.
- 제거 미기록은 무기한 장착을 뜻하지 않는다. 확실한 장착 순간·유한한 장착 확인 범위와 그 이후 미확인을 구별한다.
- 일치 구간이 없더라도 요청 범위를 덮는 완전한 이력 근거가 없으면 `needs_confirmation`이다. `excluded`는 조건 미충족을 충분한 이력으로 확인한 경우다.
- 여러 장착 기록을 함께 평가한다. 확인된 일치 구간과 다른 미확인 구간을 따로 제시하며, 판정에 영향을 주는 충돌은 숨기지 않는다.
- 보완 전후 비교는 대상 집합·로트·시점 또는 기간·시간 규칙을 고정하고 데이터 버전만 달리한다. 승인 전 결과는 예상 결과이며 승인된 사실과 구별한다.

대표 가상 사례는 U104의 L07 장착(2026-08-20), 초기 제거 시점·이력 범위 미확인, 이후 제거(2026-09-12 09:00+09:00)와 재장착 없음의 확인 범위 보완이다. A=`2026-09-20T10:00:00+09:00`, B=`[2026-09-01T00:00:00+09:00, 2026-09-21T00:00:00+09:00)`에서 충분한 보완 후 A는 조건상 제외, B는 포함이다. 보완 근거가 부족한 별도 제품은 계속 추가 확인으로 남아야 한다.

### 설계 이력과 운영 이력을 연결할 때

Git의 BOM·설계 자료는 **제품 정의·개정의 근거**다. 오탈자 수정이나 자료 보완도 있으므로 파일·커밋 변경만으로 설계 개정이나 이미 생산된 보드의 실제 부품 교체를 확정하지 않는다. BOM의 부품 모델만으로 실제 사용한 부품 로트를 알 수도 없다. 과거 설계 사용처는 CQ03/CQ10의 원본·구성 관계로, 특정 로트의 장착 이력은 CQ05/CQ06의 개별 보드·로트·사건 근거로 확인한다.

설명용 복합 요청은 “이 부품이 포함된 과거 설계를 확인하고, 그 부품의 특정 로트가 조사 기간에 장착됐던 우리 회사 보드도 찾아줘”다. 이때 확인된 부품 ID·구성 범위와 로트·보드 집합·A/B 조건을 먼저 연결하고, 설계 포함 여부와 실제 장착 판정을 따로 답한다. 현재 CQ10의 원본 범위 ID 제한을 넘어서 이름이 같은 부품을 자동 병합하지 않는다. 이 예시는 역할 통합의 개발 방향이며 복합 자연어 질의가 구현됐다는 뜻은 아니다.

‘현재 확보해 승인·반영한 근거로 특정 과거 개정을 설명’하는 질문과 ‘지정한 당시 Git 커밋의 자료만으로 설명’하는 질문은 다르다. 해당 과거 개정에 대한 추가 근거와 최신 개정의 BOM도 구별한다. 후자의 BOM을 근거 없이 과거 개정에 소급 적용하지 않는다. 현재는 원본의 고정 커밋·위치와 승인된 데이터 버전을 명시하는 계약이며, 임의 Git 시점 조회나 두 질문 사이의 신규 기본 모드를 이 문서 보완으로 채택하지 않는다. Git 이력 조회를 확장할 때 적용 근거 기준과 CQ를 함께 결정한다.

## CQ와 원본·검증 연결

아래 실제 자료 기준은 공식 저장소 커밋 `deb38a377d50eadb04ddc7118a17a5ae58b1ee53`의 `ESP32-PoE_Rev_L-BOM-WROOM.ods` 및 `ESP32-PoE_Rev_L1-BOM-WROOM.ods`와 대응 PDF다. ## 검토·반영과 실패 처리

사용자가 채택한 승인 기준은 **작성자와 검토·승인자 분리, 자기 승인 금지, 서로 의존하는 변경의 묶음 승인·원자적 반영**이다. 독립적으로 근거가 있는 제거 사실은 독립 초안으로 제출할 수 있다. 변경마다 별도 업무 단계를 늘리지 않는다.

초안은 작성 → 검증 → 사람 검토 → 수정·보완 요청 또는 승인 → 승인 버전 반영 → 결과 확인 순서로 처리한다. 검토자는 대상·원문 근거·변경점·검증 결과·미확인·초안 버전을 확인한다. 수정은 새 초안 버전을 만들고 다시 검증·승인하며, 이전 버전의 승인으로 바뀐 내용을 반영하지 않는다. 공통 기반이 바뀌어 초안의 전제가 낡으면 재검토한다.

Agent는 조회·해석·초안 작성 권한만 가진다. 승인 권한·사용자 신원은 신뢰할 수 있는 애플리케이션 경로에서 주입하며 도구 입력이나 LLM의 “승인됨” 주장으로 만들지 않는다. 개발 예제의 사람 역할 대역은 실제 사용자 인증·운영 승인과 구별한다. 로컬 프로세스나 DB 파일의 소유자까지 격리하는 보안 경계로 설명하지 않는다.

실행 상태와 초안 승인 상태를 별도로 기록한다. 각 호출은 성공·실패와 오류 의미를 남기고, 변경 호출은 재시도 시 중복 반영을 방지한다. 검증 실패·권한 부족·승인 버전 불일치·기준 데이터 변경은 사용자나 Agent가 원인을 구분할 수 있어야 한다. 승인과 실제 반영 사이에도 유효성·버전 검사를 유지한다. 여러 변경 중 하나가 실패하면 묶음 전체를 반영하지 않는다.

조회·근거 열람에는 등록 승인을 요구하지 않는다. 공유 결과에는 적용 버전, 조건, 근거, 미확인·충돌을 포함한다. 보완 사례를 저장하는 것과 범용 규칙·모델을 자동 변경하는 것은 별개다.

O01~O08은 사용자 답변으로 모두 확정했다. 미확인 원문 표기와 개정 간 부품 동일성은 자료 검증 과제로 남으며 사용자 승인만으로 사실이 검증되지는 않는다. CQ09의 채택, 실제 운영 인증 체계 통합은 이후 과제다. 확정한 기준을 다시 묻지 않으며, 이후 제품 관리 단위·시간 의미·허용 데이터·승인 권한·공통 계약의 호환성을 바꾸는 결정이 생기면 추천안·이유·영향으로 묶어 제시한다.

기획 대화의 모든 설명·비교안·복사용 요청문을 확정 요구로 간주하지 않는다. 이 문서의 확정 결정과 이후 사용자의 명시적 변경을 기준으로 대조한다. 과거 Rev M/WROVER 자료 배정안은 현재 O05의 L/L1 WROOM 기준을 바꾸지 않으며, 과거 요청문 예시의 가상 검사·사고 기록도 현행 허용 데이터에 포함하지 않는다. 대화에 나온 계획은 현재 요구, 구현 잔여, 후속 검토 후보로 구분해 보존한다.

2026-10-23 사용자 요청으로 영속 저장을 PostgreSQL + pgvector로 전환한다(v0.2.0). 이는 저장 구현 변경이며 O01~O08·S1/S2·A/B·승인 의미는 유지한다. pgvector의 근거 유사도는 후보 탐색이며 부품 동일성·장착 판정·승인 사실의 대체 근거가 아니다. SQLite 파일 자동 이전과 임베딩 API/RAG 품질 검증은 이번 전환 완료 범위에 포함하지 않는다.

2026-10-24 사용자 확정으로 개발 목표를 위 1차 서비스, 별도 통합 목표 A, 별도 배포 목표 B로 구분한다. PostgreSQL 전용 기준은 현재 구현과 1차 서비스에 적용하며, RDF/OWL·SHACL·SPARQL·Neo4j와 AWS는 별도 목표로 관리한다. 기존 O01~O08·CQ 채택 상태·공통 API·승인 권한은 변경하지 않는다. 목표 채택과 실제 구현·검증 완료는 구별하며, 기술 배치와 후속 설계는 [TOOLS](TOOLS.md#후속-통합배포-설계-미구현), 실제 완료 근거는 PROJECT_STATUS에서 관리한다. 자연어 검색을 연결할 때도 근거 후보와 확정 조회 결과를 구별하고 미확인 처리·검색 평가 사례를 마련한다.

## 동료 Agent 개발과 통합 접점

| 담당 | 개발 범위 | 공통 기준을 사용하는 방식 |
| --- | --- | --- |
| Product | 사양·BOM·운영 기록의 추출, 정규화 후보, 연결 설명, 등록·보완 대화 | 원본·근거를 붙인 구조화 초안을 제출하고 공통 검증의 미확인을 사용자에게 설명한다. |
| Knowledge | 제품·구성·부품·근거 탐색과 관계 조회 | 공통 ID·그래프 조회를 재사용하고 적용 데이터 버전을 전달한다. |
| Quality | 조사 조건 해석, A/B 선택, 포함·제외·미확인 설명과 보완 요청 | 공통 시간 계산을 호출하고 고장 원인·안전·가동 상태를 추론하지 않는다. |
| Supervisor | 요청 분류, 필요한 도구·역할 연결, 진행·결과 종합 | 실행 계층이 제공하는 상태를 사용하며 승인·트랜잭션을 대체하지 않는다. |

기획 대화의 **Coordinator(업무 접수·조율)**는 이 저장소의 **Supervisor**와 같은 책임을 가리킨다. 명칭 대응이며 별도 Agent 추가나 도구·권한 변경이 아니다. 사용자는 업무를 요청하고 서비스가 필요한 역할을 연결한다. Knowledge의 정보 탐색 책임과 API 진입점의 인증·요청 전달 책임, 공통 조회 도구의 계산 책임을 구분한다.

이는 책임 구분이며 별도 모델·서버·Agent 수를 고정한 것이 아니다. 동료는 역할 지시사항·추출·해석·대화·설명과 담당 검증에 집중한다. 품목 의미·시간 계산·승인·확정 쓰기를 Agent 내부에서 다시 구현하지 않는다.

사용자 검토 화면 또는 API는 초안 ID·버전, 변경 대상과 전후 값, 근거 위치, 검증 결과, 승인/보완 요청/거절을 다룬다. 조사 화면 또는 API는 대상 집합·A/B 조건, 제품별 판정·이유, 근거, 데이터·규칙 버전, 보완 후 비교를 다룬다. 공통 함수 호출 예제로 이 접점을 먼저 검증하고 실제 UI·인증·LLM 통합의 완료 여부는 별도로 기록한다.

`AGENTS.md`는 개발자가 저장소에서 코드를 변경하는 규칙이다. 개발용 Skill은 반복이 확인된 작업 절차만 묶는다. 서비스 Agent 실행 지침과 권한은 런타임 계약이며 개발 문서·Skill 자체가 승인 권한을 부여하지 않는다. 필요가 검증되지 않은 추가 Agent, OpenRouter, 자동 모델 라우팅, 대규모 실행 플랫폼, 별도 MCP 서버를 선행 요건으로 만들지 않는다.
