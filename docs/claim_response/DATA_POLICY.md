# claim_response 데이터 정책 추가

> 기능: C 클레임 대응 (`claim_response`)
> 기준 문서: [서비스 명세 - 공통 의미와 데이터 경계](../SERVICE_SPEC.md), [C 온톨로지 스키마 확장 전달안](references/C_온톨로지_스키마_확장_전달안.md) 10장 "자료 정책과 구현 반영 요청"
> 상태: 팀 승인 완료. 1차(PR #6, 병합됨) 6종과 2차(PR #7) 3종을 허용한다. 2차는 2026-10-29 팀 회의(테스트팀 담당)와 A 회신(C→A 한 방향 요청)을 따른다.

## 1. 요약

- 기존 허용 범위는 그대로 둔다. C 클레임 대응에 필요한 가상 기록만 **추가로** 허용한다.
- PR #6에서 허용: 생산라인과 보드별 생산 기록, 고객 클레임, 그리고 이를 잇는 품질 사건·영향 범위·중단 요청서 (타입 6개).
- PR #7에서 허용: 테스트팀에 보내는 시험 의뢰, 테스트팀이 돌려준 보드별 시험 결과·조치 판정, C가 계산한 재생산 필요량 (타입 3개).
- 시험 방법·실행·판정은 **테스트팀**이 정한다. C는 의뢰서를 만들고, 돌려받은 판정을 그대로 옮겨 세고, 재생산 필요량만 계산한다.
- 모두 시연용 가상 기록이며 실제 OLIMEX 제품의 결함이나 실제 공장 조치로 설명하지 않는다.

## 2. 기존 정책 원문

`SERVICE_SPEC.md` "공통 의미와 데이터 경계":

> 실제 자료는 OLIMEX 공개 사양·설계·BOM이다. 가상 기록은 회사의 재고·입출고, 개별 제품·부품 로트 식별, 장착·제거와 그 이력의 확인 범위에 한정한다. 가상 검사 결과·고장 원인·불량률·가동 시간은 허용 범위에 추가하지 않는다. 사용자 조사 요청과 확인된 사실도 구분한다.

C 기능은 이 범위 밖의 기록(클레임, 생산라인과 생산 기록, 이후 시험 결과·조치 판정)이 필요해서 전달안 10장으로 정책 보완을 요청했고 팀 승인을 받았다. 근거 자료는 [references](references/README.md)에 원문으로 보관한다.

## 4. 지켜야 할 조건

### 4-1. 1차 (PR #6)

1. 위 1차 타입은 모두 `origin=synthetic`이다. 공통 모델의 `SYNTHETIC`에 포함되어 있어 `real`로 넣으면 `DEMO_OPERATIONS_ONLY`로 거부된다.
2. 모든 노드는 가상 `SourceDocument`·`Evidence` 근거를 가진다. 기존 시연 원본은 `data/claim_response/`에 보관한다. 공통 화면에서 접수한 원문·입력은 기존 공통 접수 경로인 Git 제외 `data/receipts/business-<sha256>.json`에 무변경 보존하고 새 SourceDocument/Evidence를 부여한다. 승인 전 초안 원본과 승인된 사실을 구분한다.
3. 고객사·클레임 번호·납품 문서 번호는 가정 값이며 `DEMO` 표시를 넣는다(예: `DO-DEMO-C-001`). 실제 회사·고객 이름을 쓰지 않는다.
4. `reported_symptom`은 **고객 신고 원문**이다. 확인된 고장이나 고장 원인으로 표현하지 않는다.
5. `QualityScope`의 보드 목록은 **조사·보류 대상**이다. 불량 보드 목록이 아니다.
6. 중단 요청서의 생산라인은 그 요청서가 가리키는 영향 범위의 생산라인과 같아야 한다(`LINE_MISMATCH`). 다른 라인에 대한 요청이 필요하면 자동으로 허용하지 않고, 별도 의미·근거 계약을 먼저 정한다.
7. `UnitProductionRecord.production_work_id`는 **미지원 접점**이다. 공통 `ProductionWork` 타입은 있지만 C 보드가 어느 생산 작업에 속하는지 B와 합의하지 않았으므로(B·C 통합 결정 I02) 값을 넣으면 `PRODUCTION_WORK_UNSUPPORTED`로 거부한다.
8. 같은 라인이나 같은 부품 로트라는 공통점으로 고장 원인을 자동 확정하지 않는다.
9. 실제 OLIMEX 자료(사양·설계·BOM)에 C 기록을 섞지 않는다. 연결은 이미 가상인 `ProductUnit`을 통해서만 한다.

### 4-2. 2차 (PR #7)

1. 2차 3종도 모두 `origin=synthetic`이며 가상 `Evidence` 근거가 필요하다(1차 1·2번과 같음).
2. **시험 결과와 조치 판정은 테스트팀이 정해서 돌려준 값**이다. C는 판정을 만들거나 바꾸지 않는다. 시험 결과는 가상 관측이며 실제 고장 원인·불량률이 아니다.
3. 결과는 **의뢰한 보드에만** 받는다(`UNIT_NOT_REQUESTED`). 의뢰와 결과의 사건이 같아야 하고(`CASE_MISMATCH`), 의뢰·보드당 결과는 1개다(`DUPLICATE_IDENTITY`). 시험하지 않은 보드는 결과 행이 없고 미검사로 센다.
4. `customer_replacement`(고객 교체)는 사건의 신고 보드에만, `stock_replacement`(보관 대체)는 신고 보드가 아닌 보드에만 쓴다(`DISPOSITION_TARGET_MISMATCH`).
5. **계산 기준.** 제출된 숫자끼리만 비교하지 않고 같은 그래프의 의뢰·결과와 대조한다(`claim_response/schema.py`의 `calculation_basis()`).
   - 계산 대상 보드: 같은 사건의 모든 `TestRequest.unit_ids` 합집합 중 **요건의 구성과 같은 보드만**(`ProductUnit.configuration_id` 기준). 두 의뢰에 같은 보드가 있어도 한 대다. 해당 구성의 대상 보드가 없으면 거부(`NO_TEST_REQUEST`).
   - 적용 결과: 같은 사건에서 대상 보드에 대한 모든 `QualityTestResult`(어느 의뢰의 결과든).
   - 보드별 판정: 결과 없음 → 미검사(미결). 같은 결과가 여러 개 → 그 판정 한 번. **서로 다른 결과 → 충돌(미결)이며 최신 결과를 고르지 않는다**(경고 `RESULT_CONFLICT`, 사람 확인).
   - 고객 교체·보관 대체 수는 이 판정에서 센 보드 수와 같아야 하고(`QUANTITY_MISMATCH`), 미결 수는 미검사 + `unresolved` 판정 + 충돌 보드 수와 같아야 한다(`UNRESOLVED_MISMATCH`).
   - **구성이 섞인 사건**(L과 L1이 한 사건에 있는 경우)은 구성별로 따로 센다. 구성마다 `ReproductionRequirement`를 하나씩 만들며(식별자가 사건+구성), 다른 구성의 교체 수요나 미결 보드가 섞이지 않는다.
   - `test_result_ids`에 같은 보드의 결과를 두 번 넣으면 거부한다(`DUPLICATE_BOARD_RESULT`). 충돌한 결과를 넣어도 거부한다(`RESULT_CONFLICT`).
6. 재생산 필요량은 `max(0, 고객 교체 + 보관 대체 − 사용할 대체 재고)`이며 0 이상의 정수다(`QUANTITY_MISMATCH`, `INVALID_QUANTITY`).
7. 미결이 0이면 `confirmed`, 1 이상이면 `lower_bound`(최소 수량)다(`ASSESSMENT_STATE_MISMATCH`). **확인된 교체 수요 없이 미결만 있으면 미정이며 노드를 만들지 않는다**(저장하면 `UNDETERMINED_NOT_STORED`). 미결·미검사를 확정 0대로 저장하지 않는다.
8. 대체 재고 보드(`replacement_unit_ids`)는 같은 구성의 `ProductUnit`이어야 하고 개수가 사용할 대체 재고 수량과 같아야 한다(`CONFIGURATION_MISMATCH`, `QUANTITY_MISMATCH`). **같은 사건의 시험 대상 보드 및 같은 그래프의 다른 사건에서 고객 교체·보관 대체로 기록된 보드는 대체 재고가 될 수 없다**(`REPLACEMENT_TARGET_CONFLICT`). 다른 사건의 시험 의뢰·미검사만으로 일괄 제외하지 않으며, 시험 결과를 임의로 해제·수리 완료로 바꾸지 않는다. 다른 주문 배정 여부는 사람이 확인한다(재고 소속은 B·C I04 미합의).
9. **C → A는 한 방향 요청**이다(A 회신). A의 계산 결과·접수 응답을 받는 타입은 없다. A 요청서의 "이번 재생산 요청량"(같은 건의 기존 요청분 제외), 고객 희망 기한, 관련 계약은 **요청서 문서에만** 쓰고 그래프 필드로 두지 않는다. 그래프에는 문서 참조(`document_ref`)만 남는다.

### 4-3. 공통 화면의 접수·사건 연결

`claim_response/workspace.py`의 `intake`는 가상 고객·클레임 번호·신고 원문·신고 수량·일련번호를 받아 공통 초안을 만든다. 고객/클레임/선택 납품 번호는 DEMO·가상·가정·시연 표시를 확인하고 실제 고객 자료를 이 시연 경로에 넣지 않는다. 사용자는 원문·작성 시각·가상 자료 범위를 제출하며 작성자 신원은 호스트가 연결한다.

별도 사람이 정확한 접수 초안을 승인하면 `needs_review` 상태의 신고 기록이 확정된다. 이는 신고가 접수됐다는 뜻이며 신고 내용이 사실로 검증됐다는 뜻이 아니다. 이후 `confirm_case`에서 신고 일련번호와 직접 대조한 기존 ProductUnit을 선택하면 접수 `confirmed` 변경과 QualityCase를 묶은 새 초안을 만든다. 같은 공통 검증·자기 승인 금지·정확 버전 승인 후 함께 반영한다. 같은 승인 사건을 중복 생성하거나 신고와 무관한 보드를 연결하지 않는다.

현재 공통 화면은 신고 접수·사건 연결까지다. 시험팀 결과 업로드, 재생산 요청 전체 흐름, C Agent 자동 판단·A/B 자동 인계는 이 화면 통합에 포함하지 않는다. 이는 위 1·2차 타입의 허용 범위를 축소하는 것이 아니라 현재 UI 연결 상태의 구분이다. 호출·근거 보존 계약은 [TOOLS의 공통 업무 화면](../TOOLS.md#공통-업무-화면-abc)을 따른다.

## 5. 여전히 허용하지 않는 것

- 고장 원인 확정, 불량률, 가동 시간
- C가 직접 정한 시험 결과·조치 판정, 시험 시나리오(시험 방법은 테스트팀 담당이라 타입을 두지 않음)
- A의 생산 계획·접수 응답을 C 그래프 기록으로 만드는 것 (C → A 한 방향)
- C 범위 밖의 가상 검사 기록(장착 이력 조사 등 기존 기능에 시험 결과를 끼워 넣는 것)
- 기존 자유 필드에 시험·원인 정보를 넣는 방식
- 완성 보드 재고·출하(`FinishedGoodsStock`, `Shipment`)는 B 정의를 따른다. C에서 따로 만들지 않는다.

## 6. 공통 문서 반영

`SERVICE_SPEC.md` "공통 의미와 데이터 경계"의 기존 문장 뒤에 아래 문장을 추가했다. 기존 문장은 지우지 않았다.

> C 클레임 대응 범위에 한해 생산라인과 보드별 생산 기록, 고객 클레임, 품질 사건·영향 범위, 생산 중단·출고 보류 요청서를 가상 기록으로 허용한다. 클레임 증상은 고객 신고 원문이며 확인된 불량이나 원인이 아니다. 테스트팀에 보내는 시험 의뢰, 테스트팀이 돌려준 보드별 가상 시험 결과·조치 판정, 재생산 필요 수량도 허용한다. 시험 결과는 가상 관측이며 실제 고장 원인이나 불량률로 해석하지 않는다. 세부 조건은 [claim_response 데이터 정책](DATA_POLICY.md)을 따른다.

PR #6의 "시험 결과·조치 판정·재생산 요건은 별도 논의 후 정한다" 문장을 PR #7에서 위 문장으로 바꿨다.
