# 독립된 요청 입력창

기존 CQ01~06과 분리된 선택적 개발용 입구입니다. 코드를 재사용하지 않으려면 request_entry.py, request_entry.html, request_entry_cost.example.json, test_request_entry.py와 이 안내만 제거하면 됩니다. 기존 공통 코드·스키마·T-box는 수정하지 않습니다.

## 사용

http://127.0.0.1:8011/ 에서 요청 원문을 입력 → **LLM으로 요청 해석** → 표시된 내용 확인 → **확인한 내용으로 검증 환경에 등록** 순서로 사용합니다.

해석에는 실제 LLM API 비용이 발생합니다. 모델 호출 전 서버가 기존 조회 도구로 읽은 제품 구성과 기준 계획을 함께 제공합니다. 모델이 DB에 직접 쓰지 않습니다. 출력은 JSON 스키마로 제한하며 실제 ID·날짜·수량·인용 근거를 코드가 검증합니다. 해석이 올바른지 최종 확인하는 것은 입력창 사용자입니다. 원문은 요청의 사유 필드에도 그대로 포함되어 그래프에 남습니다.

등록은 기존 prepare_request → validate_draft → 별도 개발 검토 신원 review → apply_approved → Neo4j read_request로 수행합니다. 운영 사용자 인증/업무 승인으로 사용하면 안 됩니다. 전용 live_request_ 개발 스키마와 materials_live_request namespace만 받습니다. A 접수·자재 계산을 수행하지 않습니다.

## 실행

저장소 루트에서 기존 가상환경 Python으로 실행합니다.

```sh
python -m ontologics.order_fulfillment.request_entry \
  --database-env /absolute/test.env \
  --schema live_request_검증스키마 \
  --graph-env /absolute/.env.graph.local \
  --model-env /absolute/.env.local \
  --cost-policy ontologics/order_fulfillment/request_entry_cost.example.json \
  --allow-development-registration --port 8011
```

기준 데이터는 기존 개발 초기화 경로로 준비되어 있어야 합니다. 스키마가 비어 있거나 baseline_plan SourceDocument/Evidence가 없으면 요청 해석을 진행하지 않습니다. 모델 설정의 빈 비용 항목은 허용되지 않으며 --cost-policy로 명시적 공개 JSON을 지정할 수 있습니다. 키는 서버의 환경 파일에서만 읽습니다.

포함된 비용 예시는 GPT-5.4 mini 입력 $0.75/출력 $4.50 per 1M tokens, 해석 요청당 상한 $0.50입니다. [공식 모델 문서](https://developers.openai.com/api/docs/models/gpt-5.4-mini)에서 2026-11-03 확인했습니다. 누적 과거 실행 전체 비용 한도는 아니며 새 해석마다 별도 한도입니다. 공통 비용 예약 계산을 재사용합니다.

## 범위와 재시도

- 신규 추가 생산 한 건, 생산 완료/출고 기준을 지원합니다. 요청 수정·취소·고객 도착 기준은 이 간단한 입구의 범위 밖입니다.
- 미확인 필드는 보완 필요로 표시하고 등록하지 않습니다. 형식상 모델이 보완 응답에 반환하는 0/빈 문자열은 저장하지 않습니다.
- 페이지에서 같은 요청 키로 해석/등록을 재시도하면 저장된 상태를 이어갑니다. 반영 후 동기화가 실패해도 같은 키로 다시 등록할 수 있습니다.
- 입력 변경 또는 새로고침은 새 요청 키를 만듭니다. 별도 제출 간 같은 업무 수요인지 자동으로 판정하는 기능은 없습니다. 이미 등록한 수요를 새 요청으로 다시 제출하지 마세요.
- 해석 이후 DB 버전이 바뀌면 새 해석을 요구합니다.
- 원문·모델 응답·진행 상태는 이 폴더 아래 Git 제외 .local/<schema>/에 보관합니다. 기존 등록 함수가 생성하는 불변 문서는 기존 data/receipts/에 저장됩니다. 이는 코드 변경 범위가 아니라 기존 실행 결과 보존 경로입니다.
- 서버는 127.0.0.1만 바인딩하고 동일 Origin/Host 및 CSRF 토큰을 확인합니다. 공개 운영 서버가 아닙니다.

## 검증 기록

2026-11-03: 실제 API 응답으로 Rev L WROOM / 30대 / 2026-11-20 / production_complete 해석을 화면에서 확인했습니다. 초기의 날짜 기준 혼동과 응답 필드 불일치는 지침·구조화 출력으로 보완했습니다. 이 화면 확인 과정에서는 기존 사용자 요청을 중복 등록하지 않았습니다.

별도 개발 스키마에서 모델 대역을 사용한 입력→등록→Neo4j 조회 및 동일 키 재시도 테스트가 통과했습니다. 관련 테스트 21개 통과. 전체 회귀 결과는 아래 최신 결과에 기록합니다.

```sh
python -m unittest ontologics.order_fulfillment.test_request_entry -v
```

통합 테스트는 REQUEST_ENTRY_INTEGRATION=1, REQUEST_ENTRY_DB_ENV, REQUEST_ENTRY_GRAPH_ENV를 명시해야 합니다. 기존 요청 등록 테스트도 함께 실행할 때 DATABASE_URL/TEST_DATABASE_URL/NEO4J_*를 같은 검증 서버로 맞추세요. 통합 테스트는 별도 스키마를 생성하며 기존 체험 데이터는 바꾸지 않습니다.

최종 전체 회귀: 1,637개 실행, 실패 0, 오류 0, skip 10 (602.189초). `unittest discover`를 현재 검증 PostgreSQL/Neo4j 환경에서 실행했습니다. 로그는 이 폴더의 Git 제외 `.local/full-tests.log`에 보관합니다. HTTP 검사에서 CSRF 누락·다른 Origin·없는 요청 ID 거부도 확인했습니다.

## 기존 업무 맥락 연결 보완

입력창은 이제 기존 계획 원문, 제품, 계약 고객·계약 ID, 계약 품목의 기존 수량, 납품 차수의 수량·납기를 함께 표시합니다. 계획 원문/사용자 입력에 실제 계약·품목·차수 ID가 명시되거나, 계약 품목이 그 계획 Evidence를 참조하면 해당 연결을 사용합니다. 같은 제품을 사용한다는 사실만으로는 계약을 자동 선택하지 않습니다.

참조가 없거나 모호하면 실제 조회한 계약 품목·차수 후보를 표시하고 확인받습니다. 선택한 계약 품목은 제품과 실제/가상 구분이 같아야 하고, 차수는 해당 품목에 속해야 합니다. 계획/요청에 명시된 참조와 충돌하는 선택은 거부합니다. 계약에 차수가 등록되어 있지 않으면 계약 품목 수준의 요청임을 명시합니다. 연결 미확인 상태는 서버에서도 등록을 차단합니다.

확인한 contract_item_id와 delivery_round_id는 기존 요청 문서 필드에 저장됩니다. 사용자 선택으로 보완한 경우 그 선택 내역도 요청 원문 보존 기록에 남깁니다. 등록 후 PostgreSQL/Neo4j에서 동일 내용을 읽는 기존 검증을 유지합니다. 기존 요청의 계약을 소급해서 변경하지 않습니다.

현재 HB-20261102-01 원문에는 계약 식별자가 없으며 한빛물류시스템 고객이 기재되어 있습니다. 검증 DB의 기존 계약 고객들은 이 고객과 다릅니다. 따라서 현재 예시는 자동 연결되지 않는 것이 정상이며, 무관한 계약을 확정하지 말고 맞는 계약 자료를 보완해야 합니다. 기준 계획 원문을 수정하거나 임의 계약을 만들어 넣지 않았습니다.

보완 검증: 관련 테스트 28개 통과. 제품만 같을 때 자동 연결 금지, 명시 참조 자동 연결, 다중 차수 확인, 교차 계약 차수 차단, 기존 계획과 충돌하는 선택 차단, 연결 확인 전 등록 거부, 확인 후 등록·Neo4j 조회 및 재시도 검증을 포함합니다. 실제 모델 예시 해석 후 화면에서 미확인 계약 표시와 등록 버튼 비활성화를 확인했습니다. 내장 브라우저 제어 연결 오류로 Chrome에서 화면 확인했으며, 동일한 http://127.0.0.1:8011/ 을 새로고침하면 적용됩니다.

계약 맥락 보완 후 최종 전체 회귀: 1,644개 실행, 실패 0, 오류 0, skip 10 (639.023초). 로그: `.local/context-full-tests.log`. 현재 예시의 계약 미확인 요청을 실제 HTTP 등록 API에 제출했을 때 400으로 차단되는 것도 확인했습니다.
