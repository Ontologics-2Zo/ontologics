# B 담당자 생산 재고 출하 통합 작업 계획

작성일: 2026-10-27, Asia/Seoul  
대상: B의 생산 작업·완성품 재고·납품 수량을 담당하는 개발자  
상태: 통합 준비 계획. 아래 구현 작업은 미착수이며 공통 명칭과 관계는 팀 협의 후 확정한다.

B의 수량 기록과 C의 개별 보드 이력을 같은 작업·구성·출하에 연결하는 것이 목표다. B는 수량 계산과 납품 회차 연결을 맡고, C는 개별 보드와 사건 이력을 제공하는 역할 분담을 제안한다. 실제 팀 역할이 다르면 담당자만 조정한다.

팀에 보낼 내용은 [팀원 전달용 통합 협의안](B_C_INTEGRATION_TEAM_HANDOFF.md)에 정리했다. 이 계획의 현재 구현 기준은 [model.py](../ontologics/model.py), [물량 검증](../ontologics/fulfillment_validation.py), [물량 조회](../ontologics/fulfillment.py), [생산 관측 검증](../ontologics/production_validation.py)이다. C 쪽은 제공된 캡처 기준이므로 실제 스키마 확인이 선행돼야 한다.

## 현재 구현에서 유지할 기준

| 항목 | 현재 B의 계약 | 통합 시 주의점 |
| --- | --- | --- |
| ProductionWork | snapshot_id, company, configuration_id, observed_at, 목표·완료 수량, 생산 상태 | 스냅샷에 속한 작업 기록이다. 다른 시점의 기록과 동일 작업인지 식별 규칙이 필요하다. |
| ProductionObservation | production_work_id, observed_at, 총생산·정상·불량 누계 | 개별 보드 생산 기록과 별개다. produced_quantity = good_quantity + defective_quantity를 유지한다. |
| FinishedGoodsStock | 구성·위치·관측 시점별 수량 | quantity는 관측 시점 수량이다. 현황 시점 잔량과 혼동하지 않는다. |
| Allocation | 납품 회차에 재고 또는 생산 작업 수량을 배정 | stock_id와 production_work_id 중 정확히 하나를 사용한다. 둘 다 없거나 둘 다 있으면 거부한다. |
| Shipment | 배정·수량·목적지 및 예정/실제 출발·도착 시각 | 현재는 재고 배정 전량에 출하 한 건만 허용한다. 생산 작업 직접 출하와 부분·분할 출하는 지원하지 않는다. |
| ProductUnit | company, serial, configuration_id | 개별 보드 타입은 이미 있다. 회사와 일련번호가 같으면 같은 보드로 중복 검사한다. |
| 미구현 관계 | 개별 보드와 생산 작업·완성품 재고·출하의 직접 연결 | C의 타입·필드를 확인하고 공통 관계를 설계한다. |

현재 ProductionLine, UnitProductionRecord, delivery_reference는 model.py에 없다. 허용되지 않은 타입·필드를 임의로 추가하면 UNKNOWN_TYPE 또는 UNKNOWN_FIELD 검증 오류가 발생한다.

## 작업 순서와 산출물

### 1단계 팀 협의 자료 준비

독립적으로 먼저 수행할 수 있는 작업이다.

- [ ] 팀원에게 실제 C 스키마와 최소 예제 요청: 보드, 생산 기록, 창고 상태, 출하 또는 납품 참조 각 1건.
- [ ] 공통 ID 후보 정리: ProductUnit, Configuration, ProductionWork, Shipment, DeliveryRound.
- [ ] 각 ID에 대해 생성 담당, 중복 판정, 다른 버전·스냅샷에서의 재사용 여부를 표로 작성.
- [ ] delivery_reference가 출하 건·납품 회차·계약·외부 문서 중 무엇인지 확인.
- [ ] 캡처의 보드 207대와 식별자 구간이 전체 목록인지 예시인지, 기준 시점과 상태 범위 확인.

산출물은 팀원 전달 문서의 결정표 I01~I08과 C 예제 자료다. 캡처의 숫자나 식별자 구간을 확정된 통합 데이터로 사용하지 않는다.

### 2단계 공통 식별과 관계 확정

- [ ] ProductUnit과 Configuration을 공통 타입으로 재사용하고 양쪽 ID 대응표 작성.
- [ ] C의 UnitProductionRecord가 개별 보드 생산 기록이면 unit_id와 production_work_id를 연결하는 구조로 정리. 기존 ProductionObservation으로 이름을 바꾸지 않는다.
- [ ] C의 생산 작업 참조가 B의 어느 데이터 버전·스냅샷을 가리키는지 명시.
- [ ] 스냅샷을 넘어 유지할 업무상 작업 식별자가 필요하면 기존 작업 기록과의 대응 관계를 설계. 같은 작업이라는 근거 없이 이름만으로 합치지 않는다.
- [ ] 보드별 재고 소속과 출하 소속의 관계, 유효 시점, 중복 허용 범위를 정의.
- [ ] ProductionLine은 통합 질문에서 필요할 때 추가. C에 라인이 있다는 이유만으로 B의 필수 필드로 만들지 않는다.

최소 조회 문맥은 data_version, snapshot_id, as_of를 명시하고, 해당 문맥 안에서 production_work_id·stock_id·shipment_id를 해석하는 방식으로 제안한다. 영속 작업 ID의 필드명과 별도 타입 도입 여부는 C 구조를 확인한 뒤 결정한다.

개별 보드 하나가 여러 이력 사건에 등장할 수 있으므로 전 기간을 통틀어 출하 한 번 또는 창고 한 곳만 허용하는 규칙은 두지 않는다. 대신 동일 시점의 모순된 소속, 동일 출하 내 중복 보드, 지원하지 않는 재배정을 구분해 검증한다.

### 3단계 수량과 시점 대조 규칙 확정

- [ ] 정상 완료 수량, 불량 포함 총생산 수량, 현재 창고 잔량을 구분.
- [ ] 동일 회사·구성·작업·시점·범위이고 개별 기록의 완전성이 확인될 때만 C에서 B의 집계 수량을 산출.
- [ ] 같은 관측 시각의 completed_quantity와 good_quantity가 일치하는 기존 검증을 유지.
- [ ] C의 정상 완료 보드 수를 생산 누계와 대조하려면 누계 시작 범위, 보드별 완료 사실, 재작업·중복 처리 기준까지 일치하는지 확인.
- [ ] 재고 관측 시점의 보드 목록은 FinishedGoodsStock.quantity와 대조. 현황 시점의 목록은 출하 반영 후 잔량과 대조.
- [ ] 목록이 일부이거나 사건 이력이 불완전하면 집계를 미확인으로 남김. 빈 목록을 자동으로 0대로 확정하지 않는다.

현재 지원 형식에서는 재고 사건 완전성과 출하 전 재고 관측 조건 등이 확인되면 다음 계산을 사용한다.

`현황 시점 잔량 = 재고 관측 수량 - 해당 재고에서 실제 출발한 출하 수량 합계`

이미 출하가 반영된 C의 현재 창고 잔량을 위 식의 관측 수량에 넣고 출하를 다시 차감하면 안 된다. 현재 형식 밖의 추가 입고·반품·재배정이 있으면 기존 식에 임의로 끼워 넣지 않고 지원 범위와 검증을 함께 확장한다.

ProductionWork의 completed_quantity가 0보다 큰 기록은 그래프에 허용되지만, 현재 CQ02 현황 합계는 부분 생산 완료를 미지원으로 처리한다. C의 상세 기록을 연결한 것만으로 이 제한이 해소됐다고 표시하지 않는다.

### 4단계 합의한 계약 구현

1~3단계에서 확정된 범위만 구현한다. 아래는 향후 코드 변경 시의 체크리스트다.

- [ ] model.py의 SCHEMA, 필수·선택 필드, 참조, 허용 필드와 타입별 데이터 정책 갱신.
- [ ] 생산·재고·출하와 개별 보드 사이의 참조·시점·수량 검증 추가.
- [ ] 공통 변환·조회 계층에서 C 입력을 연결. Agent별 중복 모델과 직접 DB 쓰기를 만들지 않는다.
- [ ] 새 관계에 필요한 SourceDocument와 Evidence를 보존. 기존 원본은 수정하지 않는다.
- [ ] 실제 설계·BOM과 가상 운영 기록의 origin 구분 유지. 새 운영 타입의 synthetic 허용 범위를 명시.
- [ ] T-box와 JSON-LD, 대표 데이터, SERVICE_SPEC, TOOLS, 관련 버전과 PROJECT_STATUS를 함께 검토·갱신.
- [ ] 기존 데이터의 읽기 가능 여부와 변환 필요 여부를 기록. 미확인 연결은 보완 대상으로 남긴다.

### 5단계 통합 검증

| 검사 | 기대 결과 |
| --- | --- |
| 같은 회사·같은 serial의 보드가 양쪽에 존재 | 공통 보드 하나로 대응하고 중복 생성하지 않음 |
| 다른 회사에서 같은 serial 사용 | 일련번호만으로 합치지 않음 |
| 존재하지 않는 작업·보드·출하 참조 | 연결 거부 또는 명시적 보완 상태. 유효한 그래프로 통과시키지 않음 |
| 다른 구성의 보드를 작업·재고에 연결 | 구성 불일치 발견 |
| 다른 스냅샷·버전의 기록 혼합 | 혼합 사실 발견. 대응 규칙 없이 자동 연결하지 않음 |
| 동일 출하에 같은 보드 중복 등록 | 중복 집계 방지 |
| 완전한 보드 목록 수와 집계 수량 불일치 | 수량 불일치 발견 |
| 불완전하거나 빈 보드 목록 | 완전성 근거 없이는 0 또는 확정 합계로 처리하지 않음 |
| 재고 관측 후 일부 출발 | 관측 수량과 현황 잔량을 구분하고 출하를 한 번만 차감 |
| 출하 예정만 존재 | 실제 출발·고객 도착으로 계산하지 않음 |
| 실제 출발은 있으나 실제 도착 없음 | 운송 중으로 구분 |
| 생산 누계에 불량 포함 | 총생산과 정상 완료를 구분 |
| 부분 생산 완료·분할 출하 입력 | 미지원 범위를 유지하거나, 확장했다면 새 계산·검증으로 입증 |
| 새 관계의 T-box·JSON-LD 출력 | 참조 대상과 ID가 보존됨 |

구현 후 관련 단위 테스트를 먼저 실행하고 `python3 -m unittest discover -v`로 전체 회귀를 확인한다. 계약·시나리오가 바뀌면 `python3 -m ontologics.demo`와 변경 영역 예제를 실행한다. 저장소에 설정된 lint·typecheck·정적 분석이 있으면 함께 실행하고, 없으면 별도 미설정으로 기록한다. 테스트 DB는 개발 검증용 독립 스키마를 사용한다.

## 완료 기준

- [ ] 팀원 전달 문서 I01~I08의 결정 상태와 담당자가 채워짐.
- [ ] 최소 사례에서 보드 → 생산 작업, 보드 → 재고 소속, 보드 → 출하 → 배정 → 납품 회차를 근거와 함께 조회 가능. 범위에서 제외한 연결은 명시.
- [ ] 동일 시점·범위의 개별 목록과 집계 수량이 일치하거나 불일치 이유가 출력됨.
- [ ] 누락·중복·다른 버전·다른 구성 사례가 검증됨.
- [ ] 기존 B 기능과 관련 이력 조회 회귀가 통과하고 실제 실행 결과가 기록됨.

현재 완료된 것은 통합 준비 문서 작성이다. 공통 스키마 변경과 B·C 통합 구현·실행 검증은 후속 작업이다.
