- C 현황: `UnitProductionRecord.production_work_id`를 **선택 필드로 준비만** 했고 지금은 비어 있습니다. `ProductionWork` 타입이 `SCHEMA`에 들어오면 이 참조의 검증과 T-box 속성이 자동으로 켜지도록 작성했습니다.

  - `production_work_id`가 가리킬 값: `ProductionWork` 노드 ID인지, 스냅샷과 무관한 업무 ID인지

## 4. 함께 정해요: I04 보드별 재고·출하 소속

### 왜 필요한가

C는 보류·검사 대상을 **보드 한 대씩** 알아야 요청서를 쓸 수 있습니다. 지금은

- B의 `FinishedGoodsStock`·`Shipment`에는 **수량만** 있고 보드 목록이 없습니다.
- C에는 재고·출하 타입이 **없습니다** (같은 개념을 두 번 만들지 않으려고 일부러 만들지 않았습니다).
- 그래서 보드별 재고·출하 소속을 **아직 아무도 맡고 있지 않습니다.**

### C가 필요한 정보

| 질문 | 필요한 정보 | C 예시 |
|---|---|---|
| 이 보드가 기준 시점에 창고에 있나? | 보드 목록, 위치, 관측 시각, 목록 완전 여부 | C-S001~120, 데모 창고, 2026-10-26 10:00 기준, 완전 |
| 이 보드는 이미 나갔나? | 보드 목록, 실제 출발 시각, 고객, 외부 문서 번호 | C-D001~080, 2026-09-25, 가정 고객사 C-01, `DO-DEMO-C-001` |

### 정할 것과 C 제안

| # | 정할 것 | C 제안 | 누가 |
|---|---|---|---|
| ① | 보드 목록을 어디에 담나 | B의 `FinishedGoodsStock`·`Shipment`에 **선택 필드 `unit_ids`** 추가 | 함께 (B 타입 변경) |
| ② | 목록 완전 여부 | `unit_ids`가 있으면 완전 여부 필드를 함께 둔다 | 함께 |
| ③ | 시각 기준 | 재고는 관측 시각, 출하는 실제 출발 시각. 예정만 있으면 출하로 보지 않는다 | 함께 |
| ④ | 중복 규칙 | 같은 시점에 같은 보드가 재고와 출하에 모두 있으면 검증 오류 | 함께 |
| ⑤ | 외부 문서 번호 연결 | `Shipment`에 외부 문서 번호 필드를 두고 C의 `delivery_reference`와 대응 | **B 결정 요청** (필드 이름) |
| ⑥ | 출하에 필수인 연결 노드 | `Shipment → Allocation → DeliveryRound`가 필수라면 C 데모에 필요한 **최소 노드 세트**를 알려 주세요 | **B 결정 요청** |
| ⑦ | C 데모 재고·출하 데이터 작성 | **타입은 B, C-S·C-D 데이터는 C가** B 타입으로 `data/claim_response/`에 작성 | C 제안, B 동의 필요 |

다른 방식(예: 보드 소속을 별도 연결 타입으로 두기)이 B 구조에 더 맞다면 그 방식으로 맞추겠습니다. **C가 따라야 할 조건은 "보드 한 대씩 + 목록 완전 여부 + 실제 출발 시각" 세 가지**입니다.

1. `operations.json`에 재고 관측 1건(C-S 120대), 출하 1건(C-D 80대)과 ⑥의 최소 노드 추가
