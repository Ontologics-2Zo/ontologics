# B 분리 실행을 위한 최소 공통 요청 — 필수와 조건부

작성일: 2026-10-27 / 상태: **코드 근거를 붙인 요청 초안. 새 API·기반 구현 완료 또는 팀 합의를 뜻하지 않음.**

관련 [실행 보완 계획](b-common-additions-separation-20261027.md)의 E2~E3에서 재현 결과를 붙여 확정한다. 기존 [Task03 요청](../../JunhwaDocs/06_B체인_분리/분리_Task03_공통확장_계약확인.md)을 보존하며 R1~R6 전체를 일괄 선행 조건으로 요구하지 않는다. ‘공통 담당’은 원래 작성자 개인이 아니라 공통 변경의 설계·검토 책임을 뜻한다. 누구에게도 메시지나 이슈를 발송한 문서는 아니다.

## C01. B 추가 스키마·검증 정의를 공통 승인 경로가 수락 — 필수

**필요 조건:** 원래 main 위에서 Contract/ContractItem/DeliveryRound를 승인된 구조화 사실로 저장한다는 CQ01 목표를 유지할 때.

**현재 막히는 근거:**

- 기준 origin/main:model.py:72,89의 validate_graph는 SCHEMA 밖 타입을 UNKNOWN_TYPE으로 거부한다. 현재 작업 model.py:25에 B 3타입을 직접 넣어서만 수락되고 있다.
- 현재 model.py:303은 B 검증기를 직접 import한다. 이 직접 의존을 제거하고 B 소유 검증 정의를 전달해야 한다.
- 현재 service.py:455,484,519,541은 초안·검증·검토·반영에서 공통 validate_graph를 호출한다. graph_jsonld/model.py:311과 tbox_turtle/:329도 같은 타입·관계를 알아야 한다.
- 이전 임시 검사에서 원래 main은 SourceDocument/Evidence만 수락하고 계약3타입을 거부했으며 해당 그래프 JSON-LD는 KeyError였다. 이번 실행에서 재검사할 사례이며 과거 검사 통과를 새 기반의 증거로 삼지 않는다.

**요청 범위:** 구체 B 이름/업무 규칙은 B 파일에 두고, 추가 타입·필드·관계·origin/선택 필드·검증 정의를 공통이 일관되게 받아 사용하는 공개 계약. API 이름/생성자/구현 파일 수는 미정이다. 기존 타입 덮어쓰기와 중복 등록을 거부하고, 같은 승인 작업 중 서로 다른 등록 구성이 섞이지 않아야 한다.

**B가 제공할 것:** CQ01 3타입 정의, 업무 검증기, 원본·정답·유효/무효 후보, 충돌 사례, JSON-LD/T-box 기대 관계, B 버전·지원 공통 기준 목록.

**최소 수락 검사:**

1. B 미등록 시 기존 공통 회귀 통과; B 등록 시 CQ01 3타입 수락.
2. 중복/기존 타입·관계 의미 덮어쓰기 거부, 잘못된 수량/시간/참조 거부.
3. 초안→검증→다른 사람 승인→반영→명시 버전 조회·export에서 같은 정의 적용. 무효 초안 승인/반영 차단.
4. JSON-LD/T-box에서 동일 namespace·관계·근거 보존. 공통이 B 모듈을 직접 import하지 않음.
5. 등록 구성의 변경 때문에 승인 당시 검증 의미가 달라지는 경우를 명시적으로 거부하거나 재검토하도록 처리. 별도 장기 영속 구성 이력은 아래 강화 요구와 구분.

**제외:** B 계산식·고객 약속 문안·CQ02~06 정책 구현, 전역 변수 강제 변경, 별도 B 승인 엔진. 원본 metadata만 승인하는 대안은 추출된 계약 사실 승인을 충족하지 못한다.

## C02. 새 B 도구의 이름·입력·처리기를 공통 실행 경계에 연결 — 조건부

**활성화 조건:** 모델이 delivery_round 등 독립 B 도구 이름을 호출하고 그 이름으로 공통 도구 실행 기록을 남겨야 할 때. CQ01에서 기존 lookup+B 조립을 허용하면 선행 필수가 아니다.

**근거:** host.py:39~50의 역할 등록은 기존 허용 도구만 선택한다. service.py:623의 Gateway는 정적 허용 목록이다. host.py:84~106 및 runtime.py:64~81은 Service/Gateway를 직접 구성한다. B subclass 파일 추가만으로 실제 처리기가 바뀌지 않는다.

**B 우선 대응:** 기존 lookup을 정상 인자로 호출하고 B 순수 조립 결과에 lookup run_id·버전·정확 근거를 연결한다. CQ02~06도 가능한 대안을 CQ별로 평가하되 호출 수/출력 예산과 기존 의미를 검사한다. lookup 인자에 새 명령을 숨기지 않는다.

**조건부 요청:** 도구 설명·입력 형식·처리기를 공통 신원/권한/오류/실행 기록 안에서 조립하는 공개 계약. 특정 B Service 전체 교체를 처음부터 요구하지 않는다. API 형태는 미정이다.

**수락 검사:** 도구명/기존 이름 충돌 거부, 역할 최소 도구 제한, actor/principals 위조·Agent review/apply/bootstrap 거부, 성공·실패 run_id 영속 기록, Host와 실제 Runtime의 같은 정의 사용. B 처리기에서 공통 비공개 메서드를 복제/직접 호출하지 않는다.

## C03. Provider의 일반 설정 접점 — CQ01 선행 요구 아님

**근거:** runtime.py:64는 이미 callable Provider를 받는다. openai_provider.py:91,105,109,175에 추가한 parallel/도구 선택/응답 형식 연결은 B가 의존하지만 내부 훅이다. 단계별 정책은 examples/b_response_agent.py:317, b_comparison_agent.py:311 등에 있다.

**B 우선 대응:** 기존 callable protocol과 ModelConfig로 CQ01을 구현하고 업무별 단계/응답 정책을 B에 둔다. 공통 API 통신·보안 코드를 B에 복제하지 않는다.

**요청 활성화:** CQ03~06 등의 실제 필요한 설정을 기존 공개 기능으로 전달할 수 없고, B가 공통 내부 override 없이 사용할 수 있는 작은 설정 접점이 필요하다는 재현이 있을 때만.

**수락 검사:** 기본 Provider 기존 동작 유지, B 정책이 입력/출력/도구 제한을 지킴, 설정을 사용하지 않는 역할 영향0. max_tool_calls 전체 합계/실제 병렬 실행을 보장한다고 설명하지 않음. 실제 API 호출 없이 결정적 응답 대역부터 검사.

## C04. 설치·원본 공급·버전 — 배포 요구에 따른 조건부

**근거:** pyproject.toml:7은 현재 공통 버전0.8.0, :13 packages=["ontologics"], :16은 웹 정적 파일뿐이다. model.py:174의 원본 검증은 ROOT/data의 실제 파일과 SHA를 확인한다. 폴더를 옮기는 것만으로 설치나 외부 원본 검증이 해결되지 않는다.

**B 우선 대응:** 로더에 실제 경로 전달, 기존 data/sources 논리 path 유지, B fixture/예제/테스트 분리, B 시작 시 지원 공통 버전 검사 설계. 별도 배포 명세 등 공통 설정을 건드리지 않는 방안부터 검토한다.

**요청 활성화/최소 범위:**

- 새 B 하위 패키지를 기존 공통 배포물에 포함해야 한다면 패키지 포함 계약. pyproject 파일 전체 이동이나 공통 버전 임의 변경은 요구하지 않음.
- checkout 밖 다른 위치 원본까지 같은 논리 metadata로 검증해야 한다면 공통의 원본 접근 정책/공급 계약. 단순 저장소 내 CQ01에는 기존 경로 유지로 진행.
- 승인 당시 B 확장 지문을 장기간 DB에 고정·재검토해야 한다면 영속 구성/호환 계약. B 시작 시 버전 확인과 서로 다른 요구임을 명시.

**수락 검사:** 일회성 설치 후 checkout 밖 import·로딩·공통 검증, 경로탈출/원본 바이트 변경 거부, ID/path/SHA/locator 불변, 미지원 버전 거부. 장기 영속 요구를 선택하면 승인 당시 구성 재현/변경 시 재검토도 검사.

## 요청 확정·전달 형식

각 활성 요청은 `ID / 기준 전체 SHA / B 제공 파일·버전 / 실제 호출 입력 / 실제 오류·파일 줄 / B만의 대안과 한계 / 필요한 최소 동작 / 수락 검사 / DB·대역 실행 수준 / 미검증`으로 기록한다. 테스트 비밀값·개인 실행 원문은 넣지 않는다.

현재 판단은 **C01 필수, C02 조건부, C03 CQ01 불필요·후속 조건부, C04 설치/외부 공급/영속 요구별 조건부**다. 새 팀 기반이 제공되면 실제 코드를 다시 확인하고 이미 충족된 요청은 제거한다. 정확한 기반 SHA 없이 ‘공통 무수정 전체 분리 완료’로 보고하지 않는다.
