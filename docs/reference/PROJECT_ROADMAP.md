# 제조 제품정보 프로젝트 진행 순서

기준일: 2026년 10월 21일, 한국 시간. 버전: v2. 진행 방식은 **공통 기준 정리 → 실제로 동작하는 데이터·도구 준비 → 동료의 Agent 개발과 통합**이다. 전체 서비스에는 시나리오 1·2를 모두 유지한다.

현재 준비된 것은 기획 전달안과 이 진행표다. 공통 T-box·지식그래프·도구의 구현 완료 상태는 아니다. 이번 인계의 우선 목표는 동료가 공통 기반 위에서 Agent를 개발할 수 있는 기준 버전을 만드는 것이다.

이 안내는 다음 할 일을 기억하기 위한 기준이다. 관련 작업은 묶어 진행하고, 항목마다 별도 문서나 사용자 허락을 요구하지 않는다. 실제 완료 근거가 있을 때만 완료로 기록한다.

## 1 지금 전달할 것과 시작 메시지

이번에 갱신한 CODEX_HANDOFF.md와 이 PROJECT_ROADMAP.md 두 파일을 같은 프로젝트에 넣거나 첨부하고, 아래 메시지를 보낸다. 이전 대화의 추가 문구를 따로 합칠 필요는 없다. 파일명에 번호가 붙어 있다면 본문 제목과 v2 표시로 두 문서를 식별한다.

### Codex에 처음 보낼 메시지

```text
첨부한 Codex 전달안과 프로젝트 진행표(v2)를 기준으로 프로젝트를 이어서 진행해줘.

[우선 목표]
내가 Codex와 공통 기반을 먼저 준비하고, 동료들은 그 위에서 주로 Agent를 개발할 예정이야.
공통 PRD·CQ·개발 지침, T-box, 초기 지식그래프, 조회·검증·등록초안 도구가 연결되어
동료가 실제 호출 예제로 개발을 시작할 수 있는 기준 버전을 만들어줘.

[유지할 서비스 기준]
- 시나리오 1: 문제 상황 분석 및 생산·사용 이력 보완.
- 시나리오 2: 기존 구성 기준에 연결한 제품 등록.
- BOM 생성: 실제 사양서·기존 BOM을 읽어 등록용 구조화 정보를 만드는 것.
- 제품 사양·설계·BOM은 확인된 OLIMEX 공개 자료를 최대한 활용.
- 가상 회사의 재고·입출고, 개별 제품·부품 로트 식별 정보, 장착·제거 기록은 허용.
- 실제 자료와 가상 기록을 구분하고 A 시점 질문과 B 기간 질문을 모두 유지.
- 전체 서비스 범위를 먼저 잡고, 작업 효율을 이유로 두 시나리오나 보완·승인 흐름을 축소하지 말 것.

[공통 기반과 협업]
제품·로트의 의미, 그래프 구조, 시간 조회, 검증·승인 경로는 공통으로 관리해줘.
동료는 공통 도구를 활용해 Agent의 지시사항·추출·해석·대화·결과 설명에 집중하게 해줘.
공통 도구는 필요한 수준의 내부 함수나 API로 시작하고, 별도 서버·MCP를 강제하지 말아줘.
공통 기준과 코드는 같은 저장소에서 버전 관리하고, 반복되는 개발 절차만 Skill로 묶어줘.
개발용 AGENTS.md·Skill과 서비스 Agent의 실행 지침·권한은 구분해줘.

기본 Guardrail과 실행 상태·기록·실패·중복 방지는 해당 기능 구현에 함께 포함해줘.
추가 Agent, OpenRouter, 자동 모델 라우팅, 대규모 실행 플랫폼은 필요가 확인될 때 검토해줘.

[진행 방식]
관련 작업을 결과를 확인할 수 있는 업무 단위로 묶고, 기존 자료·문서·코드를 재사용해줘.
문서와 체크리스트의 각 항목을 별도 작업·파일·승인 단계로 만들지 말아줘.
중복 조사·검증·문서와 목적이 불분명한 구조는 정리하되, 원본 근거·시간 조건·권한·승인 검증은 유지해줘.
이미 확정한 내용은 다시 질문하지 말고 일상적인 조사·설계·구현은 자율적으로 진행해줘.
서비스 의미·데이터 범위·승인 권한·공통 계약에 큰 영향을 주는 결정만 추천안·이유·영향을 묶어 알려줘.
답변을 기다리는 동안에도 독립적으로 진행 가능한 작업은 계속해줘.

[바로 시작할 일]
기존 프로젝트 파일·설정·문서를 읽고 전달안과의 차이를 확인해줘.
실제 자료와 CQ를 대조하면서 공통 설계를 구체화하고,
진행 가능한 공통 기능은 대표 데이터와 호출 예제로 구현·실행 확인까지 이어가줘.
계획 제안만으로 끝내지 말고, 미결정·미검증·환경 제약은 실제 완료 범위와 구분해줘.

PROJECT_STATUS.md에는 현재 단계, 완료 근거, 남은 결정,
동료가 시작할 수 있는 범위, 다음 작업을 기록해줘.
진행 결과는 서비스 기준, 작동하는 공통 기능, 확인하지 못한 부분,
내가 결정할 사항, 다음 작업 중심으로 알려줘.
```

## 2 세 가지 큰 작업 흐름

| 단계 | Codex와 진행할 일 | 내가 확인할 것 | 결과 |
| --- | --- | --- | --- |
| 1 공통 서비스·자료 기준 | 전체 PRD·CQ, 실제 원본 대응, 핵심 용어·관리 단위·시간·승인 결정, 전체 사용자 흐름 | 두 시나리오·BOM 의미·실제/가상 경계가 유지되는가 | 구현할 업무와 검증할 답이 같은 기준으로 정리됨 |
| 2 공통 기반 구축 | T-box·초기 그래프, 조회·검증·초안·승인 반영 도구, 공통 실행·개발 지침, 핵심 화면·API 접점 | 동료가 저장 구조를 바꾸지 않고 실제 도구로 Agent 개발을 시작할 수 있는가 | 실행 방법·입출력·근거·기대 결과가 갖춰진 공통 기준 버전 |
| 3 Agent 개발과 통합 | 동료별 Agent 기능 개발, 필요한 공통 변경, 화면·API·Agent 연결, 두 시나리오 전체 검증 | 업무 결과와 원본 근거가 끝까지 이어지는가 | 등록·조사·보완·승인·재조회가 재현되는 서비스 |

이전 8단계는 확인할 내용을 세분화한 목록이었다. 이번에는 공통 설계와 그 설계를 검증하는 공통 구현을 함께 진행한다. 문서 정리는 전 과정에 포함하고, 반복적인 단계 승인 절차로 만들지 않는다. 새로운 근거가 나오면 영향받는 기준을 수정한다.

### 단계 1에서 사용자에게 필요한 판단

개별 제품의 관리 단위, 원본으로 확인할 옵션 범위, B 기간 질문의 업무 의미, 등록·보완 승인 단위와 권한처럼 서비스 결과가 달라지는 결정을 한다. 실제 사용할 제품·개정·변형은 Codex의 자료 대조 결과와 함께 판단한다.

구체적인 미결정 목록은 전달안의 O01~O08을 사용한다. 이미 합의한 내용을 다시 정하거나 기술 세부 선택마다 멈출 필요는 없다. 범위 밖의 가상 검사·고장·가동 기록은 합의 없이 추가하지 않는다.

### 단계 2에서 먼저 연결할 것

- CQ와 원본 근거에 맞는 T-box, 식별 기준, 초기 그래프와 운영 기록.
- 제품·구성·근거 조회, A·B 시간 조회, 등록·수정 초안 및 승인된 버전의 반영 경로.
- 동일한 결과·근거·미확인·오류 표현, 실행 상태와 승인 상태의 구분.
- 모델·도구 호출, 기본 기록·실패 처리, 변경 작업 재시도의 중복 방지.
- 공통 개발 지침, 필요한 반복 절차, 실행 방법과 기본 도구 호출 예제.

전체 데이터와 모든 예외를 먼저 채우는 것은 목표가 아니다. 대표 데이터로 공통 기능을 확인하고 아직 없는 범위를 명시한다. 확인한 원본의 시험용 시드 적재는 운영 등록 흐름과 구분한다. UI 전체 완성까지 기다리지 않되, 사용자 검토·승인과 결과 확인의 접점은 정리한다.

### 단계 3에서 동료가 담당할 것

동료는 주로 Agent의 지시사항·추출·해석·도구 선택·호출 순서·대화·결과 설명과 담당 기능 검증을 개발한다. Product·Knowledge·Quality 및 Supervisor는 책임 구조안이며 역할별로 별도 모델·서버·Skill을 반드시 만들지는 않는다.

공통 도구·스키마 변경이 필요하면 이유와 영향이 드러나는 제안으로 모으고 함께 반영한다. Agent 내부 개선은 담당자가 자율적으로 진행한다. 공통 기반의 주 담당은 사용자이지만 모든 코드를 혼자 작성해야 한다는 뜻은 아니다. 화면·API·승인·Agent 통합까지 전체 서비스의 담당 범위를 정해 완료한다.

## 3 동료에게 넘길 준비가 되었는지 확인

| 확인할 내용 | 확인 방법 |
| --- | --- |
| 공통 업무 기준 | S1·S2·CQ, 실제/가상 범위, 개체·로트·시간·승인 의미가 문서와 코드에서 같음 |
| 실제로 연결된 데이터 | 확인한 사양·BOM과 허용된 가상 기록이 원본 근거·버전과 연결됨 |
| 호출 가능한 도구 | 대표 등록·수정 초안과 A·B 조회를 공통 예시로 실행 가능 |
| 보완과 확정 반영 | 근거 부족·충돌을 표현하고, 승인 전후를 구분하며 같은 조건으로 재조회 가능 |
| 개발 시작 방법 | 도구 입출력, 오류·근거 형식, 실행 방법, 기본 연결 예제와 기대 결과가 있음 |
| 남은 범위 | 아직 없는 기능, 미검증 자료, 동료가 시작할 수 있는 역할을 구분함 |

공통 기능의 실제 실행을 근거로 판단한다. 문서 작성, 시드 적재, mock 호출만으로 전체 기능이 완성됐다고 표시하지 않는다. 공통 도구의 계약이 준비된 범위는 먼저 활용할 수 있고, 아직 연결되지 않은 범위는 명시한다.

## 4 공통 규칙과 선택 기능

| 구분 | 초기 적용 | 이후 판단 |
| --- | --- | --- |
| 공통 기준 | PRD·CQ·모델·도구를 같은 저장소와 기준 버전으로 관리 | 변경 영향에 맞춰 함께 갱신 |
| 개발 지침 | AGENTS.md에 공통 규칙과 참조 문서 기록 | 반복 절차가 확인되면 Skill로 재사용 |
| Guardrail | 입력·근거·권한·승인 버전 검증 | 업무별 고급 검사 확장 |
| Harness | 호출·상태·기록·실패·재시도·중복 방지 | 장기 실행·복구 등 필요에 따라 확장 |
| 모델 접근과 라우팅 | 공통 호출부와 고정 모델로 검증 가능 | OpenRouter·자동 라우팅은 실제 필요와 평가 결과에 따라 도입 |
| 추가 Agent | 기본 책임 구조를 사용 | 독립 역할의 효과가 확인되면 추가·분리·통합 |

개발 절차를 줄이는 것과 서비스의 등록·수정 승인을 생략하는 것은 구분한다. 정확성을 좌우하는 검증을 유지하되, 관련 변경이나 새 위험이 없으면 같은 검증을 반복하지 않는다. 문서·Skill·프레임워크 개수를 성과로 삼지 않는다.

## 5 프로젝트를 잊지 않고 이어가는 방법

매 작업 종료 시 PROJECT_STATUS.md에 다음을 간단히 남긴다. 별도 보고서를 추가로 만들 필요는 없다.

```text
현재 큰 단계:
현재 기준 문서·코드 버전:
이번에 완료한 결과와 실행 근거:
이번에 결정하거나 변경한 내용:
남은 결정·미검증 자료·환경 제약:
동료가 지금 시작할 수 있는 범위:
다음 한 가지 행동:
```

다음 작업을 시작할 때는 아래처럼 요청한다.

> PROJECT_STATUS.md와 최신 기준 문서·결정 기록을 읽고 다음 작업부터 이어서 진행해줘. 확정된 내용은 다시 정하지 말고, 새로 발견한 차이와 실제 검증 결과를 반영해줘. 관련 작업은 묶어서 진행해줘.

사용자는 서비스 범위·자료 해석·승인 권한 같은 중요한 선택과 실제 완료 근거를 확인한다. 일상적인 조사·설계·구현을 작은 항목으로 나누어 매번 지시할 필요는 없다.

## 6 지금 할 다음 행동

**갱신한 두 파일을 Codex 프로젝트에 첨부하고 1절의 시작 메시지를 보낸다.**

첫 작업부터 전체 서비스를 유지하면서 공통 기반 구축을 진행한다. 중요한 미결정은 추천안과 영향으로 확인하고, 독립적으로 진행 가능한 일은 계속한다. 공통 기준 버전이 준비되면 동료는 그 버전과 도구 예제를 받아 Agent 개발을 시작한다.
