# B→A 추가 생산 자재 검토 요청 — 데이터 초안·공통 연결 검토

작성일: 2026-11-02. 최종 보완: 2026-11-03. 버전: 1.2 — 조회 기대값·원문 해시·손상 후 재시도 검증 보완.
작업 브랜치: `feature/b-ab-connection`, 출발점: `integration/a-b`의 `882804f`.

**요청 타입·검증·통합 T-box에 이어 기존 B 호스트의 요청 초안 등록 호출을 연결했다. 실제 PostgreSQL 승인 저장 검증과 Neo4j 동기화·조회 검증은 아래 현재 결과를 구분해 따른다.**
아래 필드 계약은 현재 작업 브랜치의 구현 기준이다. 메모리 후보 검증 통과는 DB 반영 성공을 뜻하지 않는다.
B 1차 MVP를 기준으로 하는 연결 작업이며 B 2차 서비스 기획·가상 사업장 확장은 포함하지 않는다.
기준 요구사항은 [A 전달 문서 2.1](../../ontologics/materials/docs/B_TO_A_MATERIALS_REQUEST.md)이다.
사용자가 확인한 카톡 기준으로 최종 공유는 작업 브랜치 push까지이며 PR은 생성하지 않는다.
2026-11-03 사용자 지시에 따라 T-box를 사용자가 나중에 별도로 반영한다는 임시 방침은 적용하지 않는다.
공식 생성기로 통합 `ontology/tbox.ttl`을 갱신하고 기존 정의 보존을 검증하는 작업을 이번 구현 범위에 포함한다.
공통 등록 코드 변경이 필요할 때는 전달 문서 2절에 따라 연결 위치·오류·재현 사례와 변경 범위를 먼저 정리·조율한다.
순서 1에서 4개 공통 코드 파일과 통합 TTL·관련 시험의 최소 변경안을 정리했고,
사용자의 순서 2 진행 지시에 따라 해당 범위를 이 작업 브랜치에 적용했다. 외부 담당자에게 메시지를 발송하거나 외부 합의를 대신 기록하지 않았다.
초안 0.1/0.2는 문서만 작성했다. 0.3에서는 B 코드·시험·가상 원문을 추가했으며 기존 공통 코드·T-box·원본·DB·Git 브랜치는 변경하지 않았다.

## 1. 이번 기능이 하는 일

사용자 또는 근거 문서가 명시한 **추가 정상 완제품 수량**을 확인하고,
그 제품을 더 생산하기 위한 자재 검토 요청을 공통 그래프에 등록한다.
A 담당자가 이후 사용할 기존 공통 조회에서 요청과 근거를 읽을 수 있는지 검증한다.

```text
추가 수요 원문 + 기존 계획 근거 + 제품/계약 참조
  → B 요청 후보와 미확인 사항 검증
  → 기존 공통 초안·사람 검토·승인 반영
  → 기존 Neo4j 동기화 및 ready 확인
  → 기존 lookup으로 ID·타입·원문 근거 조회
```

- 예: 기존 계획 외에 완제품 30대가 더 필요하다는 요청. 부품 30개의 구매 요청이 아니다.
- 기존 B의 납기 부족량·미배정량·잔여 약속량을 자동으로 추가 생산량에 대입하지 않는다.
- A의 접수·읽음·자재 계산·예약·구매·회신과 기존 납품 약속 변경은 이번 기능에서 실행하지 않는다.
- 새 에이전트·공개 모델 도구는 선행 조건이 아니다. B 입력 검증과 신뢰된 호스트 등록 경로부터 연결한다.

## 2. 사용자 입력과 공통 등록 데이터 구분

사용자는 업무 내용을 제출하고 B 코드는 제품·수량·날짜·근거를 검증한다.
공통 실행자는 신원·등록 시각·초안 버전·승인·데이터 버전을 관리한다.
모델이 원문 해석을 돕더라도 신원·승인·자료 등록 여부를 생성하거나 확정하지 않는다.

| 사용자 또는 원문에서 받을 정보 | 처리 |
| --- | --- |
| 대상 제품 구성 | 실제 `Configuration` ID를 조회. 관련 계약 품목이 있으면 제품 일치 확인 |
| 추가 정상 완제품 수량 | 양의 정수, `piece`. 알 수 없으면 0으로 바꾸지 않고 후보 보완 |
| 기준 계획 문서 | 전달받은 문서 원문을 보존해 `SourceDocument`·`Evidence`로 연결 |
| 필요한 날짜와 의미 | 생산 완료·출고·고객 도착 구분. 날짜와 명시적 시각 구분 |
| 추가 사유·수량 근거 | 원문에서 확인. B 예상 부족분만으로 추가 수요를 확정하지 않음 |
| 변경 조건 | 변경 없음 / 변경 있음 / 미확인. 변경 있음이면 내용 포함 |
| 관련 계약·납품 회차 | 실제 등록 ID가 있는 경우만 참조. 미등록 계약을 조회 성공으로 표시하지 않음 |
| 기존 요청의 수정인지 | 요청 ID와 기대 개정으로 지정. 수정 수량은 대체값 |
| 관련 B/C 요청이 있는지 | 확인된 경우 관계와 근거를 보존. 외부 문서 번호와 실제 그래프 ID를 구분 |

원문 요청자·요청일은 공통 실행자·등록일과 다를 수 있다. 원문 근거에 보존하고 동일 인물·시각으로 자동 치환하지 않는다.

## 3. 요청 노드 초안

등록 타입명은 `AdditionalMaterialReviewRequest`다. 필드·enum은 현재 작업 브랜치의 공통 graph-0.4 계약이다.
이 타입은 A 자재 검토 요청 전용이므로 `recipient_role`은 선택 필드다. 명시한다면 `materials`만 허용한다.
전달 문서의 ‘해당할 때만 추가할 정보’에 맞춰 중복 필수 조건을 제거했다.
이 필드는 업무 대상의 표시이며 에이전트 실행·접근 권한·A 접수 여부를 부여하지 않는다.

### 3.1 공통 필드와 기본 업무 필드

| 필드안 | 형식·필수 조건 | 의미·검증 |
| --- | --- | --- |
| `id`, `type`, `origin`, `evidence` | 기존 공통 필드 | 이번 시험 요청은 `synthetic`. 근거 ID는 실제 원문 등록 단계에서 생성 |
| `configuration_id` | 필수, `Configuration` 참조 | 정상 완제품의 대상 구성 |
| `quantity` | 필수, 양의 정수 | **이번 추가 요청량**. 전체 계약 수량이나 투입량이 아님. bool·소수 거부 |
| `unit` | 필수, `piece` | 정상 완제품 개수 |
| `recipient_role` | 선택, 명시하면 `materials` | A 전용 타입이므로 생략 가능. 다른 역할·빈값은 거부. A 접수·검토 상태가 아님 |
| `request_revision` | 필수, 1 이상의 정수 | B 업무 요청 개정. 호스트 검증 코드가 부여·검사하며 공통 데이터 버전과 구별 |
| `reference_data_version` | 필수, 0 이상의 정수 | 같은 저장소·schema에서 참조 조건을 확인한 공통 버전. 호스트가 실제 조회 후 고정 |
| `reason` | 필수, 비어 있지 않은 문자열 | 추가 생산 수요의 사유. 수량 산식·제외 물량은 연결 원문에 보존 가능 |
| `need_mode` | 필수, `inherit_round` / `explicit` / `unknown` | 기존 회차 기한 재사용·별도 날짜 지정·미확인 구분 |
| `conditions_state` | 필수, `unchanged` / `changed` / `unknown` | 기준 계획 대비 변경 여부 |
| `readiness` | 필수, `ready` / `needs_supplementation` | B 요청 내용의 준비 수준. 공통 초안 승인 상태나 A 접수 상태가 아님 |

### 3.2 조건부 필드

| 필드안 | 필요한 경우 | 의미·검증 |
| --- | --- | --- |
| `baseline_plan_evidence_id` | `ready`이면 필수 | 기준 A 계획 문서를 보존한 `Evidence`. 존재하지 않는 공통 계획 노드를 만들지 않음 |
| `contract_item_id` | 등록된 관련 품목이 있음 | `ContractItem` 참조. 직접 지정 제품과 일치해야 함 |
| `delivery_round_id` | 관련 회차가 있거나 `inherit_round` | `DeliveryRound` 참조. 회차의 품목·제품을 따라가 요청 제품과 일치 검사. 품목도 지정하면 소속 일치 검사 |
| `need_basis` | `explicit` | 신규 요청 전용 값 `production_complete` / `dispatch` / `arrival` 제안 |
| `need_date` | `explicit`, 원문이 날짜만 제공 | 실제 달력 날짜 `YYYY-MM-DD`. 임의 시각·시간대를 붙이지 않음 |
| `need_at` | `explicit`, 원문이 시각까지 제공 | 공통 `instant()`가 허용하는 명시적 시각+UTC offset |
| `destination` | 고객 도착 기준이며 기존 회차에서 확인 불가 또는 도착지가 다름 | 추가 요청의 도착지. 기존 `DeliveryRound`를 수정하지 않음 |
| `conditions_note` | `changed` | 바뀐 조건만 기록. 제품 자체가 달라지면 별도 요청 |
| `supplementation_reason` | `needs_supplementation` | 무엇을 확인해야 하는지 설명. 상세 항목은 원문 근거에도 보존 가능 |

기존 `DeliveryRound.due_basis`는 현재 `arrival`만 지원한다.
새 요청의 생산 완료·출고 기준은 신규 필드의 의미이며 기존 허용값을 넓히는 변경이 아니다.
`reference_data_version`은 입력 task의 `input_revision`이나 A 문서 개정 번호가 아니다.
A `LibraryPlanDocument`의 실제 식별 정보는 문서 ID·`created_at`·`content_hash`이며 임의의 `document_version=1`을 만들지 않는다.

### 3.3 준비 상태와 날짜 규칙

- `ready`: 제품·추가 수량·기준 계획·사유와 근거·필요 날짜/기준·변경 조건이 확인되어야 한다.
- `inherit_round`: 실제 회차 참조가 필수다. 기준 버전에서 `due_at`·`due_basis`·`destination`을 확인하고, 당시 내용을 재현할 수 있도록 원문 근거에도 보존한다. 별도 `need_date`·`need_at`·`need_basis`를 동시에 넣지 않는다.
- `explicit`: `need_basis`와 `need_date` 또는 `need_at` 중 정확히 하나가 필요하다. 도착 기준이면 도착지도 확인한다. 회차가 있어도 새 필요 조건을 명시한 것으로 처리한다.
- `unknown`: 날짜를 추정하지 않는다. `needs_supplementation`과 이유가 필요하다.
- `unchanged`: 확인된 기준 계획의 조건을 재사용한다. 기준 계획이 미확인이면 `ready`가 될 수 없다.
- `changed`: `conditions_note`가 필요하다. `unknown`은 보완 대상으로 남긴다.
- 제품 ID·양의 수량 등 노드 필수값이 없는 후보는 유효한 그래프 요청 노드로 만들지 않는다. 후보/공통 `needs_changes` 초안과 확정 요청을 구별한다.
- 노드 필수값은 있고 기준 계획·필요 조건이 덜 확인된 경우에는 이유가 있는 보완용 노드 표현을 허용한다. 이 노드는 자재 검토 가능한 완전 요청으로 표시하지 않는다. 승인해 보관한 보완 대상 요청도 아래 규칙으로 같은 ID의 새 개정에서 완성할 수 있다.
- 고객 도착일에서 생산 완료일·자재 필요일을 역산하는 기능은 이번 범위에서 제외한다.

### 3.4 관련 요청과 요청 분리 규칙

관련 B/C 요청이 확인되면 관계를 요청 원문 또는 별도 관계 설명 원문에 남기고,
해당 `SourceDocument`·`Evidence`를 요청의 기존 `evidence`에 연결한다.
이번 최소안에서는 별도 C 요청 타입이나 자동 중복 판별 엔진을 추가하지 않는다.

| 확인한 관계 | 남길 내용·처리 |
| --- | --- |
| 기존 요청 수정 | 대상 요청 ID·이전 개정·대체할 수량과 수정 근거. 같은 요청의 새 개정으로 처리 |
| 동일 수요 | 관련 요청 식별자와 동일한 수요라는 근거. 이미 요청한 수량을 새 추가량에 자동 합산하지 않음 |
| 독립 수요 | 관련 요청이 있어도 별개로 필요한 수량과 근거. 새 요청 ID로 처리 |
| 관계 미확인 | 관련 요청 존재와 확인할 사항을 기록. 중복 여부가 추가량 확정에 영향을 주면 `needs_supplementation`으로 남김 |

관계 설명에는 대상 식별자가 **외부 문서 번호인지 실제 등록 그래프 ID인지**를 구분한다.
그래프 ID로 명시한 대상은 해당 기준 버전에서 실제 존재하는지 확인한다.
미지원 C 재생산 요청은 외부 문서 근거로만 보존하고, 등록된 내부 노드인 것처럼 참조하지 않는다.
같은 제품·날짜라는 이유만으로 동일 수요로 판정하거나 독립 수요를 병합하지 않는다.

한 입력에 제품 구성 또는 필요 날짜/기준이 다른 물량이 있으면 요청을 나눈다.
예를 들어 동일 제품 30대는 11월 6일 생산 완료, 10대는 11월 9일 고객 도착이 필요하면 별도 요청 두 건이다.
각 요청은 자기 수량·날짜/기준·근거를 가지며 원문 하나를 함께 참조할 수 있다.
같은 요청 ID의 수정에서는 제품·계약 품목과 이미 확인된 기준 계획·필요 날짜/기준을 유지하면서 수량·설명·변경 조건을 정정한다.
이전 승인 요청이 `needs_supplementation`이면 미확인 기준 계획을 채우거나, `need_mode=unknown`을 실제 날짜/기준 또는 등록된 회차 참조로 확인할 수 있다. 이때만 이전에 없던 회차 참조도 추가할 수 있다. 이미 지정된 회차는 유지한다.
미확인 정보를 보완해도 새 근거·개정 증가·실제 기준 버전 검사와 다른 사람의 정확 버전 승인을 거친다. 한 번 확인된 기준 계획·날짜는 이후 준비 상태를 보완 대상으로 바꿔도 변경·삭제할 수 없다.
제품·계약 품목 또는 이미 확인된 기준 계획·필요 날짜/기준을 바꾸는 입력은 기존 요청의 단순 수정으로 덮어쓰지 않는다.
새 요청이 이전 요청을 대체하는 것인지 별도 수요인지는 근거로 구분하며, 이전 요청을 자동 취소하지 않는다.
대체 관계에서 이전 요청의 유효 물량 처리가 확인되지 않으면 새 요청은 `ready`로 표시하지 않는다.

### 3.5 회차·품목·제품 참조 검증

1. `contract_item_id`가 있으면 품목의 `configuration_id`와 요청 제품을 비교한다.
2. `delivery_round_id`가 있으면 회차의 `contract_item_id`로 품목을 조회하고 그 제품과 요청 제품을 비교한다. 요청에 품목 ID를 따로 입력하지 않아도 이 검사를 수행한다.
3. 품목과 회차를 함께 지정하면 회차가 해당 품목에 속하는지도 확인한다.
4. 미등록 참조·소속 불일치·제품 불일치는 유효한 요청 등록을 거부한다. 조건이 단순 미확인인 보완 상태와 구분한다.

검사에는 같은 저장소·기준 버전의 자료를 사용한다.
`reference_data_version`을 적는 것만으로 과거 참조 조회가 자동 적용되는 것은 아니므로,
B 등록 경로가 해당 버전의 실제 값과 보존한 근거를 대조해야 한다.

## 4. 대표 입력과 수정 방식

아래는 설계를 설명하는 **가상 업무 입력 예시**다. 실행 fixture나 등록된 요청이 아니다.
제품 ID만 현재 `data/catalog.json`에 존재하는 값을 사용했다. 아래 문서 경로는 아직 생성하지 않은 예시다.
원문·근거 노드·참조 버전은 등록 경로에서 실제로 준비하고 검증해야 한다.

```json
{
  "business_request_id": "material-review:demo:001",
  "expected_request_revision": 0,
  "configuration_id": "config:esp32-poe:L:WROOM",
  "quantity": 30,
  "unit": "piece",
  "baseline_plan_source": "예시/기준계획.txt",
  "need": {"basis": "production_complete", "date": "2026-11-06"},
  "conditions": {"state": "unchanged"},
  "reason": "기준 계획 외 정상 완제품 30대 추가 수요",
  "request_source": "예시/추가요청30대.txt"
}
```

위 객체는 사용자 입력안이다. 그대로 `prepare_draft`에 보내는 그래프 노드가 아니다.
B 호스트 경로가 실제 참조·원문·근거·개정·버전을 확인한 후 공통 `put` 묶음으로 구성한다.
synthetic 요청 원문은 기존 원본 보존 규칙에 맞게 `data/sources/` 아래 새 파일로 추가한다.
등록되지 않은 입력의 출처를 확정 `EvidenceRef`로 미리 반환하지 않는다.

| 경우 | 업무 ID·개정 | 기대 수량·이력 |
| --- | --- | --- |
| 처음 30대 요청 | `001`, 기대 개정 0 → 개정 1 | 추가량 30대. 기준 계획 100대라는 이유로 130대를 요청량에 기록하지 않음 |
| 30대를 40대로 수정 | 같은 `001`, 기대 개정 1 → 개정 2 | 최신 추가량 40대. 새 원문·Evidence 사용. 70대로 합산하지 않음 |
| 독립 수요 10대 추가 | 새 `002`, 기대 개정 0 → 개정 1 | 독립 수요 근거를 갖는 별도 10대 요청. `001`의 수정으로 취급하지 않음 |
| 동일 명령 재시도 | 같은 키·같은 본문 | 요청·개정·공통 데이터 버전을 중복 증가시키지 않음 |
| 오래된 개정으로 수정 | 현재 2인데 기대 개정 1 | 충돌. 최신 요청을 읽고 다시 검토. 자동 합산·자동 덮어쓰기 없음 |

수정 표현은 같은 요청 노드 ID의 새 내용으로 제안한다. 기존 `put`은 ID별 갱신과 과거 스냅샷 보존을 지원하므로,
과거 30대 원문은 새 Evidence에 덮어쓰지 않고 이전 승인 데이터 버전에서 재현한다.
업무 개정 증가·기대 개정 비교는 B 등록 함수가 공통 잠금 안에서 수행한다. 기존 저장소 자체의 자동 기능으로 표현하지 않는다.
B 전용 등록 함수의 입력 검사만으로 끝내지 않는다. 공통 일반 등록에서도 이전 승인 상태와 후보의 변경 요청을 비교해
개정 증가·범위 유지·새 근거를 검사하는 공통 접점을 조율 범위에 포함한다.
반영 전 초안 수정은 기존 `draft_id`·`expected_version`을 사용하고, 이미 반영된 초안은 재사용하지 않는다.
업무 요청 수정은 새 공통 초안을 생성해 같은 노드 ID를 갱신하고 다시 검토·반영한다.
공통 `Service._run`은 저장소 잠금·권한·재시도 검사를 수행한 뒤 action을 실행한다.
B Service의 action에서 기대 개정/참조 버전을 확인하고 `_save_draft`를 호출한다.
같은 잠금 안의 검사·초안 생성과 이후 승인 시 기준 버전 거부를 격리 PostgreSQL 통합 시험으로 확인했다.
초안 이후 기준이 달라진 경우 기존 `STALE_BASE` 검사를 유지한다.

## 5. 실제 코드에서 확인한 연결 상태

아래 표는 순서 1 당시 미등록 경계의 재현 기록이다. 현재 구현·검증 상태는 5.1~5.4절이다.
이 당시 검사는 실제 PostgreSQL·Neo4j 등록 검사가 아니다.

| 검사 | 결과 |
| --- | --- |
| 신규 요청 정의를 `tbox.Extension`으로 전달해 문자열 생성 | 신규 클래스 선언 생성 가능 |
| 같은 신규 타입을 `model.validate_graph`에 전달 | `UNKNOWN_TYPE: AdditionalMaterialReviewRequest` |
| 전후 `model.SCHEMA` 타입 집합 비교 | 변경 없음 |

현재 연결은 `domain_schema`의 정적 메타데이터 → `model.SCHEMA`와 B 호환 schema → 공통 후보 검증이다.
`tbox.registered_extensions()`는 선언 합성 경로일 뿐 저장 타입 등록 API가 아니다.
기존 `lookup`은 ID·타입·버전 조회를 제공하므로 별도 `b_request_get`이나 새로운 필터 인자는 필요하지 않다.
기존 B task는 미등록 입력 검토이므로 결과를 생성한 것만으로 공통 저장이 끝났다고 보고할 수 없다.

### 5.1 현재 실행 가능한 공통 후보 검사

```bash
python3 -m examples.order_fulfillment.b_material_request
python3 -m unittest tests.order_fulfillment.test_material_request -v
```

대표 데이터는 [요청 fixture](../../examples/order_fulfillment/fixtures/material_requests.json)에 있으며,

기존 계획 100대·신규 30대·수정 40대·독립 10대는 개발용 가정이며 실제 A 계획이나 고객 수요가 아니다.
실제 catalog의 제품 구성만 참조하며 원문 해시·Evidence·synthetic 출처는 공통 검증으로 확인한다.
fixture의 `reference_data_version=0`은 예시값이다. 실제 DB 버전을 조회했다는 의미가 아니며 등록 호스트에서 실제 조회·고정해야 한다.

최신 상태에서는 같은 ID의 40대와 별도 ID의 10대가 남는다. 서로 다른 개정을 한 그래프에 넣으면 중복 ID로 거부한다.
결과의 `scope=b_request_candidate`는 공통 검증을 사용하는 메모리 후보 검사다.
정상 요청의 공통 `validate_graph`도 통과해야 예제가 종료 코드 0을 반환한다. `UNKNOWN_TYPE`을 성공으로 인정하지 않는다.
`stored`·`approved`·`neo4j_verified`는 모두 false다. 기존 catalog의 미확인 실장 경고도 제거하지 않는다.

원문 서술과 입력 수량·날짜의 일치, 관계 원문의 '동일/독립 수요' 의미 확인, 요청 당시 참조 버전의 실제 조회,
잠금 내 기대 개정 검사·재시도 멱등성은 로컬 함수가 보장하지 않는다.
이 검사는 기존 공통 등록·사람 검토와 연결할 때 구현·검증해야 한다.

### 5.2 순서 2에서 연결한 내용과 검증 한계

- `domain_schema`에 신규 요청 1종을 정적 등록했다. 공통 타입은 29종에서 30종으로 확장했고 B 메타데이터는 공통 정의의 사본을 제공한다.
- `model.validate_graph`의 B 분기에서 요청 상태 규칙을 명시적으로 실행한다. 버전은 additive 계약 변경을 반영한 `graph-0.4`다.
- 공통 `Service._candidate`가 변경된 요청의 before/after·기준 버전을 B 변경 검증 함수에 전달한다. 개정 증가·새 근거·동일 요청 범위·실제 초안 기준 버전을 검사한다.

- 필수값·허용 필드·자료형·참조·근거·자료 구분 검사는 공통 `validate_graph`가 담당한다. B는 이를 중복 구현하지 않고 수량·기준 계획·회차/제품 일치·날짜·보완 상태 등 업무 규칙을 검사한다. 정수 최솟값은 RDF와 같은 공통 메타데이터를 사용한다.
- 새 타입을 동기화할 때 표시명 누락으로 실패하지 않도록 `graph_display.py`·Browser 스타일에 항목 1개씩 추가했다. 동기화 엔진은 그대로 사용한다.
- 과거 `ab_graph_check`는 기존 fixture 11종의 검증 범위를 보고한다. 새 요청의 실제 승인·공개 검증으로 오해하지 않도록 현재 전체 타입 수와 구분한다.
- 실제 A/B/C 기존 정의·과거 fixture·해시는 보존한다. 등록 후 예제·시험은 공통 검증 통과를 요구한다.

순서 2 당시 관련 191개 검사에 메모리 공통 후보 경로의 개정·참조 버전 우회 거부, RDF/SHACL 숫자·날짜 보존,
기존 스키마·생성물 회귀, 공통 오류의 중복 보고 방지와 수신 역할 생략 허용이 포함되어 통과했다. 이는 새 B 요청의 실제 DB 승인·Neo4j 동기화 시험이 아니다.
전체 회귀는 1,635개 실행, assertion 실패 0·Neo4j 접속 설정 부족 오류 7·건너뜀 10으로 전체 성공은 아니다.
기존 PostgreSQL demo와 B 메모리 요청 예제는 종료 0이다. 실행 근거와 환경 조건은 [B 작업 기록](PROJECT_STATUS.md)의 검수 보완 항목을 따른다.
사용자 검토를 거친 구조화 입력·기대 개정 처리·실제 승인 상태 참조·호스트 호출은 아래 5.4절에 연결했다.
원문 서술의 의미 대조는 사람 검토의 책임이며, 형식·해시 검증을 수량 의미 확인으로 대신하지 않는다.
Neo4j 동기화·같은 버전의 공통 조회 검증은 실제 개발 환경에서 별도로 확인한다.

### 5.3 DB·Neo4j 연결 상태 구분

공통 코드에는 PostgreSQL 저장과 선택적인 Neo4j 투영·조회 경로가 있다. PostgreSQL 승인 스냅샷이 정본이며,
호스트는 Neo4j backend가 설정된 경우 승인 반영 후 투영을 시도한다. 두 저장소의 연결 설정과 실행 서버가 필요하다.

2026-11-03 이 worktree의 `.env`·`.env.local`은 없었으며, 기존 환경 로더에서 DB URL과 Neo4j 접속/namespace 설정도 확인되지 않았다.
따라서 이 worktree의 서비스 대상으로 설정된 DB·Neo4j 접속 성공은 미확인이다. 서버가 없거나 중단됐다고 판단한 것은 아니다.
아래 임시 검증 환경과 서비스 대상을 구분한다. 기본 조회 backend는 PostgreSQL이다.

별도 임시 PostgreSQL에서 새 B 요청의 신뢰된 등록 → 정확 초안 승인 → 저장·동일 버전 조회를 확인했다.
이 결과와 메모리 요청 예제는 현재 서비스 대상의 접속 성공을 뜻하지 않는다.
이후 소유한 임시 PostgreSQL·Neo4j에서 새 요청의 승인 반영·동기화 `ready`·같은 버전 공통 조회·근거 대조를 검증했다.
초기 Neo4j daemon 종료로 인한 접속 실패는 서버를 검사 프로세스 수명 안에서 유지해 해결했다.
이 검증은 기존 서비스 대상의 연결 성공과 구분하며 세부 범위·실행은 5.5절과 최신 B 작업 기록을 따른다.

### 5.4 B 요청 초안 등록 호출

새 Host·Agent·모델 도구를 만들지 않고 기존 B `CommonHost`의 `RequestSession.material_request_draft()`와
B `Service.prepare_material_request()`를 연결했다. 후보 조립은 `material_request.request_operations()`가 담당한다.

```python
with host.request(trusted_context) as session:
    result = session.material_request_draft(
        request_business_fields,
        supporting_nodes=source_and_evidence_nodes,
        expected_data_version=checked_data_version,
        expected_request_revision=checked_request_revision,
        request_key=stable_submission_key,
    )
```

- `request_business_fields`: 안정적인 요청 `id`와 3절의 업무 필드. 사용자가 원문과 대조한 제품·수량·날짜·사유·근거를 받는다. 납기 부족분에서 수요를 자동 생성하지 않는다.
- `type`·`origin`·`request_revision`·`reference_data_version`은 입력할 수 없다. 서버가 요청 전용 타입·synthetic·승인 개정+1·실제 기준 버전을 부여한다.
- `supporting_nodes`: 선택적인 synthetic `SourceDocument`·`Evidence` 목록. 원문 파일은 먼저 `data/sources/`에 보존한다. 기존 공통 검증이 경로·해시·참조를 확인하며 변경된 기존 근거는 거부한다. 다른 업무 노드의 동시 수정은 허용하지 않는다.
- `expected_data_version`: 사용자가 확인한 승인 데이터 버전. 공통 잠금 안에서 실제 최신 버전과 다르면 `STALE_BASE`다.
- `expected_request_revision`: 신규는 0, 수정은 현재 승인된 요청 개정. 잠금 안에서 실제 승인 상태와 다르면 `STALE_REQUEST_REVISION`이다. 미승인 초안 수정은 업무 개정을 올리지 않는다.
- 반영 전 초안을 수정할 때만 `draft_id`·`expected_version`을 함께 전달한다. 초안 작성자·최신 버전·닫힘 검사는 기존 공통 경로를 따른다.

공통 `_run(permission='draft')`의 권한·잠금·요청 키 처리를 사용하고, 같은 트랜잭션 안에서 `_save_draft`를 호출한다.
같은 actor·키·입력은 데이터가 진행된 후에도 최초 응답을 재생하며, 내용이 달라지면 멱등 충돌이다.
Session이 실행자를 고정하고 기존 실행 예산을 사용한다. AgentGateway 허용 목록·공통 승인 엔진·DB 테이블은 변경하지 않는다.

초안 생성의 `ok=true`만으로 검토 가능하다고 판단하지 않는다. 공통 계약대로 잘못된 참조·해시·필수값은
`needs_changes`와 `validation.valid=false`인 초안으로 남을 수 있고, 승인·반영은 차단된다.
검증된 초안도 다른 사람의 정확 버전 검토와 `CommonHost.apply_approved()`를 거쳐야 승인 데이터가 된다.
이 호출은 원문 파서·파일 업로드 화면·A 접수/회신·자동 수요 중복 판별을 추가하지 않는다.

실행 예제는 [PostgreSQL 등록 예제](../../examples/order_fulfillment/b_material_request_registration.py)다.
fresh `test_` schema와 개발용 DB 설정으로 실행하며 기존 메모리 예제와 구분한다.

```bash
python3 -m examples.order_fulfillment.b_material_request_registration \
  --schema test_b_material_request_demo --env-file <개발DB환경파일>
```

예제는 가상 요청만 사람 검토 대역으로 승인하고, PostgreSQL ID·타입·원문 근거 조회를 확인한다.
Neo4j 조회와 실제 운영 승인·A 처리 성공을 의미하지 않는다. 실행한 test schema는 확인용으로 남으며 재실행에는 새 이름을 사용한다.

격리 PostgreSQL에서 관련 130개 검사와 이 예제가 통과했다. 신규 30대는 데이터 v2,
40대로 수정한 같은 요청은 v3, 독립 10대 요청은 v4에 반영됐다. v2의 30대 이력과 원문 근거도 보존됐다.
개발용 다른 검토자 신원을 사용했으며 결과는 `stored=true`, `approved=true`, `neo4j_verified=false`, `a_processed=false`다.
권한 부족·자기 승인·구 기준/개정·변경된 재시도·근거 변경·승인 후 기준 변경 거부도 검사했다.
전체 회귀와 임시 DB 종료 결과는 [B 작업 기록](PROJECT_STATUS.md)의 최신 항목을 따른다.

### 5.5 Neo4j 동기화·공통 조회 검증

새 요청의 실제 저장·조회 검사는
[통합 검사](../../tests/order_fulfillment/test_material_request_graph.py)에서 실행한다.
기존 B 호스트의 초안 등록, 개발용 별도 검토자의 정확 버전 승인,
기존 공통 호스트의 승인 반영·자동 동기화를 사용한다. 요청을 Neo4j에 직접 등록하지 않는다.

```bash
python3 -B -m unittest tests.order_fulfillment.test_material_request_graph -v
```

실행 전에 소유한 격리 PostgreSQL의 `TEST_DATABASE_URL`과
`NEO4J_URI`·`NEO4J_USER`·`NEO4J_PASSWORD`·`ONTOLOGICS_GRAPH_NAMESPACE`가 필요하다.
각 검사는 별도의 UUID PostgreSQL 스키마와 Neo4j namespace를 만들고 자신이 만든 데이터만 정리한다.
환경 파일·비밀값은 Git에 넣지 않는다. 접속 실패를 skip이나 PostgreSQL 우회로 성공 처리하지 않는다.

검증 내용은 다음과 같다.

- 신규 30대 → 같은 ID의 40대 개정 → 독립 10대 요청을 실제 승인·반영한다.
  최신 수량은 40+10대이며 과거 v2의 30대와 v3의 40대도 ID·타입·근거로 조회한다.
- `ready` 응답에 이어 실제 원격 전체 스냅샷과 PostgreSQL 정본을 대조한다.
  기존 `lookup`의 요청·Evidence·SourceDocument 전체 값과 원문 위치·해시·origin을
  같은 버전의 PostgreSQL·RDF·Neo4j에서 비교한다.
  세 backend가 같은 잘못된 값을 반환하는 경우도 잡도록, 검토한 요청 입력 전체와
  예상 업무 개정·기준 데이터 버전을 별도로 대조한다. ID 조회는 정확히 1건,
  타입 조회는 예상한 요청 ID와 개수만 반환해야 한다.
  Evidence·SourceDocument 응답의 버전과 ID·타입도 확인하고,
  원문 파일 바이트의 SHA-256을 다시 계산해 조회한 해시와 비교한다.
- 읽기 권한 부족·잘못된 버전·미공개 버전·근거 연결 손상을 거부하는지 확인한다.
  손상은 시험 전용 namespace의 연결 하나에만 주입하며 운영 그래프를 수정하지 않는다.
- 동기화 장애를 주입하면 PostgreSQL 승인은 유지되지만 Neo4j 조회는 막혀야 한다.
  동일 승인 반영 재시도로 공개를 복구하고 중복 초안·물량이 생기지 않는지 확인한다.
- 미확인 기준 계획·날짜를 같은 요청 ID의 새 개정으로 보완하고 과거 상태를 보존한다.
- 조회 전후 snapshots·drafts·review_events 내용이 같아야 한다.
  기존 읽기 감사 기록을 제외한 A 접수·재고·RFQ 등의 업무 변화를 만들지 않는다.

동기화 실패와 이미 공개된 그래프의 손상은 다르게 처리한다.

| 상태 | 검사할 처리 | 완료 판단 |
| --- | --- | --- |
| 승인 저장 후 동기화 실패로 `pending` | 같은 승인 반영 키로 재시도 | 실제 원격 내용과 공통 조회까지 확인해야 복구 완료 |
| 성공한 동기화 키 재호출 | `IDEMPOTENT_REPLAY`로 과거 결과 반환 | 응답의 `ready`는 현재 그래프 상태를 증명하지 않음 |
| 공개된 그래프의 근거 연결 손상 | 공통 조회와 새 키 동기화 모두 `GRAPH_INTEGRITY` | 자동 덮어쓰기 없이 거부. 원인 조사와 별도 복구 판단 필요 |

손상 검사에서는 성공 키 재호출 후에도 실제 조회가 실패하고,
새 키 동기화 거부 후에도 최신 조회가 계속 실패하는지 확인한다.
손상된 namespace를 검사 코드가 자동 재작성하거나 정상으로 표시하지 않는다.

PostgreSQL 모드로 승인한 요청과 과거 버전은 전달 문서 6절의 기존
`python3 -m ontologics.graph_projection sync/status`로 별도 검사한다.
동일 키의 성공 재생만으로 현재 공개 상태를 판단하지 않고 실제 `status`와 공통 조회를 다시 실행한다.
실행 버전·결과·환경 정리 근거는 [B 작업 기록](PROJECT_STATUS.md)에 남긴다.
완료 표현은 **B 요청 등록·공통 읽기 가능 검증**이며 실제 A 접수·처리와 구분한다.

## 6. 사전 변경안과 조율 기록

**이 절은 순서 1에서 작성한 사전안·재현·전달 문구다. '미등록/수정 전/미확정' 표기는 당시 상태이며,
순서 2와 B 등록 호출 적용 이후의 현재 구현·권한 근거·남은 범위는 문서 첫머리와 5절을 따른다.**

아래는 **구현 위치 제안**이며 변경 승인이나 구현 완료를 뜻하지 않는다.
현재까지 공통 파일은 변경하지 않았다. 이후 공통 등록에 필요한 변경은 전달 문서의 범위 조율 절차를 따르며,
통합 T-box 생성·반영·검증은 이번 작업의 산출물로 관리한다.

| 구분 | 위치안 | 필요한 작업 |
| --- | --- | --- |
| B 정의 — 로컬 구현 | `ontologics/order_fulfillment/material_request_schema.py` | 공통 모듈을 import하지 않는 요청 타입/필드·참조·정수 메타데이터. 공통 등록에 합성하지 않은 상태 |
| B 업무 검증 — 로컬 구현 | `ontologics/order_fulfillment/material_request_validation.py` | 수량·준비 상태·날짜·계약 일치·개정 대체 검사. 공통을 대체하지 않는 B 후보 검사이며 저장·동시성 보장 없음 |
| B 검증 진입 | `ontologics/model.py`의 B 검증 분기 | 기존 B 검증과 나란히 `validate_material_requests`를 명시적으로 호출하는 안. `validate_contracts` 안에 요청 규칙을 숨기거나 호출되지 않는 B 집계 함수만 수정하지 않음 |
| B 등록 조립 | `ontologics/order_fulfillment/material_request.py` 신규 제안 | 입력→참조 확인→근거/요청 `put` 후보. 기대 개정 검사와 공통 트랜잭션 경계를 명시 |
| B 실행·검사 — 로컬 구현 | `examples/order_fulfillment/b_material_request.py`, `tests/order_fulfillment/test_material_request.py` | 신규 30대·수정 40대·독립 10대, 잘못된 입력 및 공통 미등록 경계. Host 등록·조회 예제는 후속 작업 |
| **공통 등록 필요** | `ontologics/domain_schema.py` | 기존 정적 등록 방식에 맞춰 B 요청 메타데이터를 추가하고 B 타입 집합·선택 참조·구조화 숫자 필드에 반영. B 로컬 메타데이터는 해당 정의의 호환 사본을 제공하도록 정리하는 안. monkeypatch 없음 |
| **공통 RDF 검토 필요** | `ontologics/graph_rdf.py` | 요청 `quantity`, `request_revision`의 정수 최솟값 1, `reference_data_version`의 정수 최솟값 0 반영 필요성 검토. 현재 임의 신규 숫자 필드는 자동으로 정수 SHACL이 되지 않음 |
| **공통 버전 협의** | `ontologics/model.py`의 `SCHEMA_VERSION` 등 | 신규 타입 추가에 필요한 스키마 버전·과거 승인/조회 호환 정책 결정. 현재 graph-0.3을 임의 유지/변경하지 않음 |
| **공통 변경 전후 검증 연결 필요** | `ontologics/service.py`의 후보 생성·검증 경로 | 기존 `_candidate`가 제공하는 before/after와 기준 버전을 활용해 B 개정 검증을 연결하는 최소 접점. B 전용 함수 외 일반 등록·검토·반영에서도 우회되지 않아야 함 |
| **통합 생성물 반영 필요** | `ontology/tbox.ttl` | 공통 등록 연결 후 공식 `python3 -m ontologics.tbox`로 갱신하고 `--check` 및 diff로 기존 정의 보존·B 확장분 확인. TTL만 수동 수정하거나 별도 B T-box로 대체하지 않음 |

`host.py`·`service.py`의 신원·승인·저장 엔진, `tbox.py` 생성 엔진, Neo4j 동기화 엔진을 새로 구현할 계획은 없다.
정적 등록 후 기존 RDF/Neo4j 투영과 `lookup`이 자동으로 수용하는 범위는 실제 검사로 확인한다.
최소 변경 목록은 사전 코드 검토안이며 실제 통합 전에 추가 영향이 발견되면 범위를 다시 명시한다.
A `materials` 애플리케이션·에이전트, C 미지원 관계·검증, `.gitignore`는 수정 대상이 아니다.
새 공개 API·인증·권한·DB 테이블·Agent를 필수 산출물로 추가하지 않는다.

### 6.1 순서 1의 결과 — 조율할 최소 변경안

이 절은 구현 범위 제안이다. 공통 담당자의 합의·승인이나 등록 구현 완료를 뜻하지 않는다.
이번 순서에서는 공통 실행 코드·TTL·DB를 수정하지 않았다.

| 대상 | 제안하는 변경 | 범위와 검증 조건 |
| --- | --- | --- |
| `domain_schema.py` | 신규 요청 1종과 그 필수/선택 필드·참조·숫자 필드를 정적 등록 | 기존 29종의 정의·의미는 보존. 신규 타입을 B 타입 집합에 포함하고 기존 공통 합성 경로 사용 |

| `model.py` | B 검증 분기에서 신규 요청 규칙 호출, 스키마 버전 변경 검토 | 전체 후보 그래프의 참조를 사용. 잘못된 요청이 초안·검토·반영 어느 경로에서도 검증을 우회하지 않는지 확인 |
| 공통 `service.py` | 기준 상태와 후보 변경분을 비교하는 B 검증의 최소 연결 | 기존 `_candidate`의 before/after·기준 버전을 활용. 일반 `prepare_draft`와 초안 수정·검토·반영에서도 동일 규칙 적용. 새 저장/승인 엔진을 만들지 않음 |
| `graph_rdf.py` | 요청 정수 3필드의 최솟값 등록 | `quantity >= 1`, `request_revision >= 1`, `reference_data_version >= 0`. bool·소수 거부와 RDF/SHACL 일치 검사 |
| `ontology/tbox.ttl` | 정식 등록 후 공식 생성기로 통합 파일 갱신 | `python3 -m ontologics.tbox` 및 `--check`. 기존 클래스·속성 의미 보존과 신규 선언을 diff로 확인 |
| B Service·RequestSession | 후속 순서에서 신뢰된 요청 등록 호출 연결 | 기존 `_run` 잠금 안에서 참조 버전·기대 개정 검사 후 `_save_draft`. 공통 권한·멱등 처리 재사용. 모델 승인 도구 추가 없음 |

현재 `graph-0.3`에 새 타입을 추가하는 것은 계약 변경이다. 새 버전 번호·적용 시점은 공통 범위 조율에서 정한다.
버전 문자열만 올리면 이전 자료의 조회가 자동 보장되는 것으로 보지 않는다.
RDF는 현재 스키마 버전을 검사하고, Neo4j는 버전·해시·스키마 정보가 맞는 투영을 요구하며,
읽기 체크포인트는 그래프 스키마 버전을 검사한다. 따라서 아래 조건을 함께 확인한다.

- 기존 승인 PostgreSQL 스냅샷·원문을 덮어쓰지 않고 신규 코드의 기존 데이터 조회를 검증한다.
- 필요한 RDF/Neo4j 투영 재생성과 기존 읽기 체크포인트의 거부·재시작 동작을 검증한다.
- 기존 초안의 검토·반영은 현행 검증과 정확 버전 조건을 유지한다. 업그레이드만으로 승인 상태를 부여하지 않는다.
- 위 범위에서 호환 문제가 발견되면 재현 자료와 필요한 추가 변경을 먼저 명시한다.

공통 `service.py`에는 변경 전후 검증을 호출하는 최소 연결을 조율 대상으로 포함한다.
승인/저장 엔진 재작성, 공통 `host.py`·`tbox.py` 생성 엔진·Neo4j 엔진 변경은 현재 최소안에 포함하지 않는다.
추가 변경이 필요한 문제가 재현되면 위치·이유·시험을 명시해 범위를 다시 조율한다.
새 DB 테이블·B 전용 저장소·직접 Cypher 등록·추가 Agent·A 처리 코드는 제안하지 않는다.

### 6.2 재현 근거와 조율 항목

2026-11-03 다음 명령을 재실행했다. DB를 사용하지 않는 B 로컬 예제다.

```bash
python3 -B -m examples.order_fulfillment.b_material_request
```

신규 30대·수정 40대·독립 10대의 로컬 후보/개정 검사는 통과했다.
같은 신규 요청의 공통 검증은 `UNKNOWN_TYPE: AdditionalMaterialReviewRequest`로 실패했다.
`stored=false`, `approved=false`, `neo4j_verified=false`를 유지한다. 예제 종료 코드 0은 미등록 경계 재현까지 포함한 예상 결과다.

공통 담당자와 조율할 내용은 다음 세 묶음이다. 이 문서는 전달용 근거이며 실제 메시지를 발송하지 않았다.

1. 위 정적 메타데이터·공통 상태/변경 전후 검증 호출·RDF 정수 제약의 최소 변경 파일 범위. `service.py`의 최소 검증 연결을 포함.
2. 스키마 버전 번호·배포 적용 시점과 기존 자료/투영/초안/체크포인트의 호환 검증 범위.
3. 위 등록 후 공식 통합 T-box를 생성·반영하고, 후속 B 등록 호출은 기존 잠금·승인 경로를 재사용하는 방식.

순서 1의 로컬 조사·변경안 정리는 완료다. 공통 범위 합의는 아직 확인되지 않았으며,
전달 문서 2절에 따라 공통 코드 구현 전에 조율해야 한다. 다음 구현의 첫 목표는 신규 요청 1건의
공통 검증 통과이며, 이후 승인 저장·Neo4j 동기화·조회까지 연결한다.

#### 조율용 전달 문구

아래는 사람이 전달할 수 있도록 준비한 문구이며 실제 발송하지 않았다.

> integration/a-b 기준 B 1차의 추가 생산 자재 검토 요청 등록 연결을 확인했습니다.
> B 요청 정의·로컬 검증·30대 신규/40대로 수정/독립 10대 데이터는 준비했으나,
> 공통 검증은 아직 AdditionalMaterialReviewRequest를 UNKNOWN_TYPE으로 거부합니다.
>
> 기존 경로로 등록하려면 domain_schema.py의 신규 타입/필드 등록,
> model.py의 B 요청 상태 검증 연결, service.py의 기준 상태·변경분을 사용한 개정 검증 연결,
> graph_rdf.py의 정수 3필드 조건 반영이 필요합니다.
> 공통 Service의 검증 연결은 일반 prepare_draft로 개정·새 근거 검사를 우회하지 못하게 하기 위한 최소 변경입니다.
> 승인·저장 엔진과 권한·잠금·멱등 처리는 재사용하고 새 저장소·테이블은 만들지 않습니다.
>
> 위 변경 파일 범위와 스키마 버전 번호·적용 시점, 기존 자료/초안/투영 호환 검증 범위를 확정하려고 합니다.
> 범위가 정해지면 공식 생성기로 통합 ontology/tbox.ttl을 갱신하고 관련 예제·시험도 함께 변경합니다.
> A 처리 코드는 수정하지 않고, 최종 검증 목표는 B 요청 등록·Neo4j 동기화·기존 공통 조회의 내용 일치입니다.
> 결과는 feature/b-ab-connection 브랜치로 공유하고 PR은 생성하지 않습니다.

#### 순서 1의 종료 상태와 다음 단계 조건

| 항목 | 현재 상태 | 남은 결정/행동 |
| --- | --- | --- |
| 변경 이유·위치·오류 재현 | 로컬 조사 완료 | 공통 UNKNOWN_TYPE과 후보/개정 검사의 차이를 근거로 전달 가능 |
| 공통 변경 범위안 | 준비 완료 | 위 4개 공통 코드 파일의 최소 변경 및 통합 TTL 생성 범위 조율 |
| 스키마 버전·적용 | 미확정 | 현재 graph-0.3에서의 확장 버전 번호와 적용 시점 결정. 문서에서 임의 번호 확정 안 함 |
| 기존 자료·초안·투영 호환 | 검증 기준 준비 | 기존 승인 내용 보존, 투영 재생성·체크포인트 처리 기준을 변경 범위와 함께 확정 |

따라서 **순서 1의 로컬 산출물은 준비 완료, 외부 조율 결과는 미확인**으로 구분한다.
사용자의 '순서 1 마무리'를 공통 코드·TTL 수정 승인이나 담당자 합의로 해석하지 않는다.
조율 자료를 반복해서 늘리는 대신 이 절을 사용하며, 범위가 확정되면 같은 문서에 결과를 기록하고 순서 2로 이동한다.

### 공통 연결 원칙

1. B 정의를 공통 `domain_schema`에 정식 합성하는 파일/담당 범위.
2. RDF 숫자 제약과 스키마 버전·이전 승인 데이터 호환 반영 범위.
3. 공통 등록 변경 후 공식 통합 T-box 생성·반영과 기존 선언 보존 검사. 사용자 별도 반영 대기로 남기지 않음.
4. B Service에서 기존 `_run`의 잠금 내 action과 `_save_draft`를 재사용하는 안. 중첩 `_run`이나 별도 저장 트랜잭션을 만들지 않고 통합 시험으로 확인.
5. B 전용 입력 검증을 우회해 공통 `prepare_draft`를 직접 호출해도 개정·새 근거·참조 버전 검증을 건너뛸 수 없어야 함. 구체 접점과 회귀 검사는 6.3절 기준으로 조율.

위 연결이 해결되기 전에도 B 입력안·검증 규칙·예제는 준비할 수 있다.
그러나 별도 B 저장소·직접 Cypher INSERT·시드 적재를 승인 등록의 대안으로 사용하지 않으며,
신규 타입의 실제 등록·조회 완료로 보고하지 않는다.

### 6.3 일반 등록 경로의 변경 전후 검증

`validate_material_requests`는 후보 상태를 검사하고, `validate_request_transition`은 이전 요청과 수정 요청을 비교한다.
공통 `validate_graph`에 전자만 연결해도 후자가 자동 실행되는 것은 아니다.
현재 일반 `prepare_draft`는 공통 `_candidate`와 `validate_graph`를 사용하며 B 전용 입력 함수를 거치지 않는다.
따라서 공통 후보 생성·검증 경로에 B 변경 전후 검증을 연결하는 최소 변경을 조율해야 한다.
검증 규칙 자체는 B에 두고, 공통은 기준 버전·before/after 전달과 호출·실패 처리를 담당하는 안이다.

2026-11-03 메모리 검사에서 신규 30대 요청의 수량만 40으로 바꾸고 개정·근거를 유지하면
로컬 후보 검사는 통과했지만 개정 검사는 `INVALID_REQUEST_REVISION`, `NEW_EVIDENCE_REQUIRED`로 실패했다.
이는 두 검사가 다름을 재현한 결과다. 현재 공통 타입은 미등록이므로 실제 저장 우회를 재현했다는 뜻은 아니다.

연결 구현은 다음 조건을 만족해야 한다.

- B 전용 등록, 일반 `prepare_draft`, 반영 전 초안 수정에서 변경 요청을 같은 기준으로 검사한다.
- 신규 요청은 개정 1, 수정은 이전 승인 개정 + 1이며, 수정의 제품/계약/기준 계획/필요 조건 범위를 유지하고 새 근거를 요구한다.
- B 입력의 기대 개정은 잠금 내 현재 승인 개정과 대조한다. 공통 경로도 이전 승인 상태 대비 개정 증가를 검사해 단순 필드 위조를 허용하지 않는다.
- 신규·수정 요청의 `reference_data_version`은 실제 검사한 초안 기준 버전과 대조한다. 변경되지 않은 과거 요청의 참조 버전을 현재 버전으로 일괄 변경하거나 거부하지 않는다.
- 검토·반영에서도 해당 초안의 기준 상태와 후보 변경분을 다시 검사하고, 기존 정확 초안 버전·내용 해시·`STALE_BASE` 조건을 유지한다.
- 같은 요청 키·같은 입력 재시도는 기존 공통 멱등 처리를 사용한다. 변하는 시각·자동 생성 ID를 재시도 입력 해시에 매번 새로 넣는 방식을 피한다.
- 신규 타입에 한정해 연결하며 기존 A/B/C 자료의 등록·승인 동작을 바꾸지 않는지 회귀 검사한다.

최소 시험은 정상 30→40 수정, 개정 유지/건너뛰기, 새 근거 누락, 허위 참조 버전,
일반 등록을 통한 동일 잘못된 수정, 초안 수정 시 우회, 두 초안 경합 후 구 기준 반영 거부다.
공통 접점의 구체 함수와 호출 순서는 후보 형태 검증·기존 오류 계약을 보존하는 조건으로 구현 전에 확정한다.
이 문서 보완만으로 위 우회 방지가 구현됐다고 보고하지 않는다.

### 6.4 정식 등록 전후 예제·시험의 성공 기준

| 단계 | 예제·시험의 기대 결과 | 의미 |
| --- | --- | --- |
| 현재 미등록 상태 | 로컬 검사 통과 + 공통 `UNKNOWN_TYPE` 확인 | 미등록 경계 재현. 저장 성공 아님 |
| 정식 타입/검증 연결 후 | 정상 요청의 공통 검증 통과, 잘못된 필드/참조/수량 거부 | 공통 데이터 계약 연결. DB 저장 성공 아님 |
| 등록 통합 검사 후 | 정확 초안 검토·반영, PostgreSQL 승인 버전과 Neo4j ready·기존 조회의 내용 일치 | 실제 등록·동기화·조회 검증 |

정식 등록을 구현하는 변경에서 `examples/order_fulfillment/b_material_request.py`의 종료 조건과
`tests/order_fulfillment/test_material_request.py`의 현재 `UNKNOWN_TYPE` 기대를 함께 수정한다.
등록 후에도 신규 타입의 미등록 실패를 성공 조건으로 남기거나, 등록 여부에 따라 두 결과를 모두 성공으로 허용하지 않는다.
import/로컬 검사가 런타임 스키마를 변경하지 않는 검사는 유지하되, 타입의 정식 등록 여부와 분리한다.
메모리 예제의 `stored`·`approved`·`neo4j_verified`는 타입 등록 후에도 false다.
별도 통합 검사에서 실제 수행·확인한 결과만 성공으로 보고하며, 예제 종료 코드만으로 세 값을 true로 바꾸지 않는다.
현재는 정식 등록 전이므로 실행 코드·시험의 기존 미등록 기대를 미리 변경하지 않는다.

기존 회귀 검사도 확장 영향에 포함한다. `test_schema_extraction.py`에는 과거 B 타입 목록과 현행 타입 집합의
일치를 요구하는 검사가 있고, `test_schema_export.py`에는 현행 `graph-0.3` 및 추가 타입 수를 고정한 검사가 있다.
정식 등록 시 과거 타입의 정의·순서 보존 검사와 신규 요청 1종의 추가 검사를 분리하고, 새 계약에 해당하는 기대값만 변경한다.
과거 모델 fixture·원본 해시·역사 버전 기대를 현행 값으로 덮어쓰거나 검사를 삭제해 통과시키지 않는다.
버전 문자열·타입 수만 맞춰 검사를 약화하지 않고 기존 필드·참조·허용 조건 보존을 계속 검사한다.

3. 공통 타입·상태/변경 전후 검증·RDF 조건을 연결하고 공식 통합 T-box 생성·검사. 예제·시험의 기대를 6.4절의 등록 후 기준으로 함께 전환.
4. 최소 요청 1건으로 검증→공통 초안→다른 개발 검토자 승인→정확 반영 경로 연결. 일반 등록 우회 방지 검사 포함.
5. 같은 격리 schema/새 Neo4j namespace에서 동기화 `ready`와 ID·타입·근거 조회 확인.
6. 아래 정상·실패 검사와 기존 B/공통 관련 회귀, 저장소 지침의 전체 검사·demo 수행.
7. 결과·미검증·의존성을 정리한 뒤 사용자 지시에 따라 커밋·명시적 작업 브랜치 push. PR 생성 없음.

| --- | --- |

| 날짜·조건 | 날짜만 보존, offset 시각, 회차 기한 상속, 고객 도착지 누락, 변경 조건 미확인 |
| 요청 분리·관계 | 다른 제품·필요 날짜/기준은 별도 요청, 동일 수요 중복 합산 없음, 독립 수요 별도 ID, 관계 미확인 시 보완, 이전 요청 유효 물량 미확인인 대체 요청은 `ready` 거부 |
| 참조·원문 | 회차만 지정해도 제품 불일치 거부, 품목/회차 소속 불일치, 미등록 ID, 외부 문서 번호와 내부 ID 구분, 미지원 C 노드 참조 거부, 근거 누락·해시 불일치, synthetic 구분 |
| 등록·권한 | 자기 승인·미승인 반영·구 초안·구 기준 버전·권한 부족 거부 |
| 일반 등록 우회 방지 | B 전용 호출과 일반 초안 생성·수정·검토·반영에서 개정 증가·새 근거·실제 참조 버전 검사. 변경 없는 과거 요청 보존 |
| 등록 후 기대 전환 | 정상 요청은 공통 검증 통과를 요구. UNKNOWN_TYPE을 계속 성공 처리하지 않음. 로컬 예제와 실제 저장 검증 구분 |

| 공개 오류 | pending·잘못된 버전·깨진 참조를 성공 처리하지 않고 조용한 backend 우회 없음 |

시험에는 소유한 격리 DB/schema·새 Neo4j namespace와 가상 요청을 사용한다.
기존 사용자 DB·서버·운영 namespace는 사용하거나 초기화하지 않는다.
미등록 B task 결과·seed·메모리 검사·모델 대역을 실제 승인·Neo4j 통합 검증과 구분한다.

## 8. 이번 단계의 결과와 다음 작업

- 완료: 정적 타입 등록·상태/변경 전후 검증·RDF 정수 조건·통합 T-box에 이어 B 등록 호출의 실제 참조 조회·기대 개정·공통 잠금/멱등 처리를 연결했다.
- 새 요청 PostgreSQL 검증: 관련 130개 검사와 등록 예제 통과. 신규 30대·수정 40대·독립 10대의 다른 개발 검토자 승인·v2/v3/v4 저장·과거 버전·근거 조회를 확인했다.
- 전체 회귀의 최신 결과와 이전 실행의 보완 이력은 [B 작업 기록](PROJECT_STATUS.md)에서 구분한다. 환경 오류·건너뜀을 포함한 실행을 전체 성공으로 표현하지 않는다.
- 새 요청 Neo4j 검증: 소유한 임시 PostgreSQL·Neo4j에서 승인 반영·동기화 `ready`·같은 버전 ID/타입/원문 근거 조회와 과거 버전 보존·실패 재시도·보완 개정을 확인했다.
- 남은 외부 범위: 기존 서비스 대상의 접속 설정·실제 인증/운영 승인·A 애플리케이션의 발견·접수·처리. 이번 개발용 통합 검사로 완료 처리하지 않는다.
- 최종 검사: 그래프 집중 32개·CLI sync/status 통과. 전체 1,669개 실행 중 실패0·오류0·환경 조건 skip10, 공통 demo·등록 예제 종료0. 임시 서버·데이터·비밀값·실행 파일 및 실제 포트 종료 확인.
- 다음: 최종 변경 내역과 검증 기록을 검토해 사용자 지시의 작업 브랜치 공유 범위를 따른다. 커밋·push·PR은 이번 검증에서 실행하지 않았다.
- 보고 문구: 검증 후에도 A 업무 구현이 없으면 **“B 요청 등록·공통 읽기 가능 검증”**으로 한정한다.
