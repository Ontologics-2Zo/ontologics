# claim_response 데이터 정책 추가

> 기능: C 클레임 대응 (`claim_response`)
> 기준 문서: [서비스 명세 - 공통 의미와 데이터 경계](../SERVICE_SPEC.md), `C_온톨로지_스키마_확장_전달안.md` 7장
> 상태: 팀 승인 완료. 공통 문서(`SERVICE_SPEC.md`) 반영은 공통 담당자가 병합할 때 진행한다.

## 1. 요약

- 기존 허용 범위는 그대로 둔다. C 클레임 대응에 필요한 가상 기록만 **추가로** 허용한다.
- 추가 허용: 생산라인과 보드별 생산 기록, 고객 클레임, 시험 결과, 조치 판정, 그리고 이를 잇는 품질 사건·영향 범위·중단 요청서·재생산 요건.
- 모두 시연용 가상 기록이며 실제 OLIMEX 제품의 결함이나 실제 공장 조치로 설명하지 않는다.

## 2. 기존 정책 원문

`SERVICE_SPEC.md` "공통 의미와 데이터 경계":

> 실제 자료는 OLIMEX 공개 사양·설계·BOM이다. 가상 기록은 회사의 재고·입출고, 개별 제품·부품 로트 식별, 장착·제거와 그 이력의 확인 범위에 한정한다. 가상 검사 결과·고장 원인·불량률·가동 시간은 허용 범위에 추가하지 않는다. 사용자 조사 요청과 확인된 사실도 구분한다.

C 기능은 이 범위 밖의 기록(클레임, 생산라인, 시험 결과, 조치 판정)이 필요해서 전달안 7장으로 정책 보완을 요청했고 팀 승인을 받았다.

## 3. 추가로 허용하는 가상 기록

| 단계 | 타입 | 한글 이름 | 기록하는 것 | 스키마 상태 |
|---|---|---|---|---|
| 1차 | `ProductionLine` | 생산라인 | 가정 회사의 생산라인 | 반영됨 |
| 1차 | `UnitProductionRecord` | 보드 생산 기록 | 보드가 어느 라인에서 언제 생산됐는지 | 반영됨 |
| 1차 | `ClaimIntake` | 클레임 접수 | 가정 고객의 메일·엑셀·CSV 신고 원문 변환 초안 | 반영됨 |
| 1차 | `QualityCase` | 품질 사건 | 사람이 확인한 클레임 사건과 대상 보드 | 반영됨 |
| 1차 | `QualityScope` | 영향 범위 | 조사·보류 대상 보드 목록 | 반영됨 |
| 1차 | `ContainmentRequest` | 중단 요청서 | 생산 중단·출고 보류 요청 문서 | 반영됨 |
| 2차 | `TestRequest` | 테스트 의뢰 | 테스트팀에 보내는 시험 대상 보드와 의뢰 문서 | 반영됨 |
| 2차 | `QualityTestResult` | 테스트팀 결과 | 테스트팀이 돌려준 보드별 가상 시험 결과와 조치 판정 | 반영됨 |
| 2차 | `ReproductionRequirement` | 재생산 요건 | 재생산 필요 정상 수량 | 반영됨 |

2026-10-29 팀 회의로 시험 방법·실행·판정은 테스트팀 담당이 됐다. 그래서 시험 시나리오와 C의 조치 판정 타입은 두지 않는다.

## 4. 지켜야 할 조건

1. 위 타입은 모두 `origin=synthetic`이다. `model.py`의 `SYNTHETIC`에 등록되어 있어 `real`로 넣으면 검증에서 거부된다.
2. 모든 노드는 가상 `SourceDocument`·`Evidence` 근거를 가진다. 원본 파일은 `data/claim_response/` 안에 둔다.
3. 고객사·클레임 번호·납품 문서 번호는 가정 값이며 `DEMO` 표시를 넣는다(예: `DO-DEMO-C-001`). 실제 회사·고객 이름을 쓰지 않는다.
4. `reported_symptom`은 **고객 신고 원문**이다. 확인된 고장이나 고장 원인으로 표현하지 않는다.
5. `QualityScope`의 보드 목록은 **조사·보류 대상**이다. 불량 보드 목록이 아니다.
6. 시험 결과와 조치 판정은 테스트팀이 정해서 돌려준다. C는 판정을 만들거나 바꾸지 않고, 시험 불합격만으로 자동 폐기·재생산 판정을 만들지 않는다. 시험하지 않은 보드는 결과 행이 없고 미검사로 센다.
7. 같은 라인이나 같은 부품 로트라는 공통점으로 고장 원인을 자동 확정하지 않는다.
8. 실제 OLIMEX 자료(사양·설계·BOM)에 C 기록을 섞지 않는다. 연결은 이미 가상인 `ProductUnit`을 통해서만 한다.

## 5. 여전히 허용하지 않는 것

- 고장 원인 확정, 불량률, 가동 시간
- C 범위 밖의 가상 검사 기록(장착 이력 조사 등 기존 기능에 시험 결과를 끼워 넣는 것)
- 기존 자유 필드에 시험·원인 정보를 넣는 방식
- 완성 보드 재고·출하(`FinishedGoodsStock`, `Shipment`)는 B 담당 정의를 따른다. C에서 따로 만들지 않는다.

## 6. 공통 문서 반영 제안

`SERVICE_SPEC.md` "공통 의미와 데이터 경계"의 기존 문장 뒤에 아래 문장을 추가한다. 기존 문장은 지우지 않는다.

> C 클레임 대응 범위에 한해 생산라인과 보드별 생산 기록, 고객 클레임, 품질 사건·영향 범위, 생산 중단·출고 보류 요청서, 시연용 시험 결과와 조치 판정, 재생산 요건을 가상 기록으로 허용한다. 클레임 증상은 고객 신고 원문이며, 시험 결과는 가상 관측일 뿐 실제 제품의 고장 원인이나 불량률로 취급하지 않는다. 세부 조건은 [claim_response 데이터 정책](claim_response/DATA_POLICY.md)을 따른다.
